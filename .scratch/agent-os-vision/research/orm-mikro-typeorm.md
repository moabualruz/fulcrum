# ORM Evaluation: TypeORM vs MikroORM for Fulcrum Agent OS

**Purpose:** Deep technical comparison for Fulcrum's local-first Agent OS.
**Hard constraint:** NO plaintext SQL anywhere — no `.sql` files, no raw SQL strings in code.
**Stack:** Bun >= 1.3, TypeScript, SvelteKit, PGlite (local-first) + Postgres (SaaS).
**Date:** 2026-05-01

---

## Section 1: Decorator UX

**TypeORM** offers familiar Active Record / Data Mapper duality. Decorator ergonomics are well-known, tutorials abundant. However, the DX has rough edges:
- Type inference on relations is weak — loaded relations don't narrow types.
- `@EntityRepository` was deprecated in v0.3.0+ without clear migration path.
- Query builder doesn't validate relation names at compile time.
- `reflect-metadata` is still required (v0.3.x).

**MikroORM** enforces Data Mapper only — cleaner architecture but steeper onboarding. Key DX strengths:
- `Loaded<T, Hint>` type propagates populate hints through the type system.
- `em.fork()` + Unit of Work prevents accidental cross-request state pollution.
- v7 `defineEntity` helper enables fully typed entity definition without decorator lock-in.
- `Rel<>` wrapper for circular refs works cleanly in ESM/Bun.
- v7 zero-dependency core makes cold starts faster in serverless/Bun contexts.

**Winner (decorator UX):** MikroORM, primarily due to TypeScript inference quality. The `Loaded<T>` type prevents an entire class of runtime bugs where code accesses unloaded relations. For a ~30-table schema with complex joins, this matters at scale.

## Section 2: PGlite Story

This is the most critical axis for Fulcrum's local-first default.

**TypeORM + PGlite:**
- Community package `typeorm-pglite` exists on npm. ~10 stars, single maintainer.
- Works by injecting `PGliteDriver` into `DataSource({ type: 'postgres', driver: new PGliteDriver().driver })`.
- Feature request to make PGlite a native datasource **was closed as not planned** (Aug 2024). [9]
- Risk: if maintainer abandons `typeorm-pglite`, Fulcrum is stuck or must fork.
- No official testing, no guarantee of parity on schema generation, migrations, or pgvector.

**MikroORM + PGlite:**
- Official `@mikro-orm/pglite` package is **in PR (#7622)**, ready to merge into v7.1.
- Blocked only on Kysely 0.29 reaching stable (currently 0.28.16, "0.29 getting closer").
- Community package `mikro-orm-pglite` available now — passed 99% of PostgreSQL test suite. [11]
- Architecture: `@mikro-orm/pglite` extends `@mikro-orm/postgresql` abstractions without coupling to native `pg` — exact same pattern as SQLite drivers.
- Dual targeting (PGlite local / Postgres SaaS): driver swap in config; entities unchanged.

**Winner (PGlite story):** MikroORM by a wide margin. The official driver is weeks/months away (pending Kysely 0.29), not "not planned". The community package already passes the full test suite. TypeORM's PGlite adapter is fragile community software with no official backing.

**Practical path for Fulcrum:**
1. Use `mikro-orm-pglite` community package immediately.
2. Switch to `@mikro-orm/pglite` (official) once v7.1 lands.
3. PGlite env (local-first) and Postgres env (SaaS) share identical entity classes; driver injected at startup from env config.

## Section 3: Migration Ergonomics

**The hard truth:** Both ORMs generate migration classes containing raw SQL strings. There is no fully decorator-pure migration system in either ORM. The "no plaintext SQL" constraint applies to production query code and schema definition — migration files will inevitably contain SQL strings inside `this.addSql()` (MikroORM) or `queryRunner.query()` (TypeORM). This is unavoidable without writing a bespoke code generator.

**Key differences:**

| Aspect | TypeORM | MikroORM |
|---|---|---|
| Auto-generate from entity diff | Yes — `typeorm migration:generate` diffs DB vs entities | Yes — `mikro-orm migration:generate` diffs snapshot vs entities |
| Snapshot system | No — diffs against live DB schema | Yes — stores schema snapshot in migrations folder. Can generate migration before running pending ones. |
| Migration file format | TypeScript class with `queryRunner.query(sql)` | TypeScript class with `this.addSql(sql)`. `TSMigrationGenerator` customizable. |
| Idempotency / ordering | Timestamp-based file names | Snapshot-based — prevents ordering issues |
| Rollback (down()) | Auto-generated | Auto-generated |
| Pre-v7 migration engine | umzug library | No longer umzug (v7) — custom engine built in |
| CLI | `typeorm migration:generate`, `migration:run` | `mikro-orm migration:generate`, `migration:create`, `migration:up` |

**MikroORM snapshot approach** is superior for multi-developer teams: generating a migration before all prior ones have run works correctly because the snapshot represents the target state, not the live DB. TypeORM's approach of diffing against live DB can produce incorrect migrations in concurrent dev workflows.

**Winner (migration ergonomics):** MikroORM, due to snapshot-based diffing and the customizable `TSMigrationGenerator`.

## Section 4: Vector / Full-Text Search Support

**pgvector:**
- **TypeORM:** Native since v0.3.27. `@Column('vector', { length: N })`. Clean decorator support. [24]
- **MikroORM:** Custom `VectorType` from `pgvector/mikro-orm`. `@Property({ type: VectorType })`. Known issue #5739 (schema generator drift on `vector(N)`) was fixed; follow-up #6008 (no-length vector drift) exists. [25]
- **Verdict:** TypeORM slightly ahead on pgvector — native column decorator vs custom type. MikroORM's schema generator drift issue is a real operational concern for automated CI migrations.

**Full-text search (tsvector / GIN):**
- **TypeORM:** `tsvector` is a recognized type string. GIN index creation requires either migration SQL or `@Index()` with non-standard type specification. `ts_rank` in queries requires raw SQL via query builder. No fully decorator-based FTS path.
- **MikroORM:** `@Index({ type: 'GIN' })` via decorator. `raw()` helper for `to_tsvector()` and `ts_rank` expressions in queries — keeps SQL fragments inline in TS code rather than in separate `.sql` files. `PostgreSqlPlatform` has platform-specific knowledge of GIN/GiST.
- **Verdict:** MikroORM slightly ahead on FTS — better index type expression via decorators, cleaner raw fragment handling.

**JSONB:**
Both support `type: 'jsonb'` via decorator. MikroORM supports querying nested JSON properties via filter syntax; TypeORM requires query builder with raw JSON operators.

## Answering the Specific Questions

### 1. Which ORM has strongest NestJS-style DX?

**MikroORM** has deeper NestJS DX in 2025-2026:
- `@mikro-orm/nestjs` provides auto-registration when repositories follow `EntityNameRepository` naming — eliminates `@InjectRepository()` boilerplate.
- `@CreateRequestContext()` / `@EnsureRequestContext()` decorators handle queue workers, scheduled tasks, and WebSocket contexts — TypeORM has no equivalent.
- `getRepositoryToken()` for mock injection in tests.
- `MikroOrmModule.forRoot()` accepts `autoLoadEntities: true`.
- Type-safe repository methods (via `Loaded<T>`) propagate into service layer types.

TypeORM's `@nestjs/typeorm` is maintained by the NestJS team (official), which is a credibility point. But DX depth — type safety, context management, testing utilities — favors MikroORM.

### 2. PGlite: documented adapter or write-one?

Neither has a production-shipped, fully documented official adapter **today** (May 2026):

- **TypeORM:** `typeorm-pglite` (community, ~10 stars) — functional but unsupported. Would need to fork or maintain internally.
- **MikroORM:** `mikro-orm-pglite` (community, 99% test pass rate) + `@mikro-orm/pglite` in PR — **use community package now, upgrade to official on v7.1 release**.

The MikroORM community package for PGlite is substantially more battle-tested than the TypeORM equivalent. For Fulcrum, the correct path is: deploy with `mikro-orm-pglite`, track Kysely 0.29 release, switch to official package.

### 3. Migration story when entity decorator changes?

**MikroORM workflow:**
1. Edit entity decorators (add column, rename, add index).
2. Run `mikro-orm migration:generate --name=AddOrgIdIndex`.
3. MikroORM diffs current entity metadata against stored schema snapshot.
4. Outputs `migrations/Migration20260501_AddOrgIdIndex.ts` — class extending `Migration` with `this.addSql(...)` calls.
5. Snapshot updated automatically.
6. Run `mikro-orm migration:up` in CI/deploy.

**TypeORM workflow:**
1. Edit entity decorators.
2. Run `typeorm migration:generate -d datasource.ts AddOrgIdIndex`.
3. TypeORM connects to DB and diffs live schema vs entity metadata.
4. Outputs `migrations/1234567890-AddOrgIdIndex.ts` — class with `queryRunner.query(...)`.
5. Run `typeorm migration:run`.

Both generate SQL inside migration class methods. Both have class-based migration files. The generated SQL strings are unavoidable — they live inside TS class methods, not in `.sql` files. This satisfies the spirit of "no `.sql` files" even if raw SQL strings appear inside TS.

### 4. Escape hatch for ORM-unfriendly cases (CREATE EXTENSION, ts_rank, EXPLAIN ANALYZE)?

**MikroORM escape hatches (preferred):**
- `raw(sql_fragment)` helper — inline raw SQL in filter/where/select without a separate file.
- `sql` tagged template — `sql\`lower(name)\`` for expressions.
- `em.getKysely()` — access the Kysely instance directly for full query builder access.
- `em.execute(query)` — for DDL like `CREATE EXTENSION vector` in migration `up()` methods.
- All of this is inline TypeScript — no `.sql` files, no string literals in separate modules.

**TypeORM escape hatches:**
- `dataSource.query(sql)` — raw query execution.
- `createQueryBuilder().where('col @@ plainto_tsquery(:q)', { q })` — raw fragments in QB.
- These work but produce scattered raw SQL strings throughout the codebase.

MikroORM's `raw()` + Kysely access is cleaner: raw SQL stays as expression fragments co-located with query logic, not standalone SQL strings or separate files.

### 5. Production case studies: TypeORM or MikroORM on Bun + PGlite?

**No documented production case of TypeORM + Bun + PGlite found** (as of May 2026). TypeORM on Bun with standard Postgres (via pg driver) is deployed in production but with decorator metadata workarounds required.

**No documented production case of MikroORM + Bun + PGlite** found either. MikroORM v7 on Bun with standard Postgres is working (migration issue #5690 was resolved). The PGlite combination is pre-production as of this writing.

**This is a frontier combination.** Fulcrum would be an early production adopter. The risk is managed by: using community packages that pass test suites, tracking official package releases, and having the fallback strategy below.

### 6. Failure gates / C3 fallback strategy

**Primary:** MikroORM v7 + `mikro-orm-pglite` (community) → migrate to `@mikro-orm/pglite` (official v7.1).

**Failure gate:** If `@mikro-orm/pglite` PR stalls (Kysely 0.29 delayed > 3 months or abandoned):
- **Fallback 1:** Keep using `mikro-orm-pglite` community package; pin version; fork if needed. Community package passed 99% of test suite — functional risk is low.
- **Fallback 2:** Write a thin `@mikro-orm/pglite` driver by following the PR diff (PR #7622 is public; the code is straightforward since it mirrors the SQLite driver pattern).

**If MikroORM itself fails on Bun + PGlite (catastrophic):**
- **Fallback 3 (C3):** Switch to **Drizzle ORM** with PGlite. Drizzle has official PGlite support, official Bun support, but violates the "no raw SQL" constraint — Drizzle's migrations are SQL files and its schema is SQL-like (though TypeScript). This would require re-evaluating the "no SQL files" constraint.
- **Fallback 4 (nuclear):** Write a thin custom ORM layer over PGlite/pg using TypeScript classes and a metadata registry. Not recommended.

## Verdict: TypeORM vs MikroORM

### Pick MikroORM v7.

**Reasons:**

1. **PGlite story is vastly better.** Official driver in PR; community package is battle-tested. TypeORM's PGlite adapter is fragile community software with no official backing path.

2. **TypeScript inference is a qualitative difference.** `Loaded<T, Hint>` prevents an entire class of runtime bugs across 30+ entities with complex relations. TypeORM's loose typing will produce bugs at Fulcrum's complexity level.

3. **Bun runtime story is better.** MikroORM v7's zero-dependency core, ESM-native architecture, and resolved Bun-specific issues make it a better fit for Bun 1.3+. TypeORM's `emitDecoratorMetadata` bugs in Bun are an ongoing tax.

4. **Unit of Work + Identity Map = safety at scale.** 30+ tables, complex foreign key graph, org_id tenant isolation, cascading deletes — Unit of Work batching prevents N+1 by design. TypeORM requires explicit discipline to avoid the same failure.

5. **Migration snapshot system** prevents concurrent-developer migration ordering issues. Critical for a team developing across 17 pillars simultaneously.

6. **NestJS DX depth.** Auto-register repos by naming convention, `@CreateRequestContext()` for background workers, `Loaded<T>` propagated through service types.

**Where TypeORM is ahead:**
- Native pgvector decorator (no custom type needed).
- Official Casbin adapter (`typeorm-adapter` from node-casbin org is more maintained).
- `@DeleteDateColumn` built-in soft-delete (MikroORM needs `mikro-orm-soft-delete` package).
- Larger community, more tutorials, less steep learning curve.

**These are not blockers.** pgvector custom type is 10 lines. Casbin table can live independently. Soft-delete extension is simple.

### Final recommendation:

```
ORM: MikroORM v7 (@mikro-orm/core, @mikro-orm/postgresql, @mikro-orm/nestjs)
PGlite adapter: mikro-orm-pglite (community) → @mikro-orm/pglite (official, v7.1)
Migrations: class-based TypeScript via mikro-orm migration:generate + snapshot system
pgvector: pgvector/mikro-orm VectorType
Casbin: casbin-mikroorm-adapter (community) or casbin_rule table managed independently
Soft-delete: mikro-orm-soft-delete package or manual filter pattern
FTS: @Property({ type: 'tsvector' }) + @Index({ type: 'GIN' }) + raw() for ts_rank expressions
Escape hatch: em.getKysely() for complex DDL/DML; raw() for SQL fragments inline in TS
```

**Fallback trigger:** If `@mikro-orm/pglite` official driver does not land within 90 days of Kysely 0.29 stable release, evaluate forking community driver or extending PR #7622 directly.
