# Migration up/down + schema-version tracking (MikroORM migrator wrapper)

## Parent
PRD: `.scratch/agent-os-vision/prds/01-foundation-reset.md` (Migration architecture subsection)

## What to build
End-to-end migration framework built on top of MikroORM's `Migrator`. Every schema mutation lands as a single `Migration<timestamp>` class under `src/db/migrations/` (auto-generated by `mikro-orm migration:create` from entity decorator diffs — never hand-written DDL outside the class body, per C6). Each class implements `up()` and `down()`; the `down()` method is auto-emitted lossless where possible. Where lossy (column drop with data), the override throws unless `--force` is passed and writes a warning row to `Event` via `eventRepo.create({ verb: 'migration.down-lossy-forced' })`.

`SchemaMigration` entity (mirror of MikroORM's `mikro_orm_migrations` ledger plus `checksum` + `direction` for our doctor checks) + checksum validation + `fulcrum db migrate --target-version <N>` CLI/Web/TUI/API. Doctor refuses startup if running binary's known max version < DB's current version (would require downgrade).

## Acceptance criteria
- [ ] Schema: `SchemaMigration` entity declared at `src/db/entities/SchemaMigration.ts` (`@Entity({ tableName: 'schema_migrations' })`) with `version int PRIMARY KEY`, `name text`, `appliedAt timestamptz`, `checksum text`, `direction enum('up','down')`. Auto-generated migration class adds the table.
- [ ] Server-action / tRPC procedure: `db.migrate(targetVersion?)`, `db.status()`, `db.history()` — all wrap `MikroORM.getMigrator().up({ to })` / `.down({ to })` / `.getPendingMigrations()` and read `schemaMigrationRepo`.
- [ ] Web surface: `/settings/database/migrations` showing history (from `schemaMigrationRepo.findAll`) + target-version picker.
- [ ] CLI command: `fulcrum db migrate [--target-version <N>] [--force]`, `fulcrum db status`, `fulcrum db history`.
- [ ] TUI screen: Settings → Database → Migrations.
- [ ] Tests: unit test the `up()` → `down()` round-trip on every migration class via `migrator.up({ to: name }); migrator.down({ to: previous });`; integration test downgrade-with-data refuses without `--force` (writes the `migration.down-lossy-forced` event when forced).
- [ ] Doctor: adds `db.migrationVersion` + `db.canRunOnCurrentBinary` checks (reading `schemaMigrationRepo` — no raw SQL).

## Notes
A3 lock requires lossless up/down where possible. Where lossy (column drop with data), `down()` overrides throw without `--force` and emit a warning event via `eventRepo`. Per C6 the only `addSql` allowed in migration class bodies is for sanctioned escape hatches (data backfills, index expressions MikroORM cannot infer); never hand-written DDL when a decorator can express the same thing. Per C9 migration class file path is `src/db/migrations/Migration<timestamp>.ts` — the name is auto-generated and never renamed beyond the slug suffix added at creation time.
