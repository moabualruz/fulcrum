# PRODUCT.md — Fulcrum (Target State)

> Single source of truth for design context. Describes what Fulcrum **is** as a platform, not what code is shipped today. Drives `/impeccable` register, palette, copy voice, anti-references, IA decisions.

## Register

**product** — Fulcrum is a working app (web + CLI + TUI + API). Design serves the product. A brand register exists only for the public marketing landing page and is kept separate from in-product UI.

## What Fulcrum Is

**Fulcrum is a local-first Agent OS for supervising agent-managed product work.**

It is one project workspace, end-to-end. Humans and agents share a single substrate: the same project tree, the same task graph, the same docs, the same runs, the same artifacts, the same memory. Every action a human can take, an agent can also take. Every action an agent takes is auditable, traceable, and reproducible by a human.

The canonical workflow runs left-to-right and never breaks:

```
Capture (freeform docs, notes, intake)
  → Plan (ACP planning + prototyping + plan review)
    → Build (PM tasks + dependency-aware execution + live agent runs)
      → Review (QA + UAT + code review)
        → Ship (artifacts + generated E2E + memory promotion + audit)
          → Operate (doctor + runs history + inbox + settings)
```

A user moves work through these stages without leaving the project context. A trace ID threads every stage and is visible on every surface.

**Every step in every phase exposes four execution modes. Universal — no step is exempt, including doc authoring.**

1. **Manual / freeform** — user does step by hand in freeform editor (rich-text + markdown + canvas-style block surface). Works for every artifact: docs, plans, prototypes, tasks, reviews, QA notes, audit annotations, settings edits, anything. No agent involved.
2. **Play / handoff to AI** — every step has a visible **▶ Play** affordance. One click hands the current step + its context + its trace ID to an agent. Agent runs, streams progress inline on the same surface, returns a draft the user accepts/edits/rejects. Works as "generate this doc", "draft this plan", "build this prototype", "run this review", "summarize this audit row", "configure this setting".
3. **Discuss with AI** — every step has a **💬 Discuss** affordance. Opens an inline thread anchored to the step (not a new screen). User asks questions, requests changes, gets explanations. The thread is the conversation surface; output applies back to the step on accept.
4. **AI Assist panel** — pullable from right side of any screen (web, Cloudflare AI Assist overlay pattern), bottom sheet (mobile), TUI-native inline `:ai` screen (NOT a drawer — terminal stays a terminal), `fulcrum ai` (CLI). Scoped automatically to the active step + project + trace ID. The panel is the persistent, multi-turn equivalent of Discuss. Survives navigation; reopens with state intact. Default agent comes from the routing table (`fulcrum route show ai.freeform`); user can override per-turn or persistently.

Mode is selectable per step, never globally locked. Modes interleave: a doc can be hand-typed for the intro, agent-generated for the technical body, then discussed paragraph-by-paragraph. A planning session can be half-typed and half-played. A task can be opened manual, played to completion, then discussed in review. The product never forces all-human or all-agent.

**Docs are not special.** Docs themselves are a step type. They can be created manually, generated by Play, drafted via Discuss, or built turn-by-turn in the AI Assist panel. Same modes everywhere.

## Product Vision

Fulcrum is what you reach for when:

- You want a **local-first** agent supervisor. No cloud login. Boots cold in under 5 seconds. Works offline. Owns your data, your code, your secrets.
- You want **one workspace** where docs, tasks, runs, artifacts, and memory all reference each other through a shared trace spine — no five-tab tool stack.
- You want agents (codex, claude, gemini, opencode, pi, custom) to be **first-class users**, not chatbots glued to the side. Every API endpoint, every CLI verb, every TUI screen exposes the same capability that a human gets in the web shell.
- You want production-grade discipline at every layer: one ORM, one server framework, one validation library, responsibility-named modules. The patterns the codebase ships are the patterns future agents copy.
- You want a workbench, not an admin panel. Information dense, keyboard-first, no marketing copy, no spinner-as-UX, no AI slop.

## Users

- **Operator (IC engineer).** Drives the loop. Captures intent in freeform docs, dispatches planning agents, reviews diffs, approves UAT. Lives in the web shell + CLI side-by-side. Power user; needs density and speed.
- **Agent.** A program. Reads docs, writes code, opens runs, produces artifacts, requests reviews. Reaches Fulcrum exclusively through the API + CLI. Must never have a less-capable surface than humans.
- **Reviewer / approver.** Drops in for QA, code review, UAT. Lives mostly in the review workbench and inbox. Needs clear context: what changed, why, where the trace started.
- **Maintainer / oncall.** Visits doctor, audit, runs feed, error logs, settings/connectors. Needs fast triage signal and recovery affordances — never a dashboard for its own sake.
- **Team admin.** Manages workspace identity, members, invitations, feature flags, retention. Visits once a week. Settings must be discoverable and predictable.

Fulcrum is explicitly **not** for:
- Casual end-users browsing dashboards.
- Multi-tenant SaaS operations (separate platform layer).
- Marketing-driven onboarding funnels.
- People who want a chatbot.

## Tone & Voice

- **Workbench, not admin panel.** Think Linear, k9s, lazygit, Bloomberg terminal. Not Jira, Salesforce, Notion, Vercel dashboard.
- **Direct, technical, no fluff.** Operators read fast. No marketing copy in-product. No "Welcome aboard!", no emoji confetti, no exclamation points.
- **Names describe responsibility, value, or behavior.** Never phase numbers. Never source-product references ("Plane import", "Notion-style"). Never status-as-name ("New flow"). The word for the thing is the thing.
- **Errors name the recovery action and echo the trace ID.** Pattern: `[what failed]. [why, if non-obvious]. [exact next step]. trace=<id>`. Example: `Settings could not load. The API rejected your scope. Try again, or open the trace in Audit. trace=trace-abc123`.
- **Empty states name the next workflow action.** Not decorative illustrations.
- **Copy reads like a thoughtful engineer wrote it.** Clear declarative sentences. No em dashes (use commas, colons, semicolons, periods, parentheses).

## Strategic Principles

1. **One project workspace.** Sidebar reflects workflow stages. Domain features (docs, runs, board) collapse under the stage they serve. Portfolio surfaces are explicit, not silent fallbacks.
2. **Trace spine visible at every level.** Breadcrumbs, relationship panels, activity timelines, command actions. A user must never have to guess whether a doc, task, run, artifact, or memory entry belongs to a project.
3. **Four modes per step — every step, including docs.** Manual freeform / Play (▶ handoff to AI) / Discuss (💬 inline thread) / AI Assist panel. Mode picked per step; modes interleave inside one step. Docs are not special — they are a step type that obeys the same mode rule.
4. **▶ Play and 💬 Discuss are visible affordances on every step.** Not hidden behind menus. Operator can hand any step to an agent with one click or open an inline thread with one click.
5. **AI Assist is a side drawer (web/mobile), an inline screen (TUI), an inline session (CLI).** Reachable from any surface in one keystroke (web `⌘/`, mobile bottom-tab `AI Assist`, TUI `:ai`, CLI `fulcrum ai`). Auto-scoped to active step + project + trace ID. Survives navigation; reopens with state intact. The web drawer overlays content (Cloudflare AI Assist pattern); the TUI never overlays — it swaps to the `:ai` screen so the terminal stays a terminal.
6. **Prototyping is part of planning.** Plan output is plan + prototype callouts + task breakdown, reviewed as one unit. Each output supports the same four modes.
7. **Agent-native parity.** Every UI action also runs as `fulcrum <verb>` and `POST /api/v1/...`. If a screen exists in the web shell but not in the CLI, the CLI is broken.
8. **Local-first means it actually works offline.** Startup ≤ 5s cold, ≤ 2s warm. PGlite default. PostgreSQL by env switch. No spinners blocking workflow. Service-worker shell + offline mutation queue for safe operations.
9. **Production-grade discipline.** One ORM (TypeORM). One server (NestJS). One validator (Zod). Responsibility-named modules. The codebase wins over prompts; future agents copy what they see.
10. **Workflow stage is the primary axis of navigation.** Not feature buckets, not domain trees.
11. **Density without crowding.** Linear-grade information density. Plane-grade view flexibility. No wasted pixels; also no shouting.
12. **Mobile parity is non-negotiable.** Every primary surface works on a phone in landscape and portrait. Touch targets ≥ 44×44. Bottom-sheet patterns for modals.

## Anti-References

Designs that match any of these are slop and must be reworked:

- **SaaS dashboard cream.** Stripe Atlas / Notion onboarding gradients, soft drop shadows, big hero stat cards, four-card metric grids. Fulcrum is for operators, not for IPO decks.
- **"AI" tropes.** Neon purple/pink gradients, glowing orbs, "✨ AI-powered" badges, animated typing dots as decoration, sparkle icons. Operators recoil.
- **Crypto neon-on-black.** Neon green / cyan on pitch black, hex glyphs, "agent" branding. Looks like rug-pull software.
- **Linear-clone teal sidebar.** Identical pixel-for-pixel reproduction. We borrow Linear's keyboard-first ethos and density, not its palette.
- **Notion-clone slash-everywhere prose theatre.** Round corners, pastel callouts, breadcrumb chains. Fulcrum is denser, more workmanlike.
- **Salesforce / Jira density.** Wall of fields, ribbon nav, breadcrumb chains that obscure the active task. We have density without crowding.
- **Hero-metric card grids.** Four identical cards with big numbers and tiny labels. Cliché.
- **Modal-first design.** Task create, planning start, run dispatch all behind modals. Inline / progressive surfaces always. Modals are a last resort and never the first response to a "create" action.
- **"Side stripe accent" cards.** Coloured left/right borders > 1px on list rows or callouts. Banned.
- **Gradient text.** `background-clip: text` with a gradient. Never meaningful.
- **Glassmorphism by default.** Rare and purposeful, or nothing.

## Surface Map

Workflow-stage primary navigation:

| Stage | Question it answers | Default sub-views | Per-step modes |
|---|---|---|---|
| **Capture** | What did we just learn or notice? | Freeform editor (docs / notes / canvas / intake), tree, attachments | manual / play / discuss / ACP |
| **Plan** | What are we going to build, and why? | Planning sessions list, live ACP session pane, **prototype workbench** (interactive prototypes + boilerplate review), plan review, plan diff, materialize | manual / play / discuss / ACP |
| **Build** | What's getting done right now, and is it on track? | Board / list / table / calendar / Gantt, dependency graph, run feed, live worker pane | manual / play / discuss / ACP |
| **Review** | Is this work ready to ship? | QA workbench, code review, UAT handoff, generated E2E runner, approval gates | manual / play / discuss / ACP |
| **Ship** | Where is the output of our work? | Artifacts list, audit log, reports, memory promotion | manual / play / discuss / ACP |
| **Operate** | Is the system healthy? | Doctor subsystems, runs history, inbox, settings, connectors, routing, doctor probes | manual / play / discuss / ACP |

**Prototyping lives inside Plan, not separately.** Planning produces three artifacts: a written plan, one or more prototype callouts (file paths + sketches + interactive demos), and a task breakdown. The plan review surface must show all three side-by-side; the user reviews and approves them as one unit before materializing tasks.

### Cross-cutting affordance: AI Assist drawer (formerly "ACP chat panel")

A right-side drawer slides over (Cloudflare-style overlay, not push) from any screen via the **AI Assist** segment in the status footer — always the right-most footer segment on every surface — or via `⌘/`. Pulled out, it docks the live agent session scoped to the current step (Capture: doc; Plan: planning session; Build: task or run; Review: review item; Ship: artifact; Operate: subsystem). The user types directly to an agent; the agent reads the active step's context (project + trace + scope), executes, and streams output. Closing the drawer pauses but does not abort the session. Reopening resumes. Trace ID is shared with whatever surface is open.

The drawer width is user-adjustable. On mobile the drawer becomes a bottom sheet, reachable from the bottom-tab-bar AI Assist tab. CLI/TUI equivalents:

- **CLI:** `fulcrum ai --step <step-id>` opens an inline session in the terminal, scoped to the same step.
- **TUI:** `⌘/` on any screen toggles the right-side AI pane; same scope rule.

**Why "AI Assist" and not "ACP"**: ACP is a transport protocol (Agent Client Protocol). It is *one* way Fulcrum talks to a locally-running CLI agent; in the future Fulcrum may also speak directly to hosted APIs (a user-configured Anthropic / OpenAI key), reach out over SSH to a remote machine running an agent, or attach to a sandboxed cloud runner. All of those flow through the same UI affordance. Users should never read protocol names in the chrome — they should just see "AI Assist" everywhere and pick which configured agent runs their request.

#### Multi-CLI agent model (unlimited clients)

The user can configure any number of CLI agent clients — Claude Code, Codex, Gemini CLI, OpenCode, pi-cli, or any future client that speaks an agent protocol. There is **no cap**. Each configured agent has:

- a stable id (e.g. `claude-opus-4.7`, `gpt-5.4`, `gemini-3-pro`, `opencode-llama-3`, `pi-cli-mistral`)
- a client kind (`claude-code` · `codex` · `gemini-cli` · `opencode` · `pi-cli` · `custom`)
- a runtime status (`ready` · `degraded` · `paused`)
- a ring (`preferred` · `stable` · `experimental`)
- its **own MCP server set** (configured per agent — see below)
- its **own plugin set** (configured per agent)
- its own tool-permission policy and rate-limit budget

In every place a user runs an action — `▶ Play` on a step, **AI Assist** drawer, ⌘K palette `Play current step`, CLI `fulcrum run --step …` — they get an agent picker. The picker:

1. Shows the **default-routed** agent for that action kind first.
2. Lets the user override to any other configured agent in one click.
3. Offers `Set as default route for this action kind` so the override sticks.
4. Offers `+ Add CLI agent` to configure another client without leaving the picker.

#### Default routes (per-action agent assignment)

A `routes` table in Settings maps an action kind to a preferred agent. Out-of-the-box defaults:

| Action kind         | Default agent              | Note                 |
| ------------------- | -------------------------- | -------------------- |
| `plan.draft`        | Claude Opus 4.7            | high-context planning |
| `plan.refactor`     | Claude Opus 4.7            |                      |
| `build.run.step`    | Claude Sonnet 4.6          | fast iteration       |
| `build.test.write`  | GPT-5.4                    |                      |
| `review.suggest`    | Gemini 3 Pro               | second opinion       |
| `ship.changelog`    | Claude Sonnet 4.6          |                      |
| `operate.probe`     | OpenCode (local-only)      | no cloud calls       |

Every route is overridable per action. Each rule has an `Allow inline override` toggle (on by default); turning it off forces the route and removes the picker from that action's mode popover.

#### Per-agent MCP servers and plugins

MCP servers and plugins are configured **per CLI agent** — not globally. The Operate → MCP servers and Operate → Plugins surfaces show a scope chip at the top: `Claude Opus 4.7 · Sonnet 4.6 · GPT-5.4 · Gemini 3 · OpenCode · pi-cli · Codex`. Switching the scope filters the table to that agent's installed set. The user can:

- install a server / plugin into a single agent
- uninstall it
- pin it to a specific ring
- override its tool permissions for that agent

A `Install across all agents` action is reserved for a future release; until then the design must make per-agent scoping explicit (chip selector, copy on the page, badge on rows) so users never confuse one agent's plugin set for another's.

**SaaS-future-proofing**: when Fulcrum eventually offers a cloud tier, the same UI vocabulary applies — instead of (or in addition to) local CLI clients, the user can register cloud API keys (Anthropic, OpenAI, …) and SSH-attached remote runners. Each becomes another agent entry in the registry. The chrome never says "ACP" or "API key" or "SSH agent" — it says **AI Assist** and **agent**, and the agent's metadata reveals its underlying client kind.

Portfolio surfaces (workspace-wide, cross-project, accessible from a separate scope switcher):

- Dashboard — workspace home, scoped to *every* project the user has access to
- Projects — full project list + create
- Global docs — workspace-level knowledge (not project-scoped)
- Search — federated across projects, docs, runs, artifacts, memory
- Memory — global memory review
- Inbox — notifications across every project

System surfaces (rarely visited, must be one keystroke away):

- Doctor (subsystems, probes)
- Settings: theme, API, flags, secrets, experiments, importers, retention, telemetry
- Skills, MCP servers, credentials
- Audit retention policy
- Error logs
- Identity & members

## Platforms

Equal-weight surface targets. None is a downgrade of another.

- **Web shell** — primary visual surface. SvelteKit. PWA-capable. Service worker pre-caches the shell + offline-queues safe mutations. Desktop 1440 design width; tablet + mobile mandatory.
- **CLI (`fulcrum`)** — JSON-first machine output (`--json` everywhere); human output is a render of the same data. Subcommands grouped by workflow stage. Bash / Zsh / Fish / PowerShell completion bundled.
- **TUI (`fulcrum tui`)** — full keyboard-first workbench, not a fallback. Vim-keys (j/k/gg/G/?/space/V), modal `:` command palette + modeless `cmd-k` palette, status footer that always shows API health, runtime, active project, and current trace ID.
- **API** — NestJS, OpenAPI at `/openapi-json`. Dual-exposed via tRPC for in-process callers (web/CLI/TUI). REST for external integrations.
- **Desktop shell** — Tauri wrap of the web shell with native notifications, system tray, and an always-on-top live agent session pane. Optional install; everything also works in a browser.

## Hard Invariants (drive every design choice)

1. No generic `500` / `502` / "Something went wrong". Every error names the recovery action and echoes the trace ID.
2. No blank shells. Every empty state has a primary action that moves the workflow forward.
3. No dead routes advertised anywhere (OpenAPI, nav, settings).
4. Trace ID is visible and copyable on every screen.
5. Mobile: no horizontal scroll on any primary surface. Touch targets ≥ 44×44.
6. WCAG 2.2 AA contrast. Focus visible only when keyboard-engaged. `prefers-reduced-motion` respected.
7. Workflow-stage navigation is non-negotiable. Feature-bucket sidebars are a regression.
8. Agent-native parity. Every UI capability also reachable via API + CLI + TUI. No exceptions.
9. Local-first defaults. Nothing in the product requires a cloud account to function.
10. Workflow stage and project scope are visible at the chrome level on every surface — not buried in breadcrumbs.
11. Every step in every stage exposes four modes: manual freeform / Play (▶) / Discuss (💬) / AI Assist. No step is hardcoded to one mode. Docs included.
12. ▶ Play and 💬 Discuss are visible affordances on every step header, not hidden in overflow menus.
13. AI Assist reachable from every surface in one keystroke (web `⌘/`, mobile bottom-tab AI Assist, TUI `:ai` / `[ :ai ]` footer seg, CLI `fulcrum ai`). Auto-scoped to active step + project + trace. Web/mobile use a slide-over overlay (Cloudflare AI Assist pattern); TUI swaps to the inline `:ai` screen — no terminal overlay.
14. Prototyping is a first-class plan output. Plan review shows plan + prototype + tasks together.
15. Mode switches preserve trace ID and step state. No mode is destructive of prior work.

## What Done Looks Like

A new operator clones Fulcrum, runs one command, and within 60 seconds:

1. Sees a workspace home that explains what to do next.
2. Creates a project.
3. Opens Capture. Starts a freeform canvas; types two paragraphs by hand, then hits **▶ Play** on a third paragraph stub. Agent expands the stub inline. Operator edits one sentence manually.
4. Moves to Plan. Hits **▶ Play** on the empty planning surface. Agent reads the captured doc, drafts: (a) the plan, (b) a prototype callout with an interactive demo, (c) a task breakdown. Operator clicks **💬 Discuss** on the prototype, asks for a different interaction model, agent updates inline. Accepts.
5. Materializes plan into tasks. Hits **▶ Play** on the first task. Run starts in automate mode.
6. Watches the run live with trace ID echoed in the footer. Copies trace ID to CLI; gets the same view via `fulcrum runs show <trace>`. Pulls the AI Assist drawer from the right side (web), asks the agent a follow-up scoped to the live run.
7. Review surface auto-opens. Operator reads the diff manually, hits **💬 Discuss** on one file to challenge a change, accepts after agent justifies it. Ships the artifact. Audit log shows every mode switch with the same trace ID.

At any step the operator switches modes. Half the planning can be Played and half hand-typed. A code review can start manual and be Discussed mid-flow. A doc can be agent-generated then hand-edited line by line. Docs are not special; they obey the same modes.

Every step is fast, traceable, reversible. Nothing hidden behind a modal. Nothing requires a refresh. Nothing returns a generic 500. Mode choice is one click. Trace IDs survive every switch.

That is the platform.

## Workflow Stages — Detailed Spec

Six stages. Each has a primary question, default landing surface, key sub-views, canonical artifacts, completion criteria, and exit handoff to the next stage. **No stage is skippable**, but every stage exposes manual / Play / Discuss / ACP modes for every step. A stage is "complete" when its exit-handoff criteria hold and the human (or an agent acting under approval) advances.

### 1. Capture — "What did we just learn or notice?"

- **Landing.** Freeform editor scoped to the current project. Blank canvas with cursor on first line; quick-templates row at the bottom (Doc / Note / Intake / Bug / Decision / Question).
- **Default sub-views.** Docs tree (left rail, 200px), editor (centre), attachments + backlinks (right rail, collapsible).
- **Artifact types.** Doc, freeform note, decision record, intake item, bug report, raw paste.
- **Per-step modes.** Manual freeform = blank cursor + slash menu. Play = ▶ on any block stub. Discuss = 💬 on selection. ACP = pullable drawer scoped to current doc.
- **Mode interleave example.** User hand-writes paragraph 1, hits ▶ Play on paragraph 2 stub, agent fills it in, user 💬 Discusses paragraph 3 for a different framing.
- **Completion criteria.** Doc has a title and at least one substantive paragraph; or intake item has actor + behavior + expected outcome.
- **Exit handoff.** "Hand off to Plan" button on doc header opens a planning session pre-seeded with the doc as context. Same action via CLI: `fulcrum plan start --from-doc <id>`. Trace ID is allocated at this moment and propagated forward.

### 2. Plan — "What are we going to build, and why?"

- **Landing.** Planning sessions list scoped to project. Most-recent session pinned at top; "Start new session" inline at the bottom.
- **Default sub-views.** Sessions list (left rail), live session pane (centre), plan + prototype + tasks tripane (right rail when reviewing).
- **Artifact types.** Planning session (live transcript), plan markdown, prototype callout (file path + sketch + interactive demo), task breakdown, success criteria checklist, dependency graph.
- **Per-step modes.** Every section of the plan, every prototype callout, every task entry can be authored manually, generated via Play, refined via Discuss, or driven turn-by-turn in the ACP drawer.
- **Prototyping is first-class.** A planning session produces three artifacts displayed side-by-side at review: (a) the written plan, (b) one or more prototype callouts, (c) the task breakdown. The user reviews and approves all three as one unit. Prototype callouts can be interactive HTML demos, file-path references, or sketch images — same status chip system (proposed → approved → materialized) as plan + tasks.
- **Completion criteria.** Plan has explicit success criteria; every task has at least one acceptance line; every prototype callout has a target file path; the user has clicked "Approve plan."
- **Exit handoff.** Materialize button creates tasks + dependency edges + prototype tracking issues. CLI: `fulcrum plan materialize --plan <id>`. Trace ID flows into every materialized task.

### 3. Build — "What's getting done right now, and is it on track?"

- **Landing.** Task board scoped to current cycle. Column groups: Backlog / In Progress / Review / Done.
- **Default sub-views.** Board (default), list, table, calendar, Gantt, dependency graph; runs feed; live worker pane. View switcher in the scope chrome.
- **Artifact types.** Task, sub-task, dependency edge, run, agent worker session, in-progress diff, intermediate artifact.
- **Per-step modes.** Per-task: manual edit, Play (dispatch agent), Discuss (inline thread), ACP (full session in drawer). Per-run: manual takeover, Play continue, Discuss mid-run, ACP forks new session.
- **Multi-agent orchestration.** Dependency graph view shows nodes as tasks, edges as dependencies. Each task node carries a status chip (planned / running / blocked / complete / failed) + an agent badge (codex / claude / gemini / opencode / human). Click a node → live worker pane in centre + task detail in right rail.
- **Completion criteria.** Every task either has `status: done` or is explicitly deferred with reason. The dependency graph has no open `failed` nodes without recovery.
- **Exit handoff.** "Open Review" button on the cycle header advances to Review stage with all completed tasks queued.

### 4. Review — "Is this work ready to ship?"

- **Landing.** Review workbench. Left rail: queue of items awaiting review (diffs, plans, docs, prototypes, generated tests). Centre: active item with rich diff view. Right rail: review thread + approval gate.
- **Default sub-views.** Diff viewer (centre), inline comments + annotations (overlay), approval gate (right rail bottom).
- **Artifact types.** Review request, inline annotation, decision (approve / request-changes / reject), generated E2E spec, UAT result, code-review summary.
- **Per-step modes.** Per-review-item: manual read + comment, Play (ask agent to review), Discuss (thread on selection), ACP (full review session in drawer).
- **Approval gates.** Multi-reviewer flow with role-based requirements. Approvers can be agents, humans, or both — same approval-gate shape. Pending agent reviews show "Awaiting Claude's review (~2 min)" with cancel.
- **Completion criteria.** Every review item has a decision; approval gate has met its role requirements; generated E2E has run and passed.
- **Exit handoff.** "Ship" button on the cycle header advances to Ship stage with all approved artifacts queued.

### 5. Ship — "Where is the output of our work?"

- **Landing.** Artifacts list scoped to current cycle, filterable by kind (binary / spec / report / memory candidate).
- **Default sub-views.** Artifacts list (centre), audit log strip (right rail), reports + memory promotion buttons (header).
- **Artifact types.** Final artifact (binary, file, link), shipped report, promoted memory entry, release note.
- **Per-step modes.** Per-artifact: manual download/link, Play (auto-promote to memory, auto-generate report), Discuss (annotate artifact), ACP (run packaging session).
- **Completion criteria.** Every approved artifact is downloadable or linkable; memory promotion decisions are recorded; release notes are drafted.
- **Exit handoff.** Project status updates to "shipped" for that cycle. Audit log carries the full trace.

### 6. Operate — "Is the system healthy?"

- **Landing.** Doctor subsystems table. Default view: all subsystems with current status + last-checked time.
- **Default sub-views.** Subsystems table (centre), runs history (linked from cycle), inbox, settings, connectors, routing rules, doctor probes.
- **Artifact types.** Subsystem state record, probe result, audit retention policy, telemetry opt-in record, error log entry.
- **Per-step modes.** Per-subsystem: manual probe + fix, Play (auto-remediate), Discuss (ask agent to diagnose), ACP (full ops session).
- **Completion criteria.** No subsystem in `failed` state without recovery; no notification older than retention window.
- **No exit handoff.** Operate is the always-on stage. It is the only stage you can be in without an active cycle.

## Scope Chrome — Persistent Top Bar

Every primary surface, every breakpoint, shows the scope chrome at the top. **48px desktop / 56px mobile** (lifted from the original 32/40 spec — small chrome read as outdated on modern displays, Linear / Vercel / GitHub now sit at ~48px).

Layout left-to-right:

1. **Brand mark + name.** `Fulcrum` wordmark, click → workspace home.
2. **Workspace switcher.** Folder icon + `mkh / fulcrum` + chevron. Click → workspace popover (current + other workspaces + `+ New workspace`). Pro-mode shows the current branch as a `path` chip after the switcher.
3. **Stage tab strip.** `Capture · Plan · Build · Review · Ship · Operate` segmented control — active stage has accent indicator + inset shadow. Keyboard: `g c / g p / g b / g r / g s / g o`. Per-tab `key` hint pill (`g c` etc) is pro-only.
4. **Spacer.** Pushes the right cluster to the right edge.
5. **Trace ID badge.** Copyable pill, mono font, `git-commit` icon + 10-char prefix + ellipsis + copy icon. Click-to-copy with flash feedback. Pro-only.
6. **Right-cluster icons** — every one is a real button with a labelled popover or destination (no decorative chrome):
   - **Command palette** (`search` icon) → opens ⌘K palette. Pro-only.
   - **Notifications** (`bell` icon, with red dot when unread) → opens **Notifications popover**: tabbed (All · Mentions · Runs · Ship), each row shows status icon (PR / warn / rocket / etc.), one-line summary, meta line (trace + age + scope), snooze button. Mark-all-read + settings shortcut + "View all" link.
   - **Display settings** (`settings` icon) → opens **Display popover**: segmented controls for Theme (Auto · Light · Dark), Density (Compact · Cozy · Comfortable), Mode (Simple · Pro), Motion (Full · Reduced), Sidebar (Expanded · Icons only). "Open all settings →" link to the full Settings page.
   - **Keyboard help** (`?` icon) → opens the keyboard cheatsheet overlay. Pro-only.
   - **Account avatar** → opens **Account popover**: current workspace + other workspaces + `+ New workspace`, then `Account & profile`, `API keys & tokens`, `CLI agents` (with count), `MCP servers`, `Plugins`, `Docs`, `Send feedback`, `Sign out` (danger color).
7. **AI Assist is NOT in the scope chrome.** It lives in the status footer as the right-most segment (so it stays one click away from anywhere, in line with the other status indicators rather than competing with system icons for visual weight). Keyboard `⌘/` opens the drawer from anywhere.

Each right-cluster button has a tooltip on hover; tooltips state what the button does in human language (not just the icon name). Popovers position below their trigger, slide-in animation, click-outside or `Esc` to close. Triggers expose `aria-expanded="true"` while their popover is open.

Mobile: collapses to brand + workspace + active-stage chip + notifications + account on the right edge. AI Assist becomes the right-most **tab** in the bottom tab bar. Trace ID accessible via swipe-down quick panel.

## Per-Step Mode Affordance — Universal Spec

Every step header (every doc, every task, every review item, every artifact, every subsystem row) carries three inline affordances and one drawer trigger:

```
[step title] ............... ▶ Play   💬 Discuss   ⋮ More   ⊞ Drawer
                              ────────────────────
                              Manual freeform = no button needed; user just types.
```

- **▶ Play** — primary action button, 24px. Click → mode picker popover (agent + model + policy + optional inline prompt). Run starts inline streaming below the step. Cancel button replaces ▶ during run.
- **💬 Discuss** — secondary button. Click → opens inline thread anchored to the step's selection or whole step. Thread persists until resolved or accepted.
- **⊞ AI Assist** — pulls AI Assist drawer (web/mobile) or swaps to `:ai` inline screen (TUI) scoped to this step. Remembers per-step history; switching steps changes scope but keeps thread tabs accessible.
- **⋮ More** — overflow for power actions: clone, archive, change owner, lock for review.

Mode-switch invariants:
- Switching modes does not lose user input.
- Switching modes preserves the trace ID and step state.
- All four modes can be live concurrently on one step (rare; e.g. Play running + Discuss thread open).

Keyboard parity:
- `p` on a focused step → Play.
- `d` on a focused step → Discuss.
- `⌘/` from anywhere → drawer.

## Agent Identity Model

Agents are first-class workspace members. Fulcrum ships with seven default agent identities — `claude-opus-4.7`, `claude-sonnet-4.6`, `gpt-5.4`, `gemini-3-pro`, `opencode-llama-3`, `pi-cli-mistral`, `codex-gpt-4o` — covering five default CLI client kinds (`claude-code`, `codex`, `gemini-cli`, `opencode`, `pi-cli`). Operators can register any number of additional agents — there is **no cap** — with their own id, name, client kind, model, policy, MCP set, and plugin set.

- An agent appears in every assignee picker, every mention picker, every approval-gate selector — identical UI affordance as a human user.
- Mentions: `@claude-opus-4.7` resolves to that specific agent identity in the workspace. Mentioning triggers an agent reply via its configured client (ACP, hosted API, SSH-attached runner, …).
- Agent runs are persisted with `(agent_id, client_kind, model, policy, trace_id, run_id, started_at, finished_at, cost_tokens, status)`.
- Assignment: when a step is assigned to an agent, the human stays primary owner; the agent is added as contributor. ([Linear Agents model, adopted.](https://linear.app/agents))
- Audit log records every agent action with the same trace ID as a human action; no separate audit feed.
- Policy: each agent has a policy (`auto_approve_safe`, `review_each_tool`, `danger_zone`). Policy is set at workspace, overridable at project, overridable per run.
- **MCP servers and plugins are configured per agent**, not globally. Switching the scope on Operate → MCP / Plugins shows that agent's installed set. (See `### Cross-cutting affordance: AI Assist drawer` for the full multi-CLI model.)

The right-side **AI Assist** drawer auto-resolves which agent to talk to based on the active step's assigned agent or the default-route rule for the current action kind. The drawer's header picker lists every configured agent (with status dot, client kind, latency, MCP count, plugin count, ring badge) and offers `+ Add CLI agent` inline. Switching agents mid-thread does not lose history — each agent gets its own tab in the drawer.

## Mode-First UI Contract

Every screen that mentions a step MUST include the four-mode affordance row. No exceptions. Even Doctor subsystems carry ▶ Play (auto-remediate), 💬 Discuss (ask agent why), ⊞ Drawer (full ops session). Even settings rows carry ▶ Play (suggest setting), 💬 Discuss (explain implications).

Surfaces that violate this contract are bugs.

## Onboarding Flow

A fresh operator must reach "productive" in under 5 minutes.

1. **First-run boot** — Fulcrum boots locally on `localhost`. Seeded `admin@local` identity. Welcome screen with one input field: workspace name. No marketing.
2. **Create first project** — Single prompt: "What are you building?" Project is created with that as the description and the default workflow stages enabled.
3. **Capture screen opens directly with cursor on blank doc.** "Type or paste anything. ⌘/ to ask an agent." No popups, no tutorial overlay.
4. **First Play** — When the user first hits ▶ Play, a small inline coachmark appears next to the picker explaining: "▶ Play hands this step to an agent. Pick which agent and which policy. You can switch back to manual at any time." Coachmark dismisses after first run completes.
5. **First trace ID surface** — When the first run completes, the trace ID badge in the scope chrome pulses once with a tooltip: "Trace this run across web, CLI, TUI, audit. Click to copy."

Done. No further onboarding overlays. The interface is the tutorial.

## Failure Patterns — What Operators Hate (Hard Bans)

These have been observed in PRDs as the most common operator complaints. Re-stated as hard bans for emphasis:

- **Spinner without progress.** Always show what's happening (current operation, % complete if possible, time elapsed).
- **Refresh required.** Anything that requires a manual refresh after a mutation is broken.
- **Toast for errors.** Errors live in the surface where they happen, inline. Toasts are for "we couldn't autosave, retrying" — not for "your action failed."
- **Modal stack.** Two modals open at once = bug. Sheets and drawers stack into a single right rail.
- **Tab-only access.** Anything reachable only by clicking a tab is hidden. Tabs are for parallel views, not progression.
- **Generic empty state.** Every empty state names the next workflow action.
- **Settings buried under "More" menu.** Settings is one keystroke from any surface (⌘,).
- **Save without confirmation.** Saved state visible in the surface; not a toast.

## Transformation Discipline

Fulcrum's redesign is **additive + transformative, never subtractive**. The new IA (workflow stages) replaces the current feature-bucket sidebar; it does not delete any shipped feature. Every route, command, screen, and capability already in the codebase must land somewhere in the new IA.

Carry-over invariants:

1. **Every existing web route** in `apps/web/src/routes/**` maps to a workflow stage in [IA-MAP.md §2](IA-MAP.md). Routes that don't have an obvious home land in **Operate** (default fallback for system / settings / power-tools) or get an explicit deferral note.
2. **Every existing CLI command** in `apps/cli/src/commands/**` maps to a stage-organized verb in [CLI-TUI-UX.md §1](CLI-TUI-UX.md). Anything missing gets added as a stub with the same flags as today.
3. **Every existing TUI screen** in `apps/tui/src/screens/**` maps to a `:` palette command in [CLI-TUI-UX.md §6](CLI-TUI-UX.md).
4. **Every existing service capability** in `services/**` keeps its API endpoint shape; the UI may relocate the affordance, the API contract does not break.
5. **Every existing setting** in `apps/web/src/routes/settings/**` lives in either `/<ws>/operate/settings/*` (project-scoped) or `/<ws>/settings/*` (workspace-scoped). No setting disappears silently.
6. **Renames are namespaced + aliased.** If a route or command is renamed (e.g. `boards/` → `build/board`, `inference/` → `operate/inference`), the old path stays as a 301 redirect for one minor version with a deprecation banner pointing at the new path.
