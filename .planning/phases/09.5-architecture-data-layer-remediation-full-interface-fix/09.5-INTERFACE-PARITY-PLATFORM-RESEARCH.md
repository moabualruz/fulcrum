## Summary

Fulcrum should treat Web, CLI, TUI, REST, and tRPC as invocation and visualization layers over one application command/query model. [VERIFIED: `.planning/phases/09.5-architecture-data-layer-remediation-full-interface-fix/09.5-CONTEXT.md` D-10, D-25..D-30] The strongest platform pattern across Linear, GitHub CLI/GitHub REST, Jira, Rails/Hotwire, and tRPC is not "duplicate feature logic per interface"; it is "same domain operation, many equivalent entry points, transport-specific rendering." [CITED: https://linear.app/docs/conceptual-model] [CITED: https://cli.github.com/manual/gh_issue] [CITED: https://docs.github.com/en/rest/issues] [CITED: https://developer.atlassian.com/cloud/jira/platform/rest/v3/intro/] [CITED: https://guides.rubyonrails.org/action_controller_overview.html] [VERIFIED: Context7 `/websites/trpc_io` docs query]

Primary recommendation: keep Fulcrum's Phase 09.5 boundary strict: every interface parses input, builds auth/session/app context, calls `src/application/{domain}/commands.ts` or `queries.ts` directly or through in-process tRPC caller, maps result/error to its native UX, and owns no domain mutation, authorization, tenancy, persistence, raw SQL, ProductDb, or product-kernel logic. [VERIFIED: `.planning/phases/09.5-architecture-data-layer-remediation-full-interface-fix/09.5-CONTEXT.md` D-10, D-12, D-25..D-33, D-53] [VERIFIED: `src/architecture/boundary.test.ts`]

## Exact UX / Interaction Patterns To Match

### Linear Patterns

- Same action from multiple surfaces: Linear documents issue/project actions reachable through buttons, keyboard shortcuts, contextual menus, and command menu. Fulcrum should copy this by keeping command palette, sidebar actions, TUI keybindings, CLI subcommands, and REST/tRPC operations as different invokers of the same application command/query. [CITED: https://linear.app/docs/conceptual-model]
- Command menu is contextual: Linear command menu prioritizes commands relevant to current view/selection. Fulcrum should copy this in web command palette and TUI palette by deriving commands from current route/screen and application capability metadata, not hand-coded route-only lists. [CITED: https://linear.app/docs/conceptual-model] [VERIFIED: `apps/web/src/lib/components/command-palette/navigation-commands.ts` from phase summary]
- `F` opens filters and filters apply across most views; advanced filters support AND/OR condition groups. Fulcrum should copy reusable filter DTOs for tasks/runs/audit/search views so web, CLI `--json`, and TUI list filters invoke same query shape. [CITED: https://linear.app/docs/filters]
- Display options separate view presentation from data filtering: group/order/layout/display properties are not separate data logic. Fulcrum should copy this by keeping TUI/web grouping and columns as visualization state over application query results. [CITED: https://linear.app/docs/display-options]
- Do not copy Linear AI filters for Phase 09.5: Fulcrum AGENTS requires deterministic retrieval for project-management/context surfaces unless user approves model deps. [VERIFIED: `AGENTS.md`] [CITED: https://linear.app/docs/filters]

### GitHub CLI / GitHub Web / GitHub REST Patterns

- `gh issue` groups list/create/status plus targeted operations view/edit/close/comment/delete/etc. around same issue resource. Fulcrum should copy this resource-first CLI taxonomy: `fulcrum task list/create/view/edit`, `fulcrum sprint list/create/start/close`, `fulcrum artifact list/view/archive`, and keep CLI command signatures stable while internals call tRPC/application. [CITED: https://cli.github.com/manual/gh_issue] [VERIFIED: `09.5-UI-SPEC.md` CLI UX Contract]
- `gh issue view 123 --web` explicitly bridges CLI to web for rich inspection. Fulcrum should copy a `--web`/`open` pattern for resource commands where web is richer, but only as navigation, not separate business logic. [CITED: https://cli.github.com/manual/gh_issue]
- `gh` defaults to line-based human output and uses `--json`, `--jq`, `--template` for machine output. Fulcrum should preserve current human stdout + `--json` stability and avoid web-shaped payloads leaking into CLI output. [CITED: https://cli.github.com/manual/gh_help_formatting] [VERIFIED: `09.5-UI-SPEC.md` CLI Output Format Contract]
- GitHub REST Issues docs expose issue assignees, comments, labels, milestones, issue CRUD, labels, dependencies, and timelines as resource operations. Fulcrum should make REST routes resource adapters over application modules and keep OpenAPI response shapes as adapter-level serialization only. [CITED: https://docs.github.com/en/rest/issues]
- Do not copy GitHub's separate GraphQL/REST dual public API expansion in Phase 09.5; Fulcrum locked Hono REST + tRPC and explicitly rejected GraphQL. [VERIFIED: `09.5-CONTEXT.md` D-01, D-02, D-06]

### Jira / Atlassian Patterns

- Jira Cloud REST v3 documents programmatic interaction, response codes, example requests/responses, resource names, and auth scopes separately from web UI. Fulcrum should copy this separation: `apps/server/src/api/routes/**` owns HTTP shape/OpenAPI docs/auth mapping, while application modules own behavior. [CITED: https://developer.atlassian.com/cloud/jira/platform/rest/v3/intro/] [VERIFIED: `09.5-CONTEXT.md` D-44, D-66]
- Jira Server architecture says web requests are handled by WebWork actions that use utility/Manager objects and JSP for view output. Fulcrum should copy the separation, not the technology: SvelteKit `+page.server.ts` actions/loaders should use application commands/queries and return page data/errors. [CITED: https://developer.atlassian.com/server/jira/platform/architecture-overview/] [VERIFIED: `09.5-CONTEXT.md` D-25]
- Jira REST v3 ADF-specific body/comment/description handling shows content formats belong in API contracts. Fulcrum should keep domain DTOs stable, with adapter-specific format mapping at REST/web boundaries only. [CITED: https://developer.atlassian.com/cloud/jira/platform/rest/v3/intro/]
- Do not copy Jira's heavyweight plugin/server architecture or Java manager stack; Fulcrum is local-first Bun/SvelteKit/Hono/tRPC. [VERIFIED: `AGENTS.md`] [VERIFIED: `package.json`] [CITED: https://developer.atlassian.com/server/jira/platform/architecture-overview/]

### Rails / Hotwire Patterns

- Rails controllers sit between router, model, and view: they receive requests, access parameters, fetch/save model data, and render/redirect output. Fulcrum should copy the "thin controller" posture for SvelteKit loaders/actions and Hono handlers. [CITED: https://guides.rubyonrails.org/action_controller_overview.html]
- Rails request object separates query/body/path parameters. Fulcrum adapters should parse path/search/form/json into typed application input before calling commands/queries and should not pass raw `Request` objects into application modules. [CITED: https://guides.rubyonrails.org/action_controller_overview.html]
- Turbo centralizes permission/domain logic server-side and sends HTML over the wire. Fulcrum should copy the centralized server logic principle for SSR/web, not necessarily Hotwire transport. [CITED: https://turbo.hotwired.dev/handbook/introduction]
- Turbo expects 303 after successful stateful form submission and 422 for validation errors. Fulcrum web form actions should map `AppValidationError` to field errors/status and successful mutations to redirects or stable page data, preserving existing SvelteKit UX. [CITED: https://turbo.hotwired.dev/handbook/drive] [VERIFIED: `09.5-UI-SPEC.md` Web UX Contract]
- Do not copy Rails Active Record "fat model owns persistence + domain" directly because Fulcrum has locked MikroORM plus explicit application command/query boundary. [VERIFIED: `09.5-CONTEXT.md` D-07..D-15]

### tRPC / BFF Patterns

- tRPC procedures support input validators and infer typed input from Zod/Valibot-style schemas. Fulcrum should keep tRPC procedures as schema/context/error adapters over application commands/queries; schemas should come from application modules where Phase 09.5 requires it. [VERIFIED: Context7 `/websites/trpc_io`] [VERIFIED: `09.5-CONTEXT.md` D-26, D-33]
- tRPC server-side callers allow in-process invocation of routers without HTTP. Fulcrum already uses this in CLI and TUI via `createLocalCaller()` and `buildCaller()`, and should keep that path as primary interface parity mechanism. [VERIFIED: Context7 `/websites/trpc_io`] [VERIFIED: `apps/cli/src/local-caller.ts`] [VERIFIED: `apps/tui/src/index.ts`]
- tRPC context middleware can require auth context and produce typed authorized context. Fulcrum should use this for transport authentication/permission scaffolding, but application entrypoints still enforce org/user/project rules. [VERIFIED: Context7 `/websites/trpc_io`] [VERIFIED: `09.5-CONTEXT.md` D-31, D-32]
- Do not let tRPC become a second application layer. Routers that call repositories, raw EntityManager, product-kernel stores, or contain business branching are architecture violations. [VERIFIED: `src/architecture/boundary.test.ts`] [VERIFIED: local grep found residual raw/direct patterns in interface/runtime paths]

## Thin Interface Layer Contract

Use this exact contract for all residual closure tasks:

```text
adapter receives request/event/argv/keybinding
  -> parse path/query/body/form/argv into application input schema
  -> build AppContext { orgId, userId, projectId? } from transport auth/session
  -> call application command/query
  -> map AppError to transport-native response
  -> render/serialize result in interface-native shape
```

Allowed adapter code:

- Parse request, route params, form data, JSON body, CLI flags, TUI selection. [CITED: https://guides.rubyonrails.org/action_controller_overview.html] [VERIFIED: `09.5-CONTEXT.md` D-25..D-30]
- Choose status code, redirect, headers, stdout/stderr, exit code, TUI widget state. [VERIFIED: `09.5-UI-SPEC.md`]
- Call `createLocalCaller()`, `buildCaller()`, or application command/query. [VERIFIED: `apps/cli/src/local-caller.ts`] [VERIFIED: `apps/tui/src/index.ts`]
- Map `AppValidationError`, `AppUnauthorizedError`, `AppForbiddenError`, `AppNotFoundError`, `AppConflictError`, `AppInvariantError`, `AppExternalDependencyError` to transport-native errors. [VERIFIED: `09.5-CONTEXT.md` D-12]

Forbidden adapter code:

- Raw SQL, `em.getConnection().execute`, direct `.query()` against DB connection. [VERIFIED: `09.5-CONTEXT.md` D-15] [VERIFIED: local grep]
- ProductDb/PGlite/product-kernel imports outside kernel/explicit legacy bootstrap. [VERIFIED: `src/architecture/boundary.test.ts`]
- Authorization/tenant decisions beyond transport identity/context construction. [VERIFIED: `09.5-CONTEXT.md` D-31, D-32]
- Domain event emission from interface code. [VERIFIED: `09.5-CONTEXT.md` D-34..D-36]
- Per-interface duplicated schema variants when application schema exists. [VERIFIED: `09.5-CONTEXT.md` D-33]

## Common Pitfalls

### Pitfall 1: "Thin" Adapter Still Owns Query Semantics

What goes wrong: route/procedure no longer imports ProductDb, but still assembles raw SQL or branches business rules locally. [VERIFIED: local grep found raw `.query()` and `em.getConnection().execute()` in interface/runtime paths]  
Avoid: move query semantics into application queries; adapter only passes typed filter/sort/page input. [VERIFIED: `09.5-CONTEXT.md` D-10, D-15]

### Pitfall 2: tRPC Becomes Hidden Service Layer

What goes wrong: CLI/TUI parity improves through tRPC, but procedure bodies own behavior and application layer is bypassed. [ASSUMED]  
Avoid: require every procedure to call `src/application/**` or a named legacy application compatibility module; architecture test should scan router bodies for direct raw/legacy imports. [VERIFIED: `src/architecture/boundary.test.ts`]

### Pitfall 3: Output Parity Mistaken For Data Parity

What goes wrong: web/CLI/TUI all display "same looking" data but derive it through separate queries with different auth/filter/event behavior. [ASSUMED]  
Avoid: replicate `src/application/tasks/interface-parity.test.ts` across domains and assert same IDs/fields/statuses from same application write. [VERIFIED: `src/application/tasks/interface-parity.test.ts`]

### Pitfall 4: Allowlists Hide Architecture Debt

What goes wrong: boundary tests pass by broad excludes instead of exact bootstrap/test exceptions. [VERIFIED: `09.5-12-SUMMARY.md`, `09.5-16-SUMMARY.md`]  
Avoid: exact path allowlist only, one-line rationale, no interface/runtime directories unless user explicitly accepts residual debt. [VERIFIED: `src/architecture/boundary.test.ts`]

### Pitfall 5: Platform Pattern Over-Copied

What goes wrong: team copies Linear AI, GitHub GraphQL, Jira plugin/server, Rails conventions, or Hotwire transport instead of architecture principle. [ASSUMED]  
Avoid: copy parity/thin-adapter/resource patterns only; preserve locked stack. [VERIFIED: `09.5-CONTEXT.md` D-01..D-06]
