# Phase 9.5 Research: Backend/API/Data-Layer Remediation

Date: 2026-05-06

## Research Status

This document is an initial seed, not sufficient for implementation.

Before Phase 9.5 planning/execution, every item in `09.5-GRAY-AREAS.md` must be researched, spiked, decided, or explicitly blocked.

## Research Question

What architecture should Fulcrum use to guarantee one unified data manipulation layer, zero business logic repetition between interfaces, one ORM/migration path, and real Web/CLI/TUI/API/tRPC integration?

The decision is not "Hono vs NestJS" in isolation.

The decision is:

```text
Which backend/API architecture best enforces:
interfaces -> application commands/queries -> ORM -> database
```

## Research Scope

This phase must deeply research all serious backend architecture alternatives relevant to Fulcrum, not only Hono and NestJS.

Included alternatives:

- NestJS.
- Hono.
- Elysia.
- Fastify.
- Express.
- Koa.
- hapi.
- tRPC standalone/internal API.
- SvelteKit server routes/actions as adapter layer.
- GraphQL Yoga/Apollo-style GraphQL.
- Effect Platform HTTP/API.
- Encore.ts.
- Plain application service layer with thin adapters.

Excluded unless later justified:

- Random low-adoption Bun microframeworks with weak maintenance signals.
- Hosted-only backend platforms that break local-first defaults.
- Frameworks requiring a language/runtime rewrite.

## Current Repo Context

Current dependencies include:

- `hono`

## Official Source Grounding

### Bun

Source: Bun official docs, Node.js compatibility.

Bun positions itself as a fast JavaScript runtime designed as a drop-in replacement for Node.js and aims for Node.js compatibility, but compatibility is ongoing and not complete. The official compatibility table lists many Node APIs as implemented and some as partial.

Implication:

- Node frameworks can often run on Bun.
- "Compatible" should be verified by spike, not assumed.
- Risk areas for NestJS on Bun include decorators/metadata, adapters, Express/Fastify ecosystem middleware, lifecycle hooks, websockets, auth/session libraries, and test runner/build tooling.

Sources:

- https://bun.sh/docs
- https://bun.sh/docs/runtime/nodejs-apis
- https://bun.sh/docs/runtime/nodejs-compat

### Hono

Source: Hono official docs.

Hono supports Bun directly. Official Bun setup uses:

```ts
import { Hono } from "hono";

const app = new Hono();
app.get("/", (c) => c.text("Hello Bun!"));

export default app;
```

Hono also has a Bun-specific static file helper via `hono/bun`.

Implication:

- Hono is low-friction for Bun.
- Hono is a strong candidate for thin REST/OpenAPI adapters.
- Hono does not enforce application architecture. It must be kept adapter-only.

Sources:

- https://hono.dev/docs/getting-started/bun
- https://hono.dev/docs/getting-started/basic

### Elysia

Source: Bun and Elysia official docs.

Bun's guide describes Elysia as a Bun-first performance-focused web framework that takes advantage of Bun HTTP, file system, and hot reloading APIs. It is described as full-featured with Express-like syntax, type inference, middleware, file uploads, and plugins for JWT authentication, tRPC, and more.

Elysia's Eden client provides end-to-end type safety without code generation by inferring the Elysia server type.

Implication:

- Elysia is the strongest Bun-native framework candidate.
- It may compete with tRPC for first-party type-safe APIs.
- It may reduce adapter/client code if the whole backend becomes Elysia.
- Risk: tighter Bun coupling, migration cost, ecosystem maturity relative to Nest/Fastify/Express, and possible conflict with existing tRPC/Hono code.
- Elysia still must be adapter-only or application-service-backed; its type safety does not solve business logic duplication by itself.

Sources:

- https://bun.sh/docs/guides/ecosystem/elysia
- https://elysiajs.com/eden/overview
- https://elysiajs.com/eden/treaty/overview

### Fastify

Source: Fastify official docs and NestJS Fastify adapter docs.

Fastify is a fast, low-overhead Node.js web framework with a plugin architecture and TypeScript support. NestJS officially supports Fastify through `@nestjs/platform-fastify`.

Implication:

- Fastify is a strong Node HTTP server candidate and a possible NestJS adapter.
- Good if Fulcrum wants performance plus mature plugin ecosystem.
- Less architectural enforcement than NestJS; more than raw Express only through conventions/plugins.
- Bun compatibility must be validated because Fastify targets Node.

Sources:

- https://fastify.dev/
- https://fastify.dev/docs/latest/Reference/TypeScript/
- https://docs.nestjs.com/techniques/performance

### Express

Source: Express official docs.

Express is a minimal, flexible Node.js web application framework with a robust set of web/mobile app features. Express 5.1 is current/default on npm with LTS schedule.

Implication:

- Express is mature and has broad middleware ecosystem.
- NestJS uses Express by default.
- Express by itself is not an architecture solution; it would make it easy to reproduce the current scattered-handler problem.
- Use only as underlying adapter if NestJS selected or if compatibility requires it.

Source:

- https://expressjs.com/

### Koa

Source: Koa official docs.

Koa is a smaller, expressive Node web framework by the team behind Express. It uses async middleware and does not bundle middleware in core.

Implication:

- Koa is a minimalist middleware framework.
- It provides little architecture enforcement.
- It is less aligned with current dependencies than Hono/Fastify/Nest/tRPC.
- Not a leading candidate for Fulcrum unless a specific middleware composition requirement appears.

Source:

- https://koajs.com/

### hapi

Source: hapi official site.

hapi presents itself as a secure framework with strong official plugin ecosystem and zero external code dependencies.

Implication:

- hapi may be relevant for security-conscious REST services.
- It is Node-oriented, not Bun-native.
- It is not already in the repo.
- It does not solve CLI/TUI shared application logic by itself.
- Candidate only if its security/plugin model materially beats Nest/Hono/Fastify after deeper spike.

Source:

- https://hapi.dev/

### NestJS

Source: NestJS official docs.

Nest is a framework for building efficient, scalable Node.js server-side applications. It provides architecture conventions through modules, controllers, services/providers, dependency injection, guards, pipes, interceptors, and testing utilities.

Nest officially documents:

- Node.js prerequisite.
- Express default platform.
- Fastify supported platform via adapter.
- Platform agnosticism for reusable logical parts across HTTP, microservices, websockets, and standalone application context.
- Standalone application context can be used for scripts, CRON jobs, and CLI-style applications.

Implication:

- NestJS directly addresses the "architecture enforcement" failure mode better than Hono.
- NestJS may be useful if Fulcrum needs framework-level DI/modules/guards/pipes to prevent drift.
- NestJS is Node-first; Bun compatibility must be proven with a spike.
- NestJS adoption cost is higher and could fight the existing SvelteKit/local-first architecture if introduced without clear adapter boundaries.

Sources:

- https://docs.nestjs.com/first-steps
- https://docs.nestjs.com/techniques/performance
- https://docs.nestjs.com/fundamentals/platform-agnosticism
- https://docs.nestjs.com/application-context

### tRPC

Source: tRPC official docs.

tRPC is for end-to-end typesafe APIs. It defines routers and procedures, commonly with validators such as Zod.

Implication:

- tRPC is appropriate for first-party typed adapters.
- tRPC should not own business/data logic.
- Routers must call application commands/queries only.

Source:

- https://trpc.io/

### SvelteKit Server Routes And Actions

Source: SvelteKit official route/action model must be reviewed in the detailed plan.

Current evidence from the repo shows SvelteKit page server files became a place for direct SQL and business logic.

Implication:

- SvelteKit should remain the web UI framework.
- SvelteKit server load/actions can be thin adapters.
- SvelteKit should not be treated as the core backend architecture for all interfaces.
- Page server files may call application commands/queries or typed clients only.

### GraphQL Yoga / Apollo-Style GraphQL

Source: GraphQL Yoga/Apollo docs need deeper follow-up if GraphQL becomes a real candidate.

Observed source grounding:

- Apollo Server docs recommend integrating production services with a fuller web framework such as Express, Koa, or Fastify for more control over security-related configuration.
- GraphQL Yoga is a TypeScript GraphQL server option.

Implication:

- GraphQL is probably not the best fit for Fulcrum's first-party local agent OS workflows because tRPC already gives first-party TypeScript typing with less schema overhead.
- GraphQL may help external clients needing flexible reads, but it adds resolver/schema complexity and another API semantics layer.
- Not a leading candidate for Phase 9.5 unless external API requirements demand query flexibility.

Sources:

- https://www.apollographql.com/docs/
- https://the-guild.dev/graphql/yoga-server

### Effect Platform HTTP/API

Source: Effect Platform package docs.

`@effect/platform` provides platform-independent abstractions and declarative HTTP API modules with endpoint schemas.

Implication:

- Effect is already a dependency in Fulcrum.
- Strong candidate for typed, composable application/service effects if the project wants functional error/resource/concurrency discipline.
- Adoption cost may be high if most code is not already Effect-style.
- Could be used internally for application services without replacing HTTP adapters.

Sources:

- https://www.npmjs.com/package/@effect/platform
- https://effect-ts.github.io/effect/docs/platform

### Encore.ts

Source: Encore official docs.

Encore.ts is an open-source backend framework for type-safe distributed systems. It provides built-in tooling for APIs, microservices, databases, queues, caches, cron jobs, local environment management, observability, API docs, and architecture diagrams.

Implication:

- Encore is interesting because it addresses backend primitives and observability, not just HTTP routing.
- It may conflict with Fulcrum's local-first agent OS architecture and existing Bun/SvelteKit/MikroORM stack.
- It introduces a separate platform/toolchain and optional cloud path.
- Not a leading candidate unless Phase 9.5 decides Fulcrum should move toward a backend-platform model.

Sources:

- https://encore.dev/docs/ts
- https://encore.dev/docs/ts/primitives/defining-apis

## Comparison

| Option | Strength | Weakness | Fit For Fulcrum |
|---|---|---|---|
| Hono REST adapter | Bun-native, small, already dependency, good for OpenAPI/REST | Does not enforce architecture; easy to put logic in handlers | Good as external API adapter if application layer is enforced |
| tRPC | Best first-party type safety; good web/CLI/TUI typed calls | Can become business-logic dumping ground | Good as internal API adapter only |
| NestJS | Strong architecture conventions, DI, guards, pipes, testing, standalone context | Higher migration cost, Node-first, Bun compatibility requires spike | Candidate if repo needs framework-enforced backend modules |
| SvelteKit server actions/load only | Already present, low migration for web | Dangerous if used as backend; page SQL already caused failure | Keep as thin web adapter only |
| Application layer without heavy framework | Directly solves no-duplication if enforced by tests | Requires discipline and boundary tooling | Required regardless of API framework |
| Elysia | Bun-first, high type inference, Eden typed client, OpenAPI/plugin ecosystem | Bun coupling, migration risk, ecosystem maturity, may duplicate tRPC role | Strong Bun-native candidate to spike |
| Fastify | Mature high-performance Node framework, plugin ecosystem, Nest adapter | Less architecture enforcement alone, Node-oriented | Candidate as Nest adapter or REST core |
| Express | Mature, broad middleware, Nest default | Minimal architecture, easy to recreate current mess | Underlying adapter only, not direct architecture |
| Koa | Small async middleware model | Minimal architecture, not current repo dependency | Low priority |
| hapi | Security/predictability positioning, official plugins | Node-oriented, new dependency, less type-first | Research-only unless security model wins |
| GraphQL Yoga/Apollo | Flexible client-driven queries, ecosystem | Schema/resolver overhead, auth complexity, not needed for first-party TS | Low priority; external API only if required |
| Effect Platform | Typed effects/errors/resources, platform APIs, already dependency | Steep adoption cost, paradigm shift | Candidate for application internals, not necessarily HTTP |
| Encore.ts | Backend primitives, local env, observability, docs | New platform/toolchain, likely conflicts with local-first/Bun stack | Research-only unless backend-platform pivot approved |

## Pushback

Hono does not provide something NestJS cannot provide architecturally.

Hono provides:

- Bun-first simplicity.
- Runtime portability.
- Lower ceremony.
- Easy REST/OpenAPI adapter.

NestJS provides:

- Stronger backend architecture conventions.
- Dependency injection.
- Guards/pipes/interceptors.
- Standalone app context usable beyond HTTP.
- Better built-in structural pressure against ad hoc code.

The real pushback:

- Choosing NestJS will not fix duplicated interface logic if CLI/TUI/web still bypass it.
- Keeping Hono will not be safe if route handlers own business logic.
- tRPC will not be safe if procedures own business logic.
- SvelteKit will not be safe if page server files own data logic.

Therefore, the architecture decision must start with the application layer contract, not the web framework.

## Required Spike

Implement one vertical slice across the leading alternatives, not only Hono/Nest:

Feature: projects create/list/update/delete.

Required proof:

- Application command/query service owns all validation, tenancy, permissions, transaction, events, DTO.
- MikroORM only.
- tRPC adapter calls application.
- REST adapter calls application.
- SvelteKit page action/load calls application or typed adapter.
- CLI command calls application.
- TUI screen calls application.
- Playwright creates project in web.
- CLI reads same project.
- TUI reads same project.
- REST/tRPC reads same project.
- Module-boundary test prevents direct DB imports from interfaces.

Spike variants:

1. Hono + tRPC + plain application services.
2. NestJS application module/providers + tRPC/REST adapter bridge, running under Bun.
3. Elysia + Eden typed client + application services.
4. Fastify direct or Fastify-under-Nest.
5. Effect application service core with Hono/tRPC adapters.

Non-leading alternatives should receive paper evaluation first:

- Express direct.
- Koa direct.
- hapi direct.
- GraphQL.
- Encore.ts.

Decision criteria:

- Bun runtime compatibility.
- Testability.
- Boundary enforceability.
- Migration cost.
- Local-first PGlite/PostgreSQL support.
- CLI/TUI reuse.
- Developer ergonomics.
- Ability to prevent logic repetition.

## Provisional Recommendation

Do not choose Hono vs NestJS before the spike.

Mandatory architecture regardless of framework:

```text
interfaces -> application commands/queries -> MikroORM repositories/EntityManager
```

Likely end state if Hono remains:

```text
src/application/*
apps/server/src/runtime/trpc/*  # thin adapter
apps/server/src/api/hono.ts    # thin REST/OpenAPI adapter
apps/web/*          # thin SvelteKit adapter
apps/cli/src/*          # thin CLI adapter
apps/tui/src/*          # thin TUI adapter
```

Likely end state if NestJS adopted:

```text
src/application/* or src/modules/*
Nest providers own application commands/queries
Nest controllers expose REST
tRPC adapter resolves Nest/application services
CLI/TUI use Nest standalone application context or direct application package
SvelteKit remains thin web adapter
```

Open decision:

- Whether NestJS's structure is worth the migration/runtime risk compared with enforcing boundaries in the existing Hono/tRPC/SvelteKit stack.
