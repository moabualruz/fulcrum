# Phase 9.5 UI/UX + Interface Integration Spec

Date: 2026-05-06

## Purpose

Phase 9.5 must repair the product surface, not only backend architecture.

The web app, CLI, TUI, API, and tRPC must expose the same product model through consistent workflows. No interface may drift into a separate product.

## Required UX Outcome

Fulcrum should feel like one product across:

- Web app.
- CLI.
- TUI.
- REST/OpenAPI.
- tRPC/agent-native calls.

Every implemented feature must be:

- Discoverable.
- Navigable.
- Actionable.
- Backed by real data.
- Covered by real tests.
- Consistent with the same backend semantics.

## Web Requirements

### Navigation

Audit and repair:

- Primary sidebar.
- Project-level navigation.
- Settings navigation.
- Command palette.
- Breadcrumbs.
- Contextual links from entity detail pages.
- Empty-state calls to action.

No route may remain orphaned unless explicitly hidden behind a feature flag or deleted.

### Page Quality

Every web page must have:

- Real load path through application query service.
- Real actions through application command service.
- Loading state.
- Empty state.
- Error state.
- Permission/tenant state.
- Stable layout.
- Accessible headings and landmarks.
- Keyboard path for primary actions.

### Design Language

Audit for:

- Stale placeholder pages.
- Mixed component patterns.
- Inconsistent buttons/forms/tables/cards.
- Overly decorative marketing-style layouts in operational surfaces.
- Pages that look built in different eras.
- Missing density/scanability for operational workflows.

Phase 9.5 should use Huashu Design as a review lens for web, CLI, and TUI, but implementation must stay grounded in Fulcrum's operational product needs.

## CLI Requirements

Every feature with CLI parity must expose:

- Command.
- Help text.
- JSON output where useful.
- Error mapping from application errors.
- Same validation behavior as web/API.
- Same tenant/org/project scoping.
- Integration test running real command.

CLI commands must not import DB or reimplement logic.

## TUI Requirements

Every feature with TUI parity must expose:

- Screen or panel.
- Navigation path.
- Keybindings.
- Action feedback.
- Empty/error/loading states.
- Same data and behavior as web/CLI/API.
- Integration test using real screen/action path where possible.

TUI screens must not import DB or reimplement logic.

## API/tRPC Requirements

tRPC:

- First-party typed adapter.
- Procedures call application commands/queries only.
- No business logic in router procedures.

REST/OpenAPI:

- External/stable API adapter.
- Handlers call application commands/queries only.
- OpenAPI schema matches DTOs.

Both:

- Same authz.
- Same validation semantics.
- Same error codes/classes mapped to transport-specific responses.

## E2E Acceptance Requirements

Every major workflow must have:

- Web Playwright E2E.
- CLI integration.
- TUI integration or explicit documented exception.
- API/tRPC integration.
- Shared seeded data or cross-surface flow.

Minimum route smoke:

- `page.goto()` response is OK.
- Page does not render SvelteKit global error.
- No uncaught browser console errors.
- No hydration errors.
- Main landmark visible.
- Primary nav visible.
- Primary action visible or explicit empty state visible.

## Deliverables

- Route inventory.
- Navigation inventory.
- Action inventory.
- CLI command inventory.
- TUI screen inventory.
- API/tRPC endpoint inventory.
- Cross-interface parity matrix.
- Playwright acceptance suite.
- Huashu design review notes.
