# Plan 61 Research: Local Server and Client Repository Standardization

Date: 2026-05-07
Status: active

## External Patterns Checked

### Bun workspaces

Source: https://bun.sh/docs/install/workspaces

Bun supports root `package.json` workspaces with independent packages and a root lockfile. Bun's documented example uses one root `bun.lock`, root `package.json`, and package-local `package.json` files. Workspace packages can depend on each other through `workspace:*`.

Fulcrum implication:
- Target shape should be a real Bun workspace graph, not only folders named `apps`.
- Final standard should use one package graph for `apps/cli`, `apps/server`, `apps/tui`, `apps/web`, and future shared packages.
- Plan 61 unified lockfile ownership into root `bun.lock` and removed the nested `apps/web/bun.lock`. CI now checks the root lockfile for the prior `cookie@0.6.0` regression.

### Turborepo workspace structure

Source: https://turborepo.com/repo/docs/handbook/workspaces

Turborepo recommends `apps/` for runnable applications/services and `packages/` for shared libraries/tooling. It also warns against ambiguous nested package globs like `apps/**` or `packages/**`.

Source: https://turborepo.com/repo/docs/core-concepts/package-types

Application packages should be leaves of the package graph. Shared code belongs in internal packages and flows toward application packages, not from one app into another.

Fulcrum implication:
- Keep runnable surfaces under:
  - `apps/web`
  - `apps/cli`
  - `apps/tui`
  - `apps/server`
- Do not let `apps/server` import `apps/web`, `apps/cli`, or `apps/tui`.
- Cross-surface tests may import multiple app packages, but production app code should not.
- Shared business logic belongs in root `src/application`, `src/domain`, `src/db` for now, then can move to `packages/*` after the graph is clean.

### Nx project graph and boundaries

Source: https://nx.dev/docs/features/maintain-typescript-monorepos

Nx emphasizes project graph visibility, explicit package relationships, and keeping TypeScript project references/workspaces in sync. The useful pattern for Fulcrum is enforceable project boundaries, not necessarily adopting Nx.

Fulcrum implication:
- Existing `graphify-out/GRAPH_REPORT.md` and `.planning/codebase/*` maps are the current project graph documents.
- Every structural migration must refresh graphify and maps in the same commit.
- Boundary tests should fail if old root surface directories reappear or if app packages lack runnable scripts.

### SvelteKit project structure

Source: https://svelte.dev/docs/kit/project-structure

SvelteKit owns app-local `src/routes`, `src/lib`, `static`, and configuration files. `$lib` is the app-local alias for `src/lib`.

Fulcrum implication:
- Do not flatten SvelteKit routes/components into root `src`.
- Keep web-specific `routes`, `lib`, `static`, `svelte.config.js`, `vite.config.ts`, `playwright.config.ts`, and web tests under `apps/web`.
- Cross-app or core imports from web should use explicit aliases, not deep relative paths.

## Competing Platform Patterns

| Platform | Pattern | Fulcrum Match |
|---|---|---|
| Turborepo create-turbo | `apps/*` runnable leaves + shared `packages/*` | Adopt structure, defer package extraction until imports stable |
| Nx TypeScript monorepo | Explicit project graph + boundary enforcement | Use graphify + tests now; Nx adoption not required |
| SvelteKit | App-local `src/routes`, `src/lib`, `static`, config | Keep `apps/web` self-contained |
| Bun workspaces | Root workspace graph + one lockfile | Adopted in Plan 61 with root `workspaces: ["apps/*"]` and root `bun.lock` |

## Repo-Specific Integration Map

### Producer / Consumer Map

| Producer | Consumers | Required Stable Path |
|---|---|---|
| CLI binary | user shell, install scripts, release build, hooks | `apps/cli/src/main.ts` |
| CLI command hub | CLI commands/tests, `fulcrum web`, `fulcrum tui` | `apps/cli/src/index.ts` |
| Web client | browser users, local `fulcrum web`, Playwright | `apps/web` |
| TUI client | `fulcrum tui`, TUI tests, cross-surface parity tests | `apps/tui/src/index.ts` |
| Local server adapters | Hono REST, tRPC, routing, Yjs runtime | `apps/server/src` |
| Application layer | web/CLI/TUI/server adapters | `src/application` |
| Persistence layer | application services and composition roots | `src/db` |
| Domain helpers | application/server/client DTOs and pure helpers | `src/domain` |

### Local-First Runtime Data Flow

1. CLI commands run in-process through `apps/cli/src/index.ts`, create a local container, then call application commands/queries or local tRPC callers.
2. TUI runs in-process through `apps/tui/src/index.ts`; it must not require a remote server for normal local workflows.
3. Web development runs through SvelteKit in `apps/web`; production local serving runs through `fulcrum web`.
4. `fulcrum web` currently lives in `apps/cli/src/index.ts`; it initializes local PGlite/MikroORM, loads built SvelteKit output, and serves it with `Bun.serve`.
5. `apps/server/src` exposes reusable server adapters (`createPublicApiRouter`, `appRouter`, `createContext`) for REST/tRPC tests and future local server composition.

## Current Gaps

- Root `package.json` now declares `workspaces: ["apps/*"]`.
- `apps/cli/package.json`, `apps/server/package.json`, and `apps/tui/package.json` now expose standard `dev`, `test`, and `typecheck` scripts.
- `apps/server/src/index.ts` exports adapters but does not own a standalone local server process yet.
- `fulcrum web` already serves the web app locally, but the server composition is located in the CLI app, not in `apps/server`.
- `.planning/codebase/STRUCTURE.md`, `.planning/codebase/ARCHITECTURE.md`, `.planning/codebase/INTEGRATIONS.md`, and `.planning/codebase/TESTING.md` still describe pre-move `src/web`, `src/cli`, `src/tui`, `src/api`, `src/trpc`, and `src/server` paths.
- `src/services` and `src/product-kernel` still exist as compatibility layers; they are not final-state package boundaries.
- `apps/server/src/trpc` and `apps/server/src/runtime/trpc` both remain active. This is a structural debt item and needs a dedicated router-consolidation plan.

## Decisions for Next Standardization Pass

- Do not claim Phase 09.5 structure complete while codebase maps point at old paths.
- Update codebase maps first so future agents operate from current reality.
- Add package-script guardrails for all `apps/*` packages before broader moves.
- Keep local-first rule explicit: web, CLI, and TUI must run locally without a remote server dependency.
- Treat lockfile unification and `apps/server` standalone serve mode as follow-up implementation steps because both touch CI/package-manager behavior.
- Use `ast-grep` for future import rewrites where source shape matters:
  - app-to-app production imports
  - legacy `src/services` drains into `src/application`
  - tRPC runtime/router consolidation

## Required Follow-Up Implementation Units

1. Server composition: move or wrap `fulcrum web` serving logic so `apps/server` owns local HTTP composition while CLI remains an invocation client.
2. Router consolidation: merge `apps/server/src/runtime/trpc` and `apps/server/src/trpc` behind one canonical tRPC tree.
3. Import cleanup: drain direct app/server calls from web/CLI/TUI into `src/application` and explicit local caller boundaries.
4. Docs/maps refresh: rerun graphify after every structural move and keep `.planning/codebase/*` current.
