# Phase 09.5 Plan 59: Repo Structure Research

Date: 2026-05-07
Status: active

## External Research

### Turborepo workspace structure

Source: https://turborepo.com/repo/docs/handbook/workspaces

Turborepo recommends `apps/` for deployable applications/services and `packages/` for shared libraries/tooling. It also warns against ambiguous nested package globs such as `apps/**` or `packages/**`.

Source: https://turborepo.com/repo/docs/core-concepts/package-types

Application packages should be leaves of the dependency graph. Shared code belongs in library packages and flows toward application packages, not the reverse.

Fulcrum implication:
- Long-term target can be `apps/web`, `apps/cli`, `apps/tui`, `packages/application`, `packages/db`, `packages/api`, `packages/orchestration`.
- Short-term Phase 09.5 should not do a package split unless package boundaries are already clean. Current repo still has cross-cutting imports through `src/product-kernel`, dual tRPC roots, and mixed test placement, so package split would add churn before the dependency graph is enforceable.

### Nx project graph structure

Source: https://nx.dev/docs

Nx emphasizes a project graph, task graph, and affected-project execution. The useful takeaway for Fulcrum is not adopting Nx now; it is keeping source ownership explicit enough that graph tools can explain boundaries and affected tests.

Fulcrum implication:
- Keep graphify as current project-graph source.
- Add structural tests that prevent empty/dead folders and duplicate template-only context docs from reappearing.
- Prefer progressive boundary cleanup before workspace/package extraction.

### SvelteKit file-based routes

Source: https://svelte.dev/docs/kit/routing

SvelteKit route directories are meaningful only when they contain route files or route-local modules. Empty route folders add navigation noise and imply missing product surface.

Fulcrum implication:
- Remove empty route folders.
- Keep SvelteKit route-local tests near route files only when they test route behavior.
- Shared route helpers belong under `src/web/src/lib`, not nested under route trees.

### Current TypeScript monorepo practice

Source: https://monorepo.tools/typescript

Modern TypeScript monorepos increasingly use source exports and explicit package boundaries. This depends on stable import ownership, otherwise packages just encode existing coupling.

Fulcrum implication:
- Do not introduce `apps/`/`packages/` in this step.
- First define and test canonical ownership:
  - `src/application/**`: business logic, data shaping, command/query DTOs.
  - `src/db/**`: entities, repositories, migrations, DB composition.
  - `src/server/trpc/**`: canonical tRPC adapter.
  - `src/api/**`: REST/Hono adapter.
  - `src/web/**`, `src/cli/**`, `src/tui/**`: invocation and visualization only.
  - `src/product-kernel/**`: legacy compatibility only, with no new runtime interface imports.

## Repo-Specific Findings

### Current source topology

Observed directories:
- `src/application/**`: broad domain module layer already exists.
- `src/db/**`: MikroORM entities, repositories, migrations.
- `src/web/**`: nested SvelteKit app, includes `src/web/tests/**`.
- `src/cli/**`: CLI commands plus 33 colocated tests.
- `src/tui/**`: TUI runtime plus tests in `src/tui/**` and `tests/tui/**`.
- `src/server/trpc/**` and `src/trpc/**`: dual tRPC roots remain.
- `src/router/**`: routing rule subsystem, not tRPC router, name collision with tRPC/router mental model.
- `src/services/**`: legacy service layer still present beside `src/application/**`.
- `src/product-kernel/**`: legacy product-store and compatibility modules still present.
- `tests/**`: broad integration/e2e/domain test tree.

### Test topology

Counts at research time:
- 792 `*.test.ts` files total.
- 589 tests under `src/**`.
- 203 tests under top-level `tests/**`.

Current pattern is mixed:
- colocated route/component/unit tests under `src/**`
- top-level integration/e2e/parity tests under `tests/**`
- web-specific Playwright/Vitest tests under `src/web/tests/**`

Decision:
- Do not mass-move tests now. It would create high import churn with low product value.
- Define policy: colocated unit/adapter tests stay with the module; cross-interface, e2e, acceptance, DB migration, and parity tests live under top-level `tests/**`.
- Move only obvious misplacements when imports are trivial and covered by tests.

Confirmed empty fixture folders that are intentional:
- `tests/scripts/license-audit.fixtures/*`

Decision:

### AST-grep targeted import scan

Commands run:

```bash
ast-grep --lang ts -p 'import { $$$ } from "$MOD"' src
ast-grep --lang ts -p 'import $$$ from "$MOD"' src
ast-grep --lang ts -p 'await $EM.$METHOD($$$)' src/web src/cli src/tui src/api src/server/trpc src/trpc src/router
ast-grep --lang ts -p '$EM.getRepository($$$)' src/web src/cli src/tui src/api src/server/trpc src/trpc src/router
```

Findings:
- `src/application/**` still imports legacy `src/services/**` wrappers in reports, runs, relationships, automations, templates, comments, sprints, docs, workflows, recurrence, and tasks. This matches older Phase 09.5 staged migration state, but it is not the final desired shape.
- `src/server/trpc/**` and `src/trpc/**` both remain active. This is a major structural cleanup target, but requires a dedicated adapter-consolidation plan because tests import both roots.
- Runtime interface `getRepository()` hits from the scan are test-only or already covered by boundary allowlists; no new runtime violation was introduced by Plan 59.

Decision:
- Plan 59 does not rewrite these imports. It records them as follow-up structural debt because moving service imports and unifying tRPC roots can change runtime behavior.
- Future Phase 09.5 structure plans should use AST-grep rewrite rules for each domain once replacement application commands/queries are fully covered.
