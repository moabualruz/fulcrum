## Resolved Decisions

### G-001 Backend/API Framework

Status: DECIDED

Decision:

- Do not adopt NestJS, Elysia, Fastify, Express, Koa, hapi, GraphQL, Effect Platform, or Encore.ts as the primary backend framework in Phase 9.5.
- Keep the existing Hono REST/OpenAPI adapter.
- Keep tRPC as first-party typed adapter.
- Build the actual architecture around `src/application/**`.

Rationale:

- The failure is not lack of framework; it is lack of enforced application boundary.
- Hono is already present and Bun-friendly.
- tRPC is already present and CLI/TUI already use in-process tRPC caller paths.
- NestJS provides stronger structure but is Node-first, adds migration cost, and still would not fix duplicated CLI/TUI/web logic unless the application layer exists first.
- Elysia is Bun-native and type-strong, but adopting it would duplicate or replace existing tRPC/Hono paths and increase migration blast radius.
- Express/Koa/Fastify/hapi are HTTP frameworks/adapters, not a solution to cross-interface logic duplication.
- GraphQL adds schema/resolver complexity without solving first-party TypeScript adapter needs.
- Encore.ts is a platform/toolchain pivot, not a contained remediation.
- Effect Platform may remain a future internal service pattern, but adopting it now would be a paradigm shift.

Phase 9.5 implementation consequence:

```text
SvelteKit web -> application
tRPC         -> application
Hono REST    -> application
CLI          -> tRPC/application
TUI          -> tRPC/application
Workers      -> application
application  -> MikroORM
```

### G-002 Application Layer Shape

Status: DECIDED

Decision:

Use explicit domain folders:

```text
src/application/<domain>/
  <domain>.commands.ts
  <domain>.queries.ts
  <domain>.service.ts
  <domain>.schema.ts
  <domain>.dto.ts
  <domain>.errors.ts
```

Services may remain classes initially to preserve existing code. Move existing `src/services/*Service.ts` with `git mv`, then split command/query/schema/error modules as needed.

### G-003 Dependency Injection And Runtime Context

Status: DECIDED

Decision:

Keep `needle-di` for Phase 9.5.

Rationale:

- Repo already has `src/db/db.module.ts` binding MikroORM repositories into `needle-di`.
- CLI `createLocalCaller()` and TUI `buildCaller()` already build request contexts around the container and forked EntityManager.
- Switching to Nest DI or Effect Context now would multiply migration risk.

Implementation:

- Add application-service bindings to the existing container.
- Continue per-request/per-command EntityManager forks.
- Revisit DI only after application layer is clean.

### G-004 Transaction Boundaries

Status: DECIDED

Decision:

- Commands own transaction boundaries.
- Queries do not open write transactions.
- Multi-step workflows use one top-level transactional command.
- Events/audit/outbox writes happen inside the same command transaction.

MikroORM docs support programmatic transaction control through EntityManager/migrator transaction context, and MikroORM's unit-of-work model already fits this boundary.

Implementation:

```ts
await em.transactional(async (tx) => {
  // validate + mutate + events/outbox
});
```

### G-005 Authorization And Tenant Enforcement

Status: DECIDED

Decision:

Authorization and tenant enforcement move into application command/query entrypoints.

tRPC middleware, REST auth middleware, web sessions, CLI auth, and TUI auth become transport authentication/context builders only.

Rationale:

- Current `permissionedProcedure()` protects tRPC, but REST/web/CLI/TUI can bypass if they call DB/services directly.
- Application layer must enforce org/project/user permissions so all interfaces share behavior.

### G-006 Validation And Schema Ownership

Status: DECIDED

Decision:

Application owns canonical validation schemas.

Interfaces may parse transport formats but must call application schema validation for semantic/business validation.

Use existing Zod schemas where practical and move them into `src/application/<domain>/<domain>.schema.ts`.

### G-007 Error Taxonomy

Status: DECIDED

Decision:

Create `src/application/errors.ts` with:

- `AppValidationError`
- `AppUnauthorizedError`
- `AppForbiddenError`
- `AppNotFoundError`
- `AppConflictError`
- `AppInvariantError`
- `AppExternalDependencyError`

Adapters map those to:

- tRPC error codes.
- REST HTTP status codes.
- CLI exit codes.
- TUI messages.
- Web form errors.

### G-008 DTO/Read Model Strategy

Status: DECIDED

Decision:

Application commands/queries return DTOs/read models, not ORM entities.

Rationale:

- Prevents leaking persistence objects to interfaces.
- Gives web/CLI/TUI/API stable shape.
- Allows tRPC/OpenAPI/CLI output to share schemas.

### G-009 Event/Audit/Notification Outbox

Status: PARTIAL DECISION

Decision:

- Application commands emit domain events once.
- Existing `EventDispatcher` logic must be moved/rewired away from ProductDb and into MikroORM/application.
- Add a transactional outbox pattern for downstream notification/search/telemetry fanout.

Remaining detail:

- Exact outbox table/entity shape and worker dispatch contract need implementation design.

### G-010 Migration Consolidation

Status: DECIDED

Decision:

- MikroORM migrations are the only runtime migration authority.
- Product-kernel SQL migrations become legacy compatibility input only.
- Tests must seed through MikroORM migrations unless explicitly testing legacy upgrade.

Implementation:

- Remove runtime `runMigrations()` calls from interface/runtime code.
- Add one legacy DB detection/upgrade adapter if needed.
- Keep existing MikroORM migration files; do not collapse them into one giant file.

Rationale:

- MikroORM docs provide first-class migration support.
- Current split caused schema mismatch (`project_id` missing during Playwright smoke).

### G-011 Product-Kernel Future

Status: DECIDED

Decision:

`src/product-kernel/store/**` must stop being runtime data manipulation API.

Allowed future states:

- Deprecated shim during transition.
- Source of logic to extract into `src/application`.
- Test compatibility only.

Not allowed:

- New interface imports from `product-kernel/db` or `product-kernel/store`.

### G-012 tRPC Role

Status: DECIDED

Decision:

tRPC remains the first-party typed adapter.

Use cases:

- Web typed calls when useful.
- CLI in-process caller.
- TUI in-process caller.
- agent-native local calls.

Constraint:

- Routers call application commands/queries only.

### G-013 REST/OpenAPI Role

Status: DECIDED

Decision:

Hono + `@hono/zod-openapi` remains external/stable REST/OpenAPI adapter.

Constraint:

- Hono handlers call application commands/queries only.
- No product-kernel stores.
- No direct DB.
- No fallback in-memory stores for accepted production routes.

### G-014 Web/SvelteKit Boundary

Status: DECIDED

Decision:

SvelteKit remains web UI framework and adapter layer.

`+page.server.ts` and `+server.ts` may:

- Read session/context.
- Parse form/request input.
- Call application command/query or typed adapter.
- Return data/actions/errors.

They may not:

- Import DB.
- Import product-kernel stores.
- Run SQL.
- Own business validation.
- Emit events directly.

### G-015 CLI Boundary

Status: DECIDED

Decision:

CLI should prefer existing `createLocalCaller()` in-process tRPC path during Phase 9.5, because it already creates shared context and avoids HTTP.

Exception:

- Very low-level system commands like `fulcrum db migrate` may call DB/migrator layer directly because their domain is DB administration, not product feature manipulation.

Fix:

- Convert direct PGlite CLI files (`src/cli/import.ts`, `src/cli/sprints.ts`, `src/cli/artifact.ts`) to caller/application adapters.

### G-016 TUI Boundary

Status: DECIDED

Decision:

TUI should keep existing `buildCaller()` in-process tRPC path.

Fix:

- Remove TUI direct DB enrichment from `enrichTuiCaller()` by exposing required auth/org/passkey/theme/status data through application/tRPC queries.

### G-017 Worker/Job Boundary

Status: DECIDED

Decision:

Workers call application commands/queries, not repositories or product-kernel stores directly.

Worker payload assertions remain worker-specific; business logic moves to application.

### G-018 Search/Indexing Consistency

Status: DECIDED

Decision:

Search indexing must be triggered from application events/outbox, not interface-specific writes.

Accepted feature writes cannot bypass search indexing.

### G-019 Realtime/Collaboration

### G-025 Rollout Strategy

Status: DECIDED

Decision:

Use vertical-slice migration, not big-bang rewrite.

Order:

1. Boundary tests RED.
2. Tasks vertical slice.
3. Sprints/reports.
4. Docs/memory/search.

Each slice must keep web/CLI/TUI/API/tRPC behavior alive before deleting old code.

## Solidified User Decisions

Decision date: 2026-05-06.

### Backend Spike Policy: Paper First

Phase 9.5 will not spend implementation time on runnable NestJS/Elysia spikes by default.

Rationale:

- The required architectural fix is one `src/application/**` layer that every interface calls.
- Once that boundary exists, Hono, NestJS, tRPC, CLI, TUI, SvelteKit, and future adapters can be evaluated as delivery surfaces instead of owning business logic.
- Official-doc and repo-evidence research is sufficient for the current decision: keep Hono REST/OpenAPI plus tRPC as thin adapters over the application layer.

Escalation rule:

- Build a runnable NestJS or Elysia spike only if the application-layer design fails a concrete check that paper research cannot resolve.

### ProductDb/Product-Kernel Shim Policy: Strict Allowlist

Phase 9.5 may keep old ProductDb/product-kernel runtime shims only as explicit transitional compatibility.

Rules:

- Every shim must be named in the data-layer inventory.
- Every shim must have a target removal slice.
- Every shim must have parity or integration tests proving it does not hide broken behavior.
- No new runtime data manipulation may be added to product-kernel SQL stores.
- Interfaces must migrate toward application commands/queries and away from direct DB access.

### Playwright Gate Policy: Tiered Mandatory

Phase 9.5 will use mandatory browser testing without making every local CI run pay for every full journey.

Normal CI must include:

- Playwright smoke that fails on HTTP 500.
- Global error page detection.
- Console error detection.
- Hydration error detection.
- Primary UI/action presence checks.
- Critical journey checks for the most important product flows.

Phase 9.5 acceptance and release/closure must include:

- Full Playwright workflows across all required web surfaces.
- Cross-surface verification that seeded workflows behave consistently through web, CLI, TUI, API/tRPC, and application services.
