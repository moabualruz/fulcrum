## Summary

Reviewed submitted Phase 09.5 source scope at standard depth. Found three blocker correctness/security issues and three warning-level regressions. Highest risk areas: transactional outbox event loss, task relationship mutation semantics, and project-scoped task access.

## Critical Issues

### CR-01: Outbox Deduplication Drops Legitimate Later Events

**File:** `src/application/outbox.ts:62`
**Classification:** BLOCKER
**Issue:** `eventKey` is derived only from `verb`, `subjectKind`, and `subjectId`, and `writeOutboxEvent()` returns an existing row for that key regardless of payload, created time, or processed state (`src/application/outbox.ts:80`). After first `task.updated:task:<id>` row exists, every later update for same task is silently skipped, so search, notifications, event bus subscribers, and audit-style consumers lose domain events.
**Fix:**
```ts
export function serializeOutboxEvent(input: OutboxEventInput): SerializedOutboxEvent {
  const subjectId = input.subjectId ?? null;
  return {
    orgId: input.orgId,
    projectId: input.projectId ?? null,
    verb: input.verb,
    subjectKind: input.subjectKind,
    subjectId,
    payload: input.payload ?? {},
    eventKey: crypto.randomUUID(),
  };
}
```
If producer idempotency is required, accept an explicit `idempotencyKey` from caller and scope uniqueness to that key, not to every future event for the same subject.

### CR-02: Removing `blocked_by` Dependencies Does Not Work

**File:** `src/application/tasks/commands.ts:287`
**Classification:** BLOCKER
**Issue:** `replaceTaskDependencyEdges()` initializes edges from all existing `task.dependencies.blocks`, then overwrites only the target task's outgoing `blocks` and adds new `blocked_by` reverse edges. It never removes old reverse edges pointing at the target. Example: if `B.blocks = [A]`, calling `setDependencies(A, { blocks: [], blocked_by: [] })` leaves edge `B -> A`, and `dependenciesForTask(A)` rebuilds `blocked_by: [B]`. User-requested dependency removal is silently ignored.
**Fix:**
```ts
function replaceTaskDependencyEdges(input: {
  taskId: string;
  tasks: Task[];
  dependencies: TaskDependencies;
}): Map<string, Set<string>> {
  const edges = new Map<string, Set<string>>();
  for (const task of input.tasks) {
    const blocks = new Set(task.dependencies.blocks);
    blocks.delete(input.taskId);
    edges.set(task.id, blocks);
  }
  edges.set(input.taskId, new Set(input.dependencies.blocks));
  for (const blockerId of input.dependencies.blocked_by) {
    const blocks = edges.get(blockerId) ?? new Set<string>();
    blocks.add(input.taskId);
    edges.set(blockerId, blocks);
  }
  return edges;
}
```

### CR-03: Project-Scoped Task Pages Can Read And Mutate Tasks From Other Projects

**File:** `src/application/tasks/queries.ts:47`
**Classification:** BLOCKER
**Issue:** `findVisibleTask()` enforces org isolation but ignores `ctx.projectId`. Web task detail, update, autosave, and delete actions pass `locals.activeProjectId` (`src/web/src/routes/tasks/[id]/+page.server.ts:16`, `src/web/src/routes/tasks/[id]/+page.server.ts:65`, `src/web/src/routes/tasks/[id]/+page.server.ts:75`, `src/web/src/routes/tasks/[id]/+page.server.ts:90`), but the application boundary allows any task ID in the org. A user in project-scoped web context can directly load or mutate a hidden task from another project by URL/form ID.
**Fix:**
```ts
export async function findVisibleTask(
  em: EntityManager,
  ctx: AppContext,
  taskId: string,
  options: { includeDeleted?: boolean } = {},
): Promise<Task> {
  const task = await em.findOne(Task, {
    id: taskId,
    ...(options.includeDeleted ? {} : { deletedAt: null }),
  } as never);
  if (!task) throw new AppNotFoundError(`Task not found: ${taskId}`);
  if (task.org.id !== ctx.orgId) throw new AppForbiddenError(`Task does not belong to org: ${ctx.orgId}`);
  if (ctx.projectId && task.projectId !== ctx.projectId) throw new AppNotFoundError(`Task not found: ${taskId}`);
  return task;
}
```

### WR-01: Public REST Task Create Accepts Fields Then Silently Drops Them

**File:** `src/api/routes/kernel-tasks.ts:139`
**Classification:** WARNING
**Issue:** `CreateTaskBody` accepts the application create schema plus `project_id` (`src/api/routes/kernel-tasks.ts:32`), including `descriptionText`, `tiptapContent`, `points`, and `assigneeId`, but the handler forwards only `projectId`, `title`, `description`, `status`, and `priority`. REST clients can receive `201` while their accepted fields are lost.
**Fix:** Forward every accepted field or remove unsupported fields from `CreateTaskBody`.
```ts
const task = await taskApplication.createTask(resolveEntityManager(c), appContext(c), {
  projectId: body.project_id ?? null,
  title: body.title,
  description: body.description ?? null,
  descriptionText: body.descriptionText,
  tiptapContent: body.tiptapContent,
  status: body.status,
  priority: body.priority,
  points: body.points,
  assigneeId: body.assigneeId,
});
```

### WR-02: `listTasks()` Ignores Project Scope At Application Boundary

**File:** `src/application/tasks/queries.ts:15`
**Classification:** WARNING
**Issue:** `listTasks()` accepts `ctx.projectId` but calls `repo.list({ orgId, includeDeleted })` and returns every org task. Several web adapters compensate with local filters, but tRPC/API callers using the application boundary get unscoped lists even when a project context was supplied.
**Fix:** Add project filtering to the repository call or filter at the application boundary before serialization.
```ts
const tasks = await repo.list({ orgId: ctx.orgId, includeDeleted: input.includeDeleted });
const scoped = ctx.projectId ? tasks.filter((task) => task.projectId === ctx.projectId) : tasks;
return scoped.map(serializeTask);
```

### WR-03: `bun run ci --tier=e2e` Does Not Run Full E2E Unless Hidden Env Var Is Set

**Classification:** WARNING
**Issue:** CLI help says `--tier=e2e` runs Playwright and full E2E, and `full` includes all tiers, but `web:e2e:full` is omitted unless `FULCRUM_RUN_E2E=1`. Default `bun run ci` therefore does not execute the newly added full E2E suites, so the gate can report success while Phase 09.5 browser journeys are not run.

```ts
{ name: "web:e2e:full", cmd: ["bun", "run", "web:e2e:full"], cwd: "src/web", env: hostHome ? { HOME: hostHome } : undefined, tier: "e2e", domain: "web" },
```
