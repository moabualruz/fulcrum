This is the Phase 2 codebase-specific integration map for the corrected copy-first restart.

## PostgreSQL And PGlite TypeORM Migration Strategy

Decision date: 2026-05-13.

Researched current docs and package state before locking this decision:

- Nest database docs: `https://docs.nestjs.com/techniques/database`
- TypeORM DataSource docs: `https://typeorm.io/docs/data-source/data-source/`
- TypeORM migration setup/execution docs: `https://typeorm.io/docs/migrations/setup/`, `https://typeorm.io/docs/migrations/executing/`
- PGlite docs: `https://pglite.dev/docs/`, `https://pglite.dev/docs/pglite-socket`
- npm versions checked on 2026-05-13: `@nestjs/core@11.1.19`, `@nestjs/typeorm@11.0.1`, `typeorm@0.3.29`, `pg@8.20.0`, `@electric-sql/pglite@0.4.5`, `@electric-sql/pglite-socket@0.1.5`, `typeorm-pglite@0.3.4`.

Final strategy:

- Use Nest defaults with `TypeOrmModule.forRootAsync(...)`, `TypeOrmModule.forFeature(...)`, `InjectRepository(...)`, and `DataSource`/`EntityManager` injection only inside server/application-service modules.
- Use TypeORM's normal `postgres` driver with `pg` for both production PostgreSQL and local/test PGlite. PGlite local/test runs behind `@electric-sql/pglite-socket`, so TypeORM sees the same PostgreSQL wire protocol and the same `DATABASE_URL` shape as production.
- Do not make `typeorm-pglite` the default because it is a non-default community driver and would split local/test behavior away from production. It remains a documented fallback only if the PGlite socket path hits a verified TypeORM blocker.
- Set `synchronize: false` in every environment. Schema changes land only through TypeORM migrations.
- Keep `migrationsRun: false` for normal server boot. Migrations run through explicit CLI/server commands and CI gates so app startup does not silently mutate user data.
- Use `migrationsTableName: "schema_migrations"` so the replacement keeps Fulcrum's existing migration ledger semantics.
- Keep TypeORM migration classes as the new forward history under the owning service's `src/infrastructure/database/**` directory. The exported `DataSource` helper must consume those service-owned migrations explicitly.
- Export one TypeORM `DataSource` helper from `services/platform-core/src/infrastructure/database/typeorm-data-source.ts` for CLI and tests. TypeORM docs require a data-source config path for `migration:run`, `migration:revert`, and `migration:generate`.
- Generate compiled-JS production migrations or run TS migrations through a Bun-compatible wrapper only after verifying TypeORM CLI behavior. TypeORM docs note `migration:run` and `migration:revert` operate on JavaScript unless a TS runner is used.

Migration phases:

1. Add Nest database module and exported TypeORM data-source config under service infrastructure without changing current runtime callers.
2. ## Replacement Boundary Decisions

- Preserve current application-service tests while replacing the implementation behind them.
- Do not port Svelte component-local fetch/mutation helpers into React. Replace with a typed API client or route loaders/actions backed by Nest services.
- Do not port CLI/TUI local ORM wiring. Replace `src/application/cli-tui/caller-context.ts` with a Nest/API or generated client boundary.
- Preserve current command names where they express user workflows, but expand with ACP/planning/review/dependency/UAT commands.
- Preserve current TUI screen intent, but add ACP traffic, plan review, dependency preflight, UAT/code-review, and generated E2E screens.
- Keep current tests as regression gates, but do not treat Phase 9.6 legacy UAT fixture as sufficient for the new copy-first objective.
