## 1. System Classification

**System Type:** Hybrid — autonomous task agents + code automation + agent observability + context/memory workflow system.

**Description:**
Phase 9.6 turns Fulcrum's existing Symphony/orchestration stack into a coherent local-first Agent OS workflow. Humans and agents operate on one project graph: workspace -> project/subproject -> repo -> work item -> docs/context -> run/live session -> artifacts/memory/follow-ups -> audit/reports. Good means agent runs start from real work, assemble inspectable context, execute through a traceable workflow/runtime, produce reviewable artifacts and memory candidates, and expose the same trace graph across Web, CLI, TUI, and API.

**Critical Failure Modes:**
1. Agent runs become standalone logs without task/project/repo/context/artifact/memory provenance.
2. Context bundles include stale, orphaned, or untraceable docs/memory/artifacts, causing wrong work or polluted memory.
3. Agents mutate tasks/docs/memory/project settings outside configured authority, trust mode, or audit policy.
4. Symphony runtime state diverges from product trace state, hiding retry/reconciliation/workspace/session failures.
5. Automated tests prove isolated routes/commands but miss full human and agent journeys across clients.

### Known Failure Modes in This Domain

1. **Disconnected CRUD:** surfaces expose domain objects but not workflow relationships; users cannot follow project -> task -> run -> artifact -> memory.
2. **Trace erosion:** app-server thread/turn/session IDs, token updates, approvals, workspace path, or retry entries are captured in logs but not persisted into product trace.
3. **Context pollution:** memory or docs created by failed/unreviewed runs become future context without acceptance path.
4. **Authority drift:** template trust mode, run policy, and agent profile capability disagree, and the UI cannot explain why an action was allowed.
5. **False completion:** tests pass because routes render or commands exist, while H1-H6/A1-A5 journeys fail.
6. **Safety invisibility:** destructive/executable/authority-escalating actions lack dry-run, snapshot, explicit approval, or audit evidence.

### Regulatory / Compliance Context

No external statutory compliance regime is required for Phase 9.6. Internal compliance is mandatory: Symphony SPEC conformance, local-first safety posture, no secret leakage in prompts/logs/artifacts, complete audit trails for human/agent/automation/system actors, and explicit trust-mode handling for destructive, executable, and authority-escalating actions.

## 2. Framework Decision

**Selected Framework:** Fulcrum Symphony internal orchestration + existing Codex app-server adapter + Fulcrum context/memory/artifact graph.

**Version:** Project-local implementation pinned to `vendor/openai-symphony` commit `58cf97da06d556c019ccea20c67f4f77da124bf3`; SPEC sha256 `36153a9ae3340b280cba30f3397631e466268386218dd0db8f7101a2306f3c42`.

**Rationale:**
Phase 9.6 is not selecting a new agent framework. Fulcrum already has the core runtime: Symphony workflow loader, orchestration state machine, workspace manager, Codex app-server client, artifact harvesting, memory/context systems, Web/CLI/TUI surfaces, and local-first persistence. Adding LangGraph, CrewAI, OpenAI Agents SDK, Temporal, or LangSmith as a runtime would duplicate existing orchestration and violate the phase goal of repairing product workflow completeness around Fulcrum's native graph. Phase 9.6 should model UX and eval patterns after LangSmith/Temporal/OpenAI tracing where useful, but implement them through Fulcrum's own typed services, event stream, trace spine, and tests.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangGraph | Good for stateful workflows, but would add a second orchestration runtime beside Symphony instead of fixing the existing one. |
| OpenAI Agents SDK | Strong tracing/guardrail primitives, but Phase 9.6 must preserve existing Codex app-server/Symphony integration and model/provider flexibility. |
| CrewAI | Role/task abstraction is too coarse for strict workspace, trace, retry, approval, and project graph requirements. |
| LlamaIndex | Useful for RAG/data ingestion, but this phase is orchestration/product graph repair, not RAG framework adoption. |
| Temporal | Excellent durability/visibility model, but adding it as runtime is out of scope; use its workflow/activity/retry visibility as product pattern. |
| LangSmith/Langfuse/Phoenix runtime | Useful observability products, but Fulcrum must expose local-first trace natively. External tracing can be optional later. |

**Vendor Lock-In Accepted:** Partial. Fulcrum continues using the Codex app-server/Symphony contract where required, but the product graph, context bundle, memory, artifacts, audit, and UI/API trace model remain Fulcrum-owned and local-first.

### Common Pitfalls

1. Treating `agent_runs` as sufficient instead of linking project/task/repo/context/session/artifacts/memory/audit.
2. Adding another workflow framework instead of exposing missing Symphony/Fulcrum state.
3. Returning untyped `links` blobs without required trace spine fields.
4. Allowing generated CRUD endpoints to create orphan tasks/docs/runs/artifacts/memory.
5. Capturing app-server events in logs but not persisting thread/turn/session/tool/approval/token fields.
6. Promoting memory without source refs, scope, confidence, status, and acceptance policy.
7. Testing Web, CLI, and TUI separately without verifying same IDs across clients.

## 4. Implementation Guidance

**Model Configuration:**
Use existing agent profile/model routing. Phase 9.6 must store effective profile/model/Codex command/sandbox/approval posture in the routing decision and run trace. Do not hardcode a provider. Defaults come from template/workflow/profile/project policy, with run-level override recorded.

**Core Pattern:**
Dispatch only from the product graph:

```text
task aggregate -> context preview -> route selection -> strict Symphony snapshot
  -> workspace safety -> app-server session -> event stream
  -> artifact/memory/proposal extraction -> accepted mutations -> audit/report
```

**Tool Use:**
Tools are product graph actions: read trace, preview context, create/update work items, create/update docs, link/promote artifacts, create/promote memory candidates, operate automations, import/apply templates, adjust project settings, request approval/user input. Effective permission must be computed from agent profile, template/workflow, project policy, and task/run override.

**State Management:**
Persist state through canonical application services and MikroORM/PGlite/PostgreSQL-compatible schema. Required persisted objects include context bundle source refs, routing decision, strict issue snapshot, run attempt, live session event stream, artifact lifecycle, memory candidate lifecycle, audit causation chain, and no-orphan relationship edges.

**Context Window Strategy:**
Context bundles must be deterministic, inspectable, and reconstructable. Store included/excluded source refs, reasons, token estimates, stale/conflict warnings, and scope. Do not rely on a prompt blob as the only record. Context preview defaults to current project/subproject and can explicitly include parent/root/All projects where policy allows.

## 4b. AI Systems Best Practices

### Structured Outputs with Pydantic

TypeScript uses Zod as the runtime contract source. Pydantic examples are included for evaluator/fake-run parity and external judge fixtures when needed.

```python
from pydantic import BaseModel, Field
from typing import Literal

class TraceRef(BaseModel):
    kind: Literal["workspace", "project", "repo", "task", "doc", "context_bundle", "run", "artifact", "memory", "audit"]
    id: str

class AgentRunProposal(BaseModel):
    proposal_kind: Literal["task_status", "follow_up_task", "doc_update", "memory_candidate", "artifact_retention"]
    source_run_id: str
    target: TraceRef
    summary: str = Field(min_length=1)
    confidence: float = Field(ge=0.0, le=1.0)
    requires_review: bool
```

Equivalent Zod contracts must exist for product code:

```ts
const traceRefSchema = z.object({
  kind: z.enum(["workspace", "project", "repo", "task", "doc", "context_bundle", "run", "artifact", "memory", "audit"]),
  id: z.string().min(1),
});

const agentRunProposalSchema = z.object({
  proposalKind: z.enum(["task_status", "follow_up_task", "doc_update", "memory_candidate", "artifact_retention"]),
  sourceRunId: z.string().min(1),
  target: traceRefSchema,
  summary: z.string().min(1),
  confidence: z.number().min(0).max(1),
  requiresReview: z.boolean(),
});
```

### Async-First Design

Live run supervision is event-driven. Append run events immutably, derive transcript/timeline views from events, and stream to Web/CLI/TUI. Avoid synchronous UI assumptions around app-server turns, approvals, artifact harvest, and memory extraction. Long operations emit intermediate events with causation IDs.

### Prompt Engineering Discipline

Separate Symphony strict prompt input (`issue`, `attempt`) from Fulcrum extension context (`docs`, `memory`, `artifacts`, `repo`, `priorRuns`). Unknown prompt variables/filters must fail. Prompt render errors must be visible in Web/CLI/TUI run setup and audit.

### Context Window Management

Use source selection policy, token budgets, and explicit exclusions. Prefer linked docs/memory/artifacts/repo slices from current task/project; parent/root/global context requires explicit policy. Record omitted-but-relevant sources and stale/conflict warnings.

### Cost and Latency Budget

Prefer deterministic code checks and fake-run UAT in CI. Real local agent runs are optional final evidence. Record token totals/rate-limit updates from app-server events; expose in trace and reports. Cache context previews where source refs and policies have not changed.

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| Missing trace spine | Dispatch/mutation lacks required workspace/project/task/context/run/audit refs | Block mutation or mark run invalid |
| Authority escalation | Full auto enablement, policy loosening, agent admin permission, template trust change | Require explicit approval unless preconfigured with extra confirmation |
| Destructive action | reset/rebuild/delete/schema/data wipe | Dry-run/snapshot + explicit confirmation; audit always |
| Executable template effect | Script/hook/shell/network action in template | Trust-mode check + dry-run preview + approval unless trusted policy allows |
| Memory promotion | Candidate lacks source/scope/confidence or failed-run origin | Block auto-promotion; require review |
| Prompt render/config failure | Unknown variable/filter, invalid workflow config, missing repo/workspace path | Block dispatch; surface exact error in Web/CLI/TUI |
| App-server stalled/blocked | Missing heartbeat, pending approval timeout, retry slot exhaustion | Notify, expose recovery action, record reconciliation event |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| Orphan entity count | Every CI/UAT fixture and nightly local audit | Block phase completion; add migration/service fix |
| Cross-surface ID parity | H1-H6/A1-A5 journey suites | Regress failing surface adapter or shared API |
| Memory rejection/supersession rate | Sample completed fake/real runs | Tune extraction policy and review UI |
| Context stale/conflict warnings | Sample context previews with parent/child inheritance | Improve source freshness and conflict resolution |
| Agent authority denials/overrides | Sample run policies and audit events | Tighten defaults or clarify trust UI |

## 7. Production Monitoring

**Tracing Tool:** Fulcrum native trace spine by default. Optional future export to Arize Phoenix/Langfuse/LangSmith can be added behind config, but Phase 9.6 completion depends on native local trace.

**Key Metrics to Track:**
- Run count by project/subproject/status/attempt/failure class.
- Context bundle source counts, token estimates, stale/conflict warning counts.
- Approval requests, denials, timeouts, and Full auto actions.
- Artifact lifecycle counts and retention expirations.
- Memory candidates accepted/rejected/superseded/promoted by scope.
- Orphan graph count and cross-surface parity failures.

**Alert Thresholds:**
- Any orphan task/doc/run/artifact/memory in canonical UAT fixture: block.
- Any dispatch without project/task/repo/context/routing trace: block.
- Any destructive/executable/authority-escalation action without audit: block.
- Any fresh local doctor false schema error after rebuild: block.
- Any H1-H6/A1-A5 journey failure: block Phase 10.

**Smart Sampling Strategy:**
Prioritize failed/stalled/retried runs, Full auto runs, destructive/template executions, global memory promotions, parent-project aggregate mutations, and any run with stale/conflicting context warnings.
