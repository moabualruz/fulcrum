## Hard Rules For This Restart

- Do not delete `.scratch/upstream-product-replacement/**` until the full usability/workflow/value mapping is verified and cleanup is explicitly approved.
- Do not track `vendor-src/**` or any equivalent third-party archive folder as the implementation.
- Keep full upstream repos and baseline-copy experiments in ignored scratch storage.
- Track copied upstream code only after it is copied or adapted into Fulcrum's real `apps/**`, `src/**`, `tests/**`, migrations, or package structure.
- Every copied/adapted production file must be traceable to upstream repo, commit SHA, original path, local target path, license, and adaptation notes through the planning/copy matrix docs. Do not put third-party product names or provenance headers in runtime code unless the file is a real third-party integration boundary.
- Start with research and mapping. Do not approximate UI/UX before reading upstream flows and tests.
- Web, CLI, and TUI stay invocation/visualization layers. No direct ORM calls and no duplicated business logic in those surfaces.
- Server target remains NestJS defaults with `@nestjs/typeorm`, `typeorm`, Express adapter, OpenAPI, and class-validator unless deep mapping finds a blocker.
- Database remains PostgreSQL/PGlite.
- Database startup must be seamless: no configured database URL means managed local PGlite under `FULCRUM_HOME/pglite.data`; `FULCRUM_DATABASE_URL` or `DATABASE_URL` switches the same Nest/TypeORM code path to normal PostgreSQL; `FULCRUM_TYPEORM_PGLITE_SOCKET_URL` is only for an explicit prestarted PGlite socket.
- Single stack rule, effective now: no `.sql` migration files, no dual ORM runtime, and no parallel HTTP/API framework beside NestJS. TypeScript TypeORM migration classes are the persistence migration target. Hono, tRPC, MikroORM, and Kysely are removal debt unless a short-lived bridge is explicitly documented with owner, blocker, and deletion criteria.
- NestJS project standard, effective now: server features are organized as Nest modules with controllers, providers/application services, DTOs, validation pipes/class-validator DTOs, guards/interceptors where appropriate, Swagger/OpenAPI through `@nestjs/swagger`, and TypeORM access through service infrastructure or injected providers. Standalone route trees, ad hoc adapters, and database logic in app surfaces are not acceptable final structure.
- Dependency consolidation rule, effective now: use one dependency per need. Duplicate routers, ORMs, migration systems, schema tools, queue engines, state libraries, or API frameworks are architecture debt until removed or explicitly justified.
- Bun remains preferred. Switch to pnpm only if Bun blocks the chosen Nest/React integration.
- Legal/about/package metadata is not the first workstream. Workflow preservation comes first.
- Naming is responsibility-first: do not introduce goal, phase, plan-progress, or third-party app/tool names in code symbols, code comments, user-facing code labels, or code file names. Use names that describe the feature, module, responsibility, or behavior. Keep inspiration, attribution, and copied-source/provenance shoutouts in docs or manifest-style documentation unless a file is truly a third-party integration boundary.
- Existing code/file names must pass `tests/infrastructure/responsibility-first-naming.test.ts` before new workflow progress is accepted. Do not broaden or reintroduce source-product, phase, goal, or plan-progress labels while implementing the remaining workflow pieces.
- Structure is service-oriented DDD: product code should live behind bounded service/domain boundaries with clear `domain`, `application`, `infrastructure`, and `interface` responsibilities, so each service can later split into an independent package, process, or repository. Do not create catch-all copied-source, upstream-derived, phase-named, or goal-named runtime/test folders.
- Current runtime service roots are `services/agent-client-protocol`, `services/knowledge-workspace`, `services/work-management`, `services/planning-review`, `services/execution-orchestration`, and `services/workflow-coordination`. New code belongs under the owning service's `src/{domain,application,infrastructure,interface}` boundary or the existing `apps/**` invocation/visualization layer.
- `apps/server` is a Nest/Express composition root. It may wire service modules and exported compatibility APIs, but TypeORM boot/data-source/persistence implementation belongs under service infrastructure such as `services/platform-core/src/infrastructure/database/**` or the owning bounded service's `src/infrastructure/database/**`.
