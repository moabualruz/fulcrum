## Hard Rules For This Restart

- Do not delete `.scratch/upstream-product-replacement/**` until the full usability/workflow/value mapping is verified and cleanup is explicitly approved.
- Do not track `vendor-src/**` or any equivalent third-party archive folder as the implementation.
- Keep full upstream repos and baseline-copy experiments in ignored scratch storage.

- Every copied/adapted production file must be traceable to upstream repo, commit SHA, original path, local target path, license, and adaptation notes through the planning/copy matrix docs. Do not put third-party product names or provenance headers in runtime code unless the file is a real third-party integration boundary.
- Start with research and mapping. Do not approximate UI/UX before reading upstream flows and tests.
- Web, CLI, and TUI stay invocation/visualization layers. No direct ORM calls and no duplicated business logic in those surfaces.
- Server target remains NestJS defaults with `@nestjs/typeorm`, `typeorm`, Express adapter, OpenAPI, and class-validator unless deep mapping finds a blocker.
- Database remains PostgreSQL/PGlite.
- Database startup must be seamless: no configured database URL means managed local PGlite under `FULCRUM_HOME/pglite.data`; `FULCRUM_DATABASE_URL` or `DATABASE_URL` switches the same Nest/TypeORM code path to normal PostgreSQL; `FULCRUM_TYPEORM_PGLITE_SOCKET_URL` is only for an explicit prestarted PGlite socket.
- Single stack rule, effective now: no `.sql` migration files, no dual ORM runtime. TypeScript TypeORM migration classes are the persistence migration target. Hono, MikroORM, and Kysely are removal debt unless a short-lived bridge is explicitly documented with owner, blocker, and deletion criteria. tRPC is retained as a NestJS-native dual-exposure protocol: `@trpc/server` is mounted as Express middleware inside the NestJS bootstrap via `createExpressMiddleware`, tRPC routers are `@Injectable()` NestJS providers that inject the same application services as HTTP controllers, and CLI/TUI use `createCallerFactory` for zero-overhead in-process calls. Both HTTP (NestJS controllers) and tRPC endpoints expose every API surface — tRPC is the default for web/CLI/TUI, HTTP is the fallback for external integrations and webhooks. WebSocket is added only where beneficial (real-time subscriptions). See `.planning/research/nestjs-trpc-native-integration-patterns.md` for the Pattern A architecture reference.
- NestJS project standard, effective now: server features are organized as Nest modules with controllers, providers/application services, DTOs, validation pipes/class-validator DTOs, guards/interceptors where appropriate, Swagger/OpenAPI through `@nestjs/swagger`, and TypeORM access through service infrastructure or injected providers. tRPC routers are NestJS `@Injectable()` providers within a `TrpcModule` — they inject the same application services as controllers and are mounted as Express middleware. Standalone route trees, ad hoc adapters, and database logic in app surfaces are not acceptable final structure.
- Dependency consolidation rule, effective now: use one dependency per need. Duplicate routers, ORMs, migration systems, schema tools, queue engines, state libraries, or API frameworks are architecture debt until removed or explicitly justified.
- Bun remains preferred. Switch to pnpm only if Bun blocks the chosen Nest/React integration.
- Legal/about/package metadata is not the first workstream. Workflow preservation comes first.
- Naming is responsibility-first: do not introduce goal, phase, plan-progress, or third-party app/tool names in code symbols, code comments, user-facing code labels, or code file names. Use names that describe the feature, module, responsibility, or behavior. Keep inspiration, attribution, and copied-source/provenance shoutouts in docs or manifest-style documentation unless a file is truly a third-party integration boundary.
- Existing code/file names must pass `tests/infrastructure/responsibility-first-naming.test.ts` before new workflow progress is accepted. Do not broaden or reintroduce source-product, phase, goal, or plan-progress labels while implementing the remaining workflow pieces.
- Structure is service-oriented DDD: product code should live behind bounded service/domain boundaries with clear `domain`, `application`, `infrastructure`, and `interface` responsibilities, so each service can later split into an independent package, process, or repository. ## Required Workflow To Preserve

1. Start work from freeform docs or ACP guided UI.
2. Use freeform docs as context when the user later moves into ACP planning/task creation.
3. Generate technical planning with prototypes and boilerplate, not document-only planning.
4. Run Plannotator-style feedback loops over plans, prototypes, boilerplates, UAT, and code review.
5. Document approved plans/prototypes/boilerplate into Fulcrum workflow docs.
6. Break work into goals, phases/cycles, tasks, dependencies, success criteria, and agent-checkable completion criteria.
7. Provide Plane/Fusion-style board/task run buttons that disclose dependency trees before execution.
8. Run task agents against success criteria, then QA/review feedback loops until automated feedback is exhausted.
9. Run final QA/review against docs and success criteria.
10. Prompt for UAT and code review, with optional auto-approval/auto-feedback configuration.
11. After approval, generate real-data E2E tests without mocks/fakes to codify accepted behavior.
12. Continue the cycle from ACP edits or manual/freeform document edits.

Test-scope note: the real-data/no-mock rule above is for post-approval E2E workflow regression tests. It must not be generalized to unit tests or narrow integration tests; those stay fixture-backed unless the behavior under test is persistence, migration, transactionality, query shape, or service wiring through the database boundary.
