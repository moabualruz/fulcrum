# Phase 9.6 Agent Workflow and UX Spec

**Created:** 2026-05-08
**Audience:** Agent operator and agents acting inside Fulcrum.

## Agent Product Model

Agent runs are not standalone logs. They are workflow executions attached to project work.

Required relationship graph:

```text
Agent profile
  -> Routing rule / workflow config
  -> Project
  -> Task / issue
  -> Context bundle
  -> Run attempt
  -> Trace / transcript / tool calls
  -> Workspace diff
  -> Artifacts
  -> Memory candidates
  -> Follow-up tasks / docs / decisions
  -> Audit + notifications
```

Symphony-compatible trace graph:

```text
workflow service config
  -> strict issue snapshot
  -> workflow selection
  -> workspace key/root/local path
  -> run attempt
  -> app-server thread/turn/session
  -> event stream/tool policy/approvals/user input
  -> tracker comments/status
  -> cleanup/reconciliation/retry entry
```

Fulcrum must support both views at once: product graph for project management and Symphony graph for orchestration conformance. The same run detail must show both.

## Agent UX Contract

| Agent Surface | Required Data | Required Actions | Human-Visible Mirror |
|---|---|---|---|
| Dispatch context | task, docs, memory, artifacts, repo state, skill/rules, previous runs, exclusions, token counts | preview, override, approve route, start | task detail context preview |
| Routing decision | workflow config, agent profile, model, runtime, matched rule, alternatives | confirm, override, retry with changed route | run dispatch route panel |
| Live session | transcript, events, tool calls, pending approvals, user input, tokens, heartbeat | approve, deny, answer, cancel, continue | Web live run, CLI watch, TUI live pane |
| Workspace safety | repo path, workspace root/key, git status, hooks, dirty files, cleanup mode | inspect, hold cleanup, archive diff | repo/run safety panel |
| Output review | diff, artifacts, summaries, proposals, memory candidates | accept, reject, link, promote, create follow-up | run completion review |
| Audit/trace | actor, causation id, event ids, source/target entities | inspect trace, export JSON | trace drawer and reports |

## Agent Journey A1: Dispatch From a Task

Goal: start an agent run from a real work item.

Required steps:

1. Human or automation selects project task.
2. Fulcrum assembles context from task, linked docs, repo state, recent runs, memory, artifacts, and skill prompts.
3. Operator previews context bundle.
4. Routing chooses agent/profile/model or asks for confirmation.
5. Run starts with explicit project/task/repo/workspace path.
6. Symphony run snapshot stores upstream-compatible issue/workflow/service/workspace fields when orchestration uses Symphony.

Detailed runtime steps:

1. Task aggregate loads project, repo, docs, dependencies, comments/activity, previous runs, artifacts, memory, and automation rules.
2. Context builder emits deterministic source list with inclusion reasons, exclusions, token estimates, stale/conflict warnings, and source ids.
3. Route engine evaluates workflow configs and agent profiles; records selected rule, alternatives, and override actor.
4. Dispatch creates run attempt with project/task/repo/context/route/workflow ids.
5. Workspace allocator resolves local path, workspace root, safety hooks, branch/dirty state, cleanup policy.
6. App-server or local runner starts live session with thread/session identifiers.
7. Audit event records dispatch actor and causation id.

Required trace ids:

- workspace id
- project id
- task id
- repo id/local path/workspace root
- context bundle id
- routing decision id
- workflow config id
- agent profile/model id
- run attempt id
- live session/thread id when available

Acceptance:

- `agent_runs` row has project, task, repo/workspace, profile, context bundle, status, attempt, and actor.
- Web, CLI, and TUI all show the same dispatch options and context preview.
- Dispatch from a task is the primary run path; global run creation is advanced/secondary.

## Agent Journey A2: Supervise Execution

Goal: observe and intervene in an active run.

Required steps:

1. View active run in project and global run views.
2. See lifecycle state, transcript, tool events, current step, elapsed time, last heartbeat, and retry policy.
3. Cancel, retry, continue, or approve gated action.
4. Receive notification on blocked, failed, succeeded, artifact-created, memory-candidate events.
5. See Symphony state machine state, retry/backoff policy, tracker update status, cleanup state, and reconciliation status when applicable.

Detailed runtime steps:

- Event ingestion appends immutable events with event id, source, sequence, timestamp, turn id, tool call id, and causation id.
- Transcript view is derived from events, not separately edited.
- Tool timeline groups by turn and distinguishes reads, writes, shell commands, network calls, approvals, and errors.
- Approval gates show policy, requested tool/action, arguments summary, risk, timeout, requester, and available actions.
- Retry screen shows failed attempt, failure class, retry count, backoff, whether context/workspace changed, and new attempt link.
- Cancellation records who cancelled, when, current runner state, cleanup result, and partial artifacts.

Required event consumers:

- Web live run detail and notification center.
- CLI `fulcrum runs watch --json`.
- TUI live run pane.
- Artifact harvester.
- Memory candidate extractor.
- Automation rule engine.
- Audit/report metrics.

Acceptance:

- Web run detail shows trace timeline, transcript, diff, artifacts, memory candidates, context bundle, and audit events.
- CLI supports `fulcrum runs watch <id>`, `cancel`, `retry`, `continue`, `artifacts list`, `context show`.
- TUI run screen supports live supervision, key actions, and detail panes.

## Agent Journey A3: Produce Artifacts and Diffs

Goal: make agent output inspectable and reusable.

Required steps:

1. Agent creates or modifies files.
2. Fulcrum captures workspace diff.
3. Fulcrum harvests artifacts.
4. Artifacts link to run, task, project, repo commit/path, and search index.
5. Human accepts, rejects, archives, downloads, or promotes artifacts into docs/memory.
6. Run completion proposes follow-up tasks, doc changes, and memory candidates from artifact contents with source refs.

Detailed runtime steps:

- Workspace diff capture records changed files, status, repo path, branch, base/head when available, and safety state.
- Artifact capture records source event id, source file path, kind, MIME, checksum, size, retention policy, and preview metadata.
- Artifact relationship writer attaches artifact to run, task, project, repo, and optional doc/memory targets.
- Search index receives artifact kind/id/project/task/run and preview fields.
- Audit records artifact creation, archive, promotion, and retention changes.

Required artifact kinds:

- patch/diff
- transcript/report
- generated doc/spec/plan
- test output/log
- image/media where applicable
- structured JSON result
- external tracker/comment snapshot for Symphony-linked runs

Acceptance:

- Artifact detail shows source run, task, project, file path, MIME/kind, checksum, retention, preview, and linked docs/memory.
- CLI/TUI can inspect/download/archive artifacts.
- Search returns artifacts with project/task/run context.

## Agent Journey A4: Convert Output Into Knowledge

Goal: capture useful decisions and facts without polluting memory.

Required steps:

1. Run completes with transcript and artifacts.
2. Fulcrum extracts memory candidates with source refs.
3. Human reviews candidates.
4. Accepted candidates become project or global memory.
5. Future context bundles cite those memory entries and source runs/docs.
6. Rejected/superseded memory remains auditable and excluded from future context.

Detailed runtime steps:

- Candidate extractor receives run transcript, artifacts, accepted proposals, linked docs, task outcome, and failure notes.
- Candidate stores scope suggestion, source refs, confidence, duplicate/supersession candidates, and reason.
- Review UI groups candidates by project/task/run and risk: decision, fact, convention, failure, dependency, user preference.
- Accepted memory writes scope and source provenance; future context bundles cite exact memory id and reason.
- Demotion/supersession records old/new memory ids and preserves source trail.

Required constraints:

- No memory without source.
- No project memory from failed run unless human explicitly accepts.
- No global memory promotion without scope warning and audit row.
- Context preview must show last-used and source refs for every included memory.

Acceptance:

- Memory candidate UI exists in run detail and project memory view.
- Memory entries include scope, key/topic, source kind/id, confidence, created by, and last used.
- Doctor memory schema check passes on fresh and migrated DB.
- CLI/TUI support list/review/promote/demote memory candidates.

## Agent Journey A5: Close the Loop

Goal: agent work updates the product graph.

Required steps:

1. Run result proposes task status update, follow-up tasks, doc updates, and automation outcomes.
2. Human accepts or edits proposed changes.
3. Fulcrum records audit events and notifications.
4. Project dashboard reflects updated status.
5. Symphony-linked tracker comments/status updates reconcile to Fulcrum task activity without overwriting human decisions.

Detailed runtime steps:

- Completion review separates facts from proposed mutations: status update, labels, follow-up tasks, doc edits, artifact retention, memory promotions.
- Human can accept all, accept selected, edit before apply, reject, or defer.
- Automation can apply only rules explicitly configured for that project/workflow.
- Tracker sync records upstream/downstream ids and conflict resolution.
- Reports update from accepted state changes and run outcome metrics.

Required audit fields:

- actor type: human, agent, automation, system.
- source entity and target entity.
- operation and before/after summary.
- causation id linking dispatch/run/proposal/action.
- external ids for Symphony/tracker/app-server events where applicable.

Acceptance:

- A succeeded run can update task status only through explicit accepted action or configured automation.
- Follow-up tasks link back to source run.
- Doc updates link to run and task.
- Audit differentiates agent, human, automation, and system actors.

## Agent-Accessible Product Actions

Agents must be able to operate through the same product graph humans use. Required actions:

| Action | Inputs | Output | Guard |
|---|---|---|---|
| read project trace | project id/slug | linked repos/tasks/docs/runs/artifacts/memory | read-only |
| preview context | task id, optional route | context bundle with source refs/reasons | read-only |
| create run proposal | run id, proposal kind/body | pending proposal id | requires human/automation acceptance |
| create follow-up task | project id, source run/task, draft fields | pending or created task | policy-controlled |
| link artifact | artifact id, target kind/id | link event | audit |
| create memory candidate | source kind/id, scope suggestion, body | candidate id | review required |
| append doc suggestion | doc id or template, source run/task | pending doc change | review required |
| request approval/user input | run id, prompt/tool context | approval event | timeout/policy |

Agents must not update task status, accepted memory, retained artifacts, or docs directly unless an explicit project automation policy grants that action.

## Web/CLI/TUI Parity Requirements

Web:

- Run dispatch modal/drawer shows task, context, route, workspace, Symphony state.
- Run detail shows live session, transcript, tool timeline, approvals, diff, artifacts, memory candidates, proposals, audit.
- Trace drawer shows product and Symphony graphs.

CLI:

- `fulcrum runs start --task <id> --project <id> --json`
- `fulcrum context preview --task <id> --json`
- `fulcrum runs watch <id> --json`
- `fulcrum runs approve|deny|cancel|retry|continue <id>`
- `fulcrum artifacts list --run <id> --json`
- `fulcrum memory candidates list --run <id> --json`
- `fulcrum trace show run <id> --json`

TUI:

- Active project workbench.
- Task-to-run dispatch flow.
- Live run pane with approvals.
- Relationship/trace pane for selected run.
- Completion review pane.

## Symphony-Specific Acceptance

Fulcrum must document and test both roles:

- Implementer: consumes upstream `SPEC.md` semantics for workflow configs, issue snapshots, worker lifecycle, app-server events, tracker updates, retry/reconciliation, cleanup, tests.
- Provider: exposes project/context/workspace/docs/memory/artifacts/runs in a shape that Symphony-style orchestrators can consume without losing local-first graph links.

Minimum tests:

- Spec lock test compares latest fetched upstream SHA to committed lock or fails with clear update workflow.
- Conformance test maps each upstream §17 and §18 bullet to pass/fail/explicit non-applicability.
- Fixture run stores strict issue snapshot, workflow config id, workspace key/root, app-server session ids, event ids, artifacts, memory candidates, and audit rows.
- Web/CLI/TUI assertions prove those same ids are visible.

## Agent UX Completion Gate

End-to-end tests must start from a task, dispatch a no-sandbox local run, capture a trace/artifact/memory candidate, verify relationships in web, verify JSON via CLI, and inspect same run in TUI.
