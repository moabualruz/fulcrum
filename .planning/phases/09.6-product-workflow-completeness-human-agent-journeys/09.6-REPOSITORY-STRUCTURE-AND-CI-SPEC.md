# Repository Structure & CI Optimization Spec

**Created:** 2026-05-16
**Status:** proposed — awaiting user approval before implementation
**Context:** Phase 9.6 Priority 1 cleanup revealed scattered test locations, inconsistent service layouts, and CI running 25 sequential stages with duplicate test runs. This spec defines the canonical structure and CI strategy.

## Design Premise

Fulcrum is a monorepo that deploys as ONE NestJS process today. Each bounded service must be self-contained enough to extract to its own repo/process later. The structure must make extraction a mechanical task (add package.json, switch tsconfig alias to workspace dep), not an architectural migration.

## Current Problems

| Problem | Impact |
|---|---|
| 6 services have tests in BOTH `tests/<svc>/` AND `services/<svc>/src/` | Unclear where to add new tests, duplicated test setup |
| 15 orphan test dirs under `tests/` with no matching service | Stale migration artifacts, confusing navigation |
| `platform-core` is 581 files (god service) | Single change rebuilds everything, extraction impossible |
| CI runs 25 sequential stages (~7 min) | No parallelism, no affected-file filtering |
| `coverage:root` re-runs ALL root tests | Doubles test time |
| `web:test` + `coverage:web` runs web tests twice | Triples web test time |
| No `bun test --changed` usage | Every CI run tests everything, even for 1-file changes |

## Rules

### Service Internal Layout (every service follows this exactly)

```
services/<name>/src/
  <name>.module.ts          # NestJS module: imports, providers, exports
  index.ts                  # barrel re-export of module + public types

  domain/                   # pure TS: entities, value objects, events, errors
  application/              # use cases: services, commands, queries, ports
    *.test.ts               # unit tests CO-LOCATED beside source
  infrastructure/
    database/
      entities/             # TypeORM @Entity classes
      repositories/         # custom TypeORM repositories (@Injectable)
      migrations/           # TypeORM migration classes for THIS service
    external/               # third-party API clients (optional)
  interface/
    http/
      *-public-api.controller.ts
      dto/                  # Zod request/response schemas
    events/                 # domain event listeners (optional)
```

### Test Organization

| Type | Location | Naming | CI Tier |
|---|---|---|---|
| Unit (pure logic, mocked deps) | beside source in `services/<svc>/src/` | `*.test.ts` | 2 |
| Integration (DB, multi-service) | `tests/<svc>/` | `*.integration.test.ts` or `*.test.ts` | 3 |
| Architecture/boundary guards | `tests/architecture/` | `*.test.ts` | 1 |
| API (HTTP-level) | `tests/api/` | `*.test.ts` | 3 |
| CLI surface | `tests/cli/` | `*.test.ts` | 3 |
| TUI surface | `tests/tui/` | `*.test.ts` | 3 |
| Web component/route | `apps/web/tests/` | `*.test.ts` | 3 |
| E2E (full stack) | `tests/e2e/` | `*.test.ts` | 4 |
| Acceptance/UAT | `tests/acceptance/` | `*.test.ts` | 4 |

**Rule:** No test file should exist in both `tests/<svc>/` and `services/<svc>/src/` for the same behavior. Unit tests go beside source. Integration tests go under `tests/`.

### Dirs to Delete (orphans from pre-migration)

```
tests/application/          → move remaining to tests/<owning-service>/ or delete
tests/services/             → move remaining to tests/<owning-service>/ or delete
tests/platform/             → move to tests/platform-core/
tests/docs/                 → move to tests/knowledge-workspace/
tests/init/                 → move to tests/platform-core/
tests/local-startup/        → move to tests/platform-core/
tests/scripts/              → move to tests/architecture/ or delete
tests/infrastructure/       → move to tests/architecture/
tests/web/                  → move to apps/web/tests/ or tests/knowledge-workspace/
```

### Dependency Direction (enforced by boundary tests)

```
domain/ ← application/ ← infrastructure/
                        ← interface/

interface/ → application/ (never → infrastructure/ directly)
application/ → domain/ (never → infrastructure/ directly, use ports)
```

For pragmatic DDD at current scale: `application/` MAY import from `infrastructure/database/repositories/` directly (skip port indirection). This is acceptable until a service extracts.

## CI Strategy

### Current: 25 sequential stages, ~7 min, full suite every run

### Target: 4 tiered stages, ~2 min for PRs, full suite on main/nightly

```
just ci-fast                        # PR check: affected-only
  Stage 1: LINT (parallel, <15s)
    bun -e <typecheck-script>
    bun test tests/architecture/
  Stage 2: AFFECTED UNIT (<60s)
    bun test --changed=origin/main --parallel services/
  Stage 3: AFFECTED INTEGRATION (<90s)
    bun test --changed=origin/main --parallel tests/
  Stage 4: BUILD
    bun run scripts/build-all.ts

just ci                             # main/nightly: full suite
  Stage 1: LINT (same)
  Stage 2: ALL UNIT
    bun test --parallel services/
  Stage 3: ALL INTEGRATION
    bun test --parallel tests/
  Stage 4: BUILD + WEB
    bun run scripts/build-all.ts
    cd apps/web && bun run build && bun run check
  Stage 5: E2E (optional, nightly)
    bun test tests/e2e/ tests/acceptance/
```

### Key Eliminations

| Eliminated | Reason |
|---|---|
| `coverage:root` | Re-ran all tests. Coverage computed during Stage 2+3 with `--coverage` flag |
| `coverage:web` | Re-ran web tests. Combined with `web:test` |
| `symphony:lock` + `symphony:conformance` | Folded into Stage 2 (they're just `bun test` on specific files) |
| `trpc:permissions` | Folded into Stage 2 |
| `license-audit` + `ci:codegen` + `ci:schemas` | Folded into Stage 1 or run only on main |
| `web:install` | Already installed by root `bun install` |

### Bun Features to Use

| Feature | Command | Where |
|---|---|---|
| Affected-only | `bun test --changed=origin/main` | PR CI |
| Parallel files | `bun test --parallel` | All stages |
| Sharding | `bun test --shard=1/4` | CI runners (future) |
| Path filter | `bun test services/` | Tier 2 only |

## platform-core Split Plan

At 581 files, `platform-core` is a god service. Split candidates:

| Candidate | Files | Move to |
|---|---|---|
| `application/feature-flags/` | ~15 | New `services/feature-flags/` OR keep (small) |
| `application/backup/` | ~10 | Keep (cross-cutting infra) |
| `application/telemetry/` | ~8 | Keep (cross-cutting infra) |
| `application/secrets/` | ~12 | Keep (cross-cutting infra) |
| `application/skills/` | ~20 | New `services/skill-registry/` |
| `application/jobs/` | ~8 | Keep (infra) |
| `application/agent-hooks/` | ~15 | Move to `execution-orchestration` |
| `application/runtime/` | ~15 | Keep (bootstrap infra) |
| `infrastructure/application-database/` | ~200+ | This is the real blocker — entities/repos for ALL services lived here before the split. Audit what's left. |

**Decision needed:** How aggressively to split platform-core. Minimum viable: move agent-hooks and skills out. Maximum: split into platform-core (DB+config+health only) + skill-registry + observability.
