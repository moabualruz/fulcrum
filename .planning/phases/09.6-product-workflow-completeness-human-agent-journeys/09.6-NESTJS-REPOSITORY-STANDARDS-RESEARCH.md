## Research Findings

NestJS standards are feature-module centric. Official NestJS docs say closely related controllers and services should be grouped into feature modules, and a module's exported providers are its public interface. For Fulcrum this means each bounded service must expose Nest modules and providers, not scattered route registrars or ad hoc adapters.

NestJS monorepo mode puts runnable projects under `apps/**` and reusable components in library-style projects. It also warns that conversion relies on canonical Nest structure. Fulcrum should use `apps/server` as the Nest application and `services/**` as library-like bounded services that export modules/providers. CLI, TUI, web, and desktop stay separate runnable apps.

NestJS database docs support choosing one database abstraction and using the corresponding Nest integration. Since the user selected NestJS defaults and asked for TypeORM, the final server stack is `@nestjs/typeorm` + `typeorm` + `pg` + PGlite test/local bridge. Feature modules register entities via `TypeOrmModule.forFeature(...)`; persistence helpers live in service infrastructure, not app surfaces.

NestJS validation and OpenAPI are decorator/class based. DTOs should be concrete classes with `class-validator` decorators, global `ValidationPipe` should be enabled with whitelist/transform settings, and OpenAPI should be generated through `@nestjs/swagger` decorators and `SwaggerModule`.

TypeORM migration docs generate TypeScript migration files by default and execute ordered migrations through `migration:run` with a `DataSource`. Fulcrum should remove tracked `.sql` migrations and use TypeScript migration classes/modules only.

npm workspace docs define workspaces as root-managed nested packages. Fulcrum can keep Bun as the runner, but the repo shape should still behave like a clean workspace: root-owned package metadata, explicit workspace roots, no hidden package-manager islands unless a package truly needs independent release/build config.

GitHub README guidance says README, license, citation, contributing, and code of conduct communicate project expectations, and GitHub surfaces README files from `.github`, root, then `docs`. GitHub contribution guidance and CODEOWNERS guidance support keeping contributor expectations, ownership, and review routing in standard repository files. For Fulcrum, generic rules belong in `rules/AGENTS.md` and memory; project-specific architecture belongs in root `AGENTS.md`; public user/developer onboarding belongs in `README.md`, `docs/**`, and optional `.github/**`.

## Fulcrum Decisions

### Final Backend Stack

- Runtime framework: NestJS only.
- HTTP adapter: Express through `@nestjs/platform-express`.
- API description: OpenAPI through `@nestjs/swagger`.
- Validation: `class-validator` + `class-transformer` DTO classes and a global Nest `ValidationPipe`.
- Configuration: `@nestjs/config` loaded in the root application module with typed/namespaced config and validation.
- ORM: TypeORM only through `@nestjs/typeorm`.
- Production DB: PostgreSQL using `pg`.
- Local/test DB: PGlite through a TypeORM-compatible bridge or socket adapter.
- Removed final-state dependencies: `hono`, `@hono/zod-openapi`, `@mikro-orm/*`, `kysely`, legacy Kysely/PGlite drivers, and server-side tRPC routers once equivalent Nest controllers/clients exist.

### Final Repository Shape

### Clean Code Rules

- Code names describe responsibility/value/behavior, never phase, goal, provenance, or inspiration.
- Runtime code and tests do not use third-party product names unless integrating that product directly.
- Server features are Nest modules/controllers/providers/DTOs, not standalone route registrars.
- Web, CLI, and TUI are invocation/visualization only; they call generated clients, HTTP APIs, or application-service facades.
- No direct ORM imports or query builders in app surfaces.
- No `.sql` migration files. Migration logic is TypeScript TypeORM classes/modules.
- No dual ORM runtime. TypeORM is the only accepted ORM for this target.
- No parallel HTTP framework. NestJS is the only accepted server API framework for this target.
- No duplicate dependency for the same responsibility without a written removal owner and deletion criteria.
- No empty runtime directories or old compatibility folders after the workflow value is verified and migrated.

## Required Goal Updates

- Acceptance criteria must include no Hono runtime, no MikroORM/Kysely runtime, no `.sql` migrations, and no duplicated API framework after final cutover.
- Copy/adapt completeness must be audited by upstream screen, workflow, model, and test cluster, not only by broad workflow labels.
- Project cleanup is not cosmetic: it is a release blocker for the active goal.
- Documentation split:
  - Generic cross-project rules: memory and `rules/AGENTS.md`.
  - Fulcrum-specific project architecture: root `AGENTS.md` and phase tracker.
  - Research evidence: this file and linked planning docs.
