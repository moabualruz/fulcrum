## Product Pattern: Jira

Jira is strongest at configurable work hierarchy, workflow state, board/backlog/sprint planning, development links, reports, and timeline dependency planning.

Fulcrum must match these exact patterns:

- **Project as primary container:** every board, backlog, sprint, timeline, report, release/status surface belongs to a project or explicit all-project portfolio.
- **Issue hierarchy:** initiative/capability/epic/story/task/bug/subtask must be visible as parent/child relationship, not only as arbitrary links.
- **Board configuration:** board columns are status mappings; board swimlanes and quick filters are saved views over the same task data.
- **Backlog vs board:** backlog is intake/prioritization; board is execution state. Same work item can move from backlog to sprint/cycle to board without duplication.
- **Timeline:** roadmap/timeline maps higher-level work and dependencies; it must expose blockers, dates, progress, and dependency health.
- **Development panel:** task detail should expose repo branch, commits, PRs/diffs, check/run status, and artifact outputs.
- **Reports:** burndown, velocity, cumulative flow, cycle time, WIP, scope change, workload, forecast must update from actual project task state.
- **Automation:** rule triggers are entity lifecycle events: issue transitioned, comment added, sprint started/closed, version/release changed, build/deployment changed.
- **Confluence integration:** a Jira issue shows linked Confluence pages; Confluence pages embed issue tables/reports/boards and can create work items from highlighted text.

Fulcrum translation:

- `Project` detail must show work, docs, repo, runs, artifacts, memory, context, automation, and reports.
- `TaskDetailPanel` must be Jira issue view equivalent: fields, hierarchy, linked docs, repo activity, runs, artifacts, comments, watchers, automation, audit.
- `Board`, `Backlog`, `Sprint`, `Calendar`, `Gantt`, `Reports` are views over `Task` + `SavedView`, not standalone screens.

## Product Pattern: Linear

Linear is strongest at speed, low navigation overhead, contextual command palette, clean hierarchy, triage, cycles, project pages, dynamic views, keyboard-first execution.

Fulcrum must match these exact patterns:

- **Team/project pages:** default pages aggregate issues, projects, cycles, views, and graphs.
- **Triage:** incoming work is reviewed before backlog/cycle acceptance. Fulcrum must use this for user notes, imported issues, agent follow-ups, and automation-created work.
- **Display options:** every view exposes display fields and grouping/order. Fulcrum must persist per-project saved view settings for board/list/table/calendar/Gantt/report.
- **Parent/sub-issues and relations:** blocked/blocking/related/duplicate links must be typed and visible inline.
- **Cycles:** sprint/cycle shows current work, completed/rolled-over work, estimates, workload, progress, and graphs.
- **Projects:** project overview includes details, issues, progress graphs, timeline/date ranges, related initiatives, and docs/links.
- **Keyboard-first UX:** command palette creates/updates/issues/projects/docs and navigates based on current context.

Fulcrum translation:

- Web topbar/palette must know active project and selected entity.
- TUI must start at current project/work queue, not domain list.
- CLI must have active project defaults and workflow commands, not only domain CRUD.

## Product Pattern: Plane

Plane is closest to Fulcrum’s local-first/open-source posture. It combines project management, pages/wiki, cycles/modules, views, dashboards, webhooks, API, and MCP.

Fulcrum must match these exact patterns:

- **Workspace -> projects -> work items:** workspace houses multiple projects; projects hold work items, cycles, modules, pages, views, intake, dashboards.
- **Cycles and modules:** cycles are timeboxes; modules are thematic/product areas. Fulcrum needs both sprint/cycle and module/component grouping.
- **Pages/wiki:** pages are project knowledge beside work, not separate docs CRUD.
- **Multiple views:** list, board, spreadsheet/table, calendar, Gantt/timeline all work from the same project item set.
- **Intake:** incoming requests move through review before accepted work.
- **Dashboards:** aggregate workload, progress, estimates, cycle/module health.
- **API/webhooks/MCP:** all product actions available to agents and automation with structured tool/API contracts.

Fulcrum translation:

- Add `module` or use existing components/labels/custom fields with first-class module view.
- Treat docs/pages as project-space knowledge with backlinks.
- Agent tools should operate on projects, work items, pages/docs, cycles, modules, artifacts, memory candidates, and context bundles.

## Product Pattern: GitHub Issues + Projects

GitHub is strongest at developer-native work: issues, sub-issues, PR/commit references, milestones, project fields, saved views, automations, insights, and CLI/API access.

Fulcrum must match these exact patterns:

- **Issue sidebar as relationship hub:** assignee, labels, milestone/project, linked PRs, development status, custom fields, sub-issues.
- **Saved views:** table/board/roadmap views with fields/filters/sorts.
- **Sub-issues:** progress indicators roll up child issue state.
- **Milestones:** time-bound or release-bound grouping across issues.
- **Markdown references:** docs/issues/PRs link bidirectionally through references.
- **CLI-first parity:** GitHub exposes issue/project operations via CLI/API; Fulcrum CLI must do same with JSON.

Fulcrum translation:

- Work item detail must show project fields, labels, sprint/milestone, children progress, linked run/artifact/diff, and repo path.
- Search results must include project/task/run/doc/artifact/memory context.

## Product Pattern: Confluence + Wikis + Notion

Confluence is strongest at structured spaces, page hierarchy, templates, comments, Jira embedding, reports, and knowledge lifecycle. GitHub/GitLab Wikis are strongest at repo-local documentation with sidebar/footer navigation. Notion is strongest at relational databases connecting tasks, docs, projects, decisions, and templates.

Fulcrum must match these exact patterns:

- **Project docs space:** every project has docs tree/space with homepage, sidebar tree, templates, backlinks.
- **Templates:** spec, ADR, runbook, meeting note, retro, incident, agent prompt, handoff, release note.
- **Work embedding:** docs can embed live task tables, board/report snapshots, run summaries, artifacts, memory entries.
- **Create work from docs:** highlight/section/action item becomes a task or follow-up.
- **Repo wiki mode:** project repo path can include docs/wiki folder; Fulcrum can sync or link it.
- **Backlinks/provenance:** docs link to tasks/runs/artifacts/memory and show incoming references.

Fulcrum translation:

- Docs cannot remain generic `/docs` CRUD. Project docs must be default, with global docs as portfolio/library.
- Agent outputs must be promotable into docs/memory with source refs.

## Product Pattern: LangSmith + Temporal + Agents SDK

Agent OS product quality requires observability and durable workflow patterns, not just a `runs` table.

Fulcrum must match these exact patterns:

- **Project -> trace -> run/span:** every agent run belongs to project/task/context; nested tool calls are timeline spans.
- **Threads/sessions:** multi-turn or resumed runs need thread/conversation identity.
- **Context bundle:** prompt, task, docs, repo state, memory, artifacts, skills, routing decisions are captured before run and reconstructable after.
- **Durable run state:** queued, started, heartbeat, blocked, waiting approval, retrying, failed, succeeded, cancelled.
- **Activities/tool calls:** separate fallible operations from orchestration state; display retries, errors, duration, inputs/outputs.
- **Replay/clone/debug:** prior run context can be cloned into a new run.
- **Memory candidate lifecycle:** extracted -> reviewed -> promoted/demoted -> used in future context with provenance.

Fulcrum translation:

- `RunDetail` must be trace/observability UI: timeline, transcript, tool calls, context, diff, artifacts, memory, audit, notifications, follow-up tasks.
- TUI run screen must supervise active runs with status, heartbeat, current step, details, cancel/retry/approve.
- CLI must expose `runs watch`, `runs context`, `runs artifacts`, `runs memory-candidates`, `runs retry/cancel/continue`.

## Anti-Patterns To Avoid

- Flat nav full of domain nouns.
- Global pages that silently ignore active project.
- Boards/tasks/docs/runs/artifacts/memory each having their own unrelated filters and IDs.
- Completion proof by page render tests.
- TUI as menu launcher only.
- CLI as generated CRUD only.
- Agent run as log record without task/context/repo/artifact/memory provenance.
- Memory as free-text snippets without source, scope, key/topic, confidence, and usage tracking.

## Phase 9.6 Product Bar

State-of-the-art Fulcrum must feel like:

- Jira/Linear/Plane for project workflow.
- Confluence/GitHub Wiki for project knowledge.
- GitHub Issues/Projects for developer-native links and CLI/API parity.
- LangSmith/Temporal for agent execution observability.
- MCP-ready local Agent OS for machine-accessible actions and context.
