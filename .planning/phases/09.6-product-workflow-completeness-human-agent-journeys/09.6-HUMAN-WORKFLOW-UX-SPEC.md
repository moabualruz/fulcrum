# Phase 9.6 Human Workflow and UX Spec

**Created:** 2026-05-08
**Audience:** Human operator using Fulcrum as a local-first Agent OS and project/work/documentation platform.

## Product Shape

Fulcrum must feel like one project workspace, not separate pages.

Primary hierarchy:

```text
Workspace -> Project -> Work item -> Run / Doc / Repo / Artifact / Memory / Automation
```

Global pages are portfolio views. Project pages are the default work surfaces.

Trace spine every human screen must preserve:

```text
workspace -> project -> repo/local path -> work item -> docs/context -> run -> artifacts/memory/follow-ups -> audit/reports
```

The UI must make this spine visible through breadcrumbs, relationship panels, activity timelines, and command actions. A user must never have to infer whether a board item, doc, run, memory entry, artifact, or automation belongs to a project.

## Core UX Contract

| Surface | Primary Question It Answers | Required Adjacent Links | Required Actions |
|---|---|---|---|
| Workspace home | What projects need attention? | projects, active runs, blocked tasks, recent docs, alerts | create project, switch project, search, run doctor |
| Project dashboard | What is happening in this project? | repo, board, docs, runs, artifacts, memory, automation, reports | create task/doc/run, link repo, inspect context, view trace |
| Board/list/table/calendar/Gantt | What work exists and how is it moving? | task parents/deps, docs, runs, artifacts, memory, activity | create/update task, bulk move, dispatch run, link doc |
| Task detail | What context and execution history does this work item have? | project, repo, docs, deps, context bundles, runs, artifacts, memory, comments, audit | edit, link, dispatch, preview context, accept run proposals |
| Docs space/page | What knowledge exists and where is it used? | project tree, backlinks, tasks, runs, artifacts, memory, versions | edit, template, link, promote memory, cite in context |
| Run detail | What did the agent do and what should happen next? | task, context bundle, route, repo/workspace, live session, transcript, diff, artifacts, memory candidates, audit | approve, cancel, retry, continue, accept proposals |
| Artifact detail | What output exists and where did it come from? | project, task, run, repo path/commit, docs, memory | preview, archive, link, promote, compare |
| Memory review | What facts/decisions are reusable and trustworthy? | source doc/run/task/artifact, scope, last-used contexts | accept, reject, demote, supersede, inspect provenance |

## Human Journey H1: First Local Workspace

Goal: get from empty machine to usable local product.

Required steps:

1. Start local server/web/CLI/TUI with default local state.
2. Doctor shows no blocking errors.
3. Create or select workspace/org.
4. Create first project.
5. Add local repository path during project setup.
6. Confirm project dashboard shows repo status, board status, docs status, run status, and next actions.
7. Confirm trace spine exists: workspace id, project id, repo id/path, default board id, docs space id, audit event ids.

Detailed UX:

- Web first-run opens a workspace setup screen with project name, slug, local path picker/manual path field, and default workflow template.
- After create, user lands on project dashboard, not global CRUD pages.
- Project dashboard top area shows project name, local path, git branch/dirty state, doctor status, and active workflow mode.
- Dashboard body exposes work queue, docs, runs, artifacts, memory, automation, and reports as integrated project modules.
- Empty project states are step-specific: link repo, create task, create spec doc, run context preview, dispatch first agent.
- CLI mirrors same path: create workspace/project/repo link in one command, then `fulcrum project use`.
- TUI first screen shows current project setup if none exists, then project workbench.

Trace and data requirements:

- `project.created` event stores workspace/project/actor ids.
- `repo.linked` event stores project/repo/local path/workspace root.
- Project API response includes `links.repo`, `links.board`, `links.docsSpace`, `links.audit`.
- Doctor output links to project/repo checks, not only global health.

Acceptance:

- Web: `/projects/new` requires or strongly prompts local repo path; resulting project detail shows repo path and sync status.
- CLI: `fulcrum projects create --name ... --repo-path ... --json` creates same project and repo link.
- TUI: first-run screen offers "Create project" and "Link local repo"; result appears in project dashboard.
- Server: same project/repo rows visible through tRPC/API queries.

## Human Journey H2: Plan Work Like Jira/Linear/Plane

Goal: manage real work under a project.

Required steps:

1. Select project from persistent selector.
2. Create epic/initiative or project milestone.
3. Create tasks under that parent.
4. Move tasks between backlog, board columns, sprint/cycle, list/table, calendar, and Gantt.
5. Set status, priority, assignee, labels, due date, dependencies, custom fields.
6. See reports update from real data.
7. Inspect trace from any card/row to see docs, runs, artifacts, memory, repo paths, and audit events tied to the work item.

Detailed UX:

- Board swimlanes support status, assignee, cycle/sprint, milestone, and parent grouping.
- List/table supports configurable columns for priority, status, labels, dates, estimate, dependencies, linked docs, open runs, artifacts, and blocked state.
- Calendar uses due/start dates from same task data, not a separate calendar object.
- Gantt uses dependencies and parent/milestone relationships from same task graph.
- Task quick-create can attach doc template, repo path/branch, and suggested agent workflow.
- Task detail keeps a dense top summary: status, priority, owner, project, parent, dependencies, cycle, due date, branch/path, run state.
- Right relationship rail shows docs, context bundles, runs, artifacts, memory, comments, audit, and automations.
- Reports derive from task/run/audit data: throughput, blocked work, agent success rate, artifact volume, stale docs, memory candidates pending review.

Trace and data requirements:

- Task create/update emits audit event with causation id.
- Task rows expose linked docs count, run count/status, artifact count, memory count, dependency count.
- Task detail can call one aggregate endpoint, not stitch unrelated CRUD responses in component code.
- Saved views persist project scope, filters, grouping, columns, and sort.

Acceptance:

- Every work view has project selector or clear project context.
- Board/list/table/calendar/Gantt/report views share same filters and saved views.
- Task detail shows parent/subtasks, dependencies, linked docs, linked repo/branch, runs, artifacts, memory, comments, activity, watchers.
- CLI can create/update/list/filter tasks with project scope and JSON.
- TUI can navigate project -> board/list -> task detail -> update status/priority/dependency.

## Human Journey H3: Document Work Like Confluence/GitHub Wiki

Goal: make docs part of work, not a separate CRUD area.

Required steps:

1. Open project docs space.
2. Create doc from template: spec, ADR, runbook, meeting note, retro, agent prompt, handoff.
3. Link doc to task/project/repo/run/artifact.
4. Edit doc, see backlinks and version history.
5. Promote doc sections to memory/context candidates.
6. Run context preview shows which doc sections would be included and why.
7. Task/run/artifact pages show doc backlinks with version refs.

Detailed UX:

- Project docs space has tree, recent pages, templates, backlinks, orphan pages, and stale pages.
- Templates include SPEC, ADR, PRD, runbook, meeting note, retro, agent prompt, handoff, incident report.
- Doc page header shows project, path, owner, linked tasks/runs/artifacts/memory, version, last edited.
- Backlinks distinguish explicit links, mentions, context inclusions, artifact citations, and memory provenance.
- Version history supports compare and restore if existing storage model allows; otherwise Phase 9.6 must specify migration.
- Doc editor/sidebar can link selected section to task, artifact, run, memory candidate, or context bundle.
- GitHub wiki pattern: tree/path semantics, markdown-friendly editing, backlinks.
- Confluence pattern: page tree, templates, rich relationship metadata, version/activity.

Trace and data requirements:

- `doc.linked` event records doc id, linked entity kind/id, project id, actor, source section.
- Context bundle stores doc version/section refs.
- Memory candidate sourced from doc stores exact source doc/version/section.

Acceptance:

- Docs have workspace/project/task/run/artifact scope.
- Docs tree exists per project; global docs are separate.
- Task detail shows linked docs; doc detail shows linked tasks/runs/artifacts.
- CLI supports doc CRUD, linking, versions, and project scope.
- TUI supports project docs tree, read view, create/edit lightweight doc, link doc to task.

## Human Journey H4: Run Agents From Work

Goal: dispatch and supervise agents from concrete work items.

Required steps:

1. Select a task.
2. Inspect generated context bundle before dispatch.
3. Choose agent/profile/model/routing rule.
4. Start run.
5. Watch run status, transcript, tool timeline, workspace diff, artifacts, memory candidates, and follow-up tasks.
6. Approve/retry/cancel as needed.
7. Merge accepted output into docs/memory/task status/artifacts.
8. Verify Symphony-compatible trace: workflow config, strict issue snapshot, workspace key/root, app-server session, retry entry, cleanup state.

Detailed UX:

- Start run button lives on task detail, board cards, command palette, docs, and automation rules, but all paths resolve to a project/task context.
- Context preview is inspectable before dispatch: task fields, docs, memory, repo slices, prior runs, artifacts, skills/rules, exclusions, token estimates.
- Routing screen shows selected agent/profile/model/workflow, matched rule, alternatives, cost/risk notes, required approvals, workspace safety mode.
- Live run page has panes for overview, transcript, tool timeline, diff, artifacts, memory candidates, approvals, context, and audit.
- Pending approvals are actionable in Web and mirrored in CLI/TUI watch flows.
- Retry explains prior failure, backoff/retry policy, reused context, changed workspace state, and new attempt number.
- Run completion creates explicit proposals: status update, follow-up tasks, doc changes, memory candidates, artifact retention changes.

Trace and data requirements:

- Run start stores project id, task id, repo id, context bundle id, routing decision id, workflow config id, actor id.
- App-server events store event id, turn id, tool call id, approval/user-input status, tokens, timestamp.
- Diff/artifacts store source run attempt and repo path/commit if available.
- Accepted proposals emit audit rows and update dashboard/report metrics.

Acceptance:

- Task detail has "Start run" with context preview.
- Run detail links back to task, project, repo, docs, context bundle, artifacts, and memory candidates.
- Artifacts are visible from run, task, project artifact view, and search.
- CLI can dispatch, watch, cancel, retry, list artifacts, and inspect context.
- TUI has a run supervision workflow, not only a list.

## Human Journey H5: Search, Memory, and Context

Goal: find and reuse knowledge across projects and runs.

Required steps:

1. Search for task/doc/run/artifact/memory by project.
2. Inspect memory provenance.
3. Promote/demote memory from run/doc/task.
4. Assemble context for a task and preview exact slices.
5. Use context in a run and verify trace provenance.
6. From search result, jump to trace spine and adjacent entities.

Detailed UX:

- Search defaults to current project with obvious `All projects` toggle.
- Results group by work, docs, runs, artifacts, memory, repos, automations.
- Each result row includes project, source entity, linked task/run/doc, last activity, and reason matched.
- Memory review shows candidate queue, accepted memory, superseded memory, rejected memory, and last-used contexts.
- Context preview explains included, excluded, stale, conflicting, and missing sources.
- Memory promotion requires scope selection: workspace, project, task, repo, doc, or run.

Trace and data requirements:

- Memory entries are never anonymous; every entry has source kind/id/version/section when applicable.
- Context bundles store inclusion reason and source refs for every slice.
- Search index stores entity kind/id/project and relationship metadata sufficient to render results without orphan UI.

Acceptance:

- Search results are relational: item kind, project, linked task/run/doc, last activity.
- Memory entries show source, confidence, scope, and linked entities.
- Context preview explains why each memory/doc/run/artifact/repo slice was included.
- CLI and TUI expose same search/memory/context workflows.

## Human Journey H6: Automation and Notifications

Goal: automate project operations and know what changed.

Required steps:

1. Create notification rule scoped to project/task/run/artifact.
2. Configure automation: on task status change, on run success/failure, on artifact created, on memory candidate.
3. Trigger event.
4. See notification, audit row, and automation result.
5. Inspect rule trace from trigger event to affected entity and output action.

Detailed UX:

- Automation rules are configured inside project settings and optionally reusable from workspace templates.
- Rule builder supports trigger, condition, action, dry-run, enabled state, actor policy, notification targets.
- Supported triggers for Phase 9.6: task status changed, run started/completed/failed/blocked, artifact created, memory candidate created, doc linked/stale, repo dirty/clean.
- Notification center groups by project and entity, with direct links to task/run/artifact/memory/doc.
- Audit panel shows human, agent, automation, and system actors differently.

Trace and data requirements:

- Every automation execution stores trigger event id, rule id, action ids, affected entity ids, actor policy, result.
- Notifications store source event id and target entity id.

Acceptance:

- Notifications link to the entity that caused them.
- Audit trail shows human vs agent actor.
- Automation rules are project-scoped and testable.
- CLI/TUI can list, create, test, enable/disable rules.

## Web UX Requirements

- Replace flat nav with project-first shell.
- Persistent project selector in topbar or sidebar, visible on all work pages.
- Project dashboard becomes hub: board, backlog, docs, repos, runs, artifacts, memory, context, automation, reports.
- Global pages must state when they are showing "all projects" and offer project filter.
- Task, doc, run, artifact, repo, and memory details must include relationship panels.
- Empty states must suggest the next workflow step, not generic "no items".
- Command palette must operate on current project and offer contextual actions.
- Trace drawer available on project/task/doc/run/artifact/memory rows and detail pages.
- Breadcrumbs must reflect current trace level, for example `Workspace / Project / Task / Run`.
- Each detail page must expose an activity timeline filtered to that entity plus causally related events.
- Visual hierarchy: project context first, workflow object second, relationship/action panels third.
- Web tests must assert IDs/links are shared across dashboard, task detail, run detail, docs, artifacts, memory, and audit.

## CLI UX Requirements

- Every command accepts `--project <id|slug>` or uses active project.
- `fulcrum project use <slug>` sets active project for CLI/TUI.
- Workflow commands exist:
  - `fulcrum work init`
  - `fulcrum work plan`
  - `fulcrum work run`
  - `fulcrum work inspect`
  - `fulcrum context preview`
  - `fulcrum memory promote`
  - `fulcrum trace show`
  - `fulcrum runs watch`
  - `fulcrum artifacts inspect`
  - `fulcrum docs link`
- JSON output must include linked entity IDs.
- JSON output must include `links`, `trace`, or both for project/task/doc/run/artifact/memory commands.
- Active project resolution must be shown in `--json` metadata so automation can prove scope.

## TUI UX Requirements

- First screen is "Current Project", not domain nav.
- Left pane: project/work queue. Center: selected workflow. Right/detail: linked docs/runs/artifacts/memory.
- Command palette: create task/doc/run, switch project, link repo, search, promote memory.
- TUI must support at least the critical human journeys H1-H5.
- Trace drawer/pane shows adjacent entities and event timeline.
- Live run screen shows pending approvals, transcript cursor, artifacts, diff, memory candidates, and context bundle.
- TUI tests or snapshots must prove project selector, task relationship pane, run supervision pane, and trace drawer exist.

## Human UX Completion Gate

Playwright and CLI/TUI tests must verify H1-H6 end-to-end on fresh local state.

Minimum fixture:

1. Create workspace.
2. Create project with repo local path.
3. Create board/cycle/task/dependency.
4. Create/link doc.
5. Preview context.
6. Dispatch local no-op or fixture agent run.
7. Capture transcript/tool event/artifact/memory candidate/audit.
8. Verify same entity ids and backlinks in Web, CLI JSON, and TUI.
