## External Product Patterns

### Project Management

Jira Cloud structures work around projects, boards, work items, workflows, sprints, reports, timelines, project navigation, development integrations, dashboards, and keyboard workflows. Atlassian's docs group project setup, board configuration, backlog/sprint management, reports, timeline, work item fields, repository/development links, dashboards, and command palette/keyboard actions as one connected system, not separate CRUD pages. Source: https://support.atlassian.com/jira-software-cloud/docs/use-jira-work-management-for-project-management/

Linear structures work around teams, issue workflows, projects, cycles, views, triage, issue relations, display options, parent/sub-issues, notifications, and timeline planning. Source: https://linear.app/docs

Exact Linear UX patterns to match:

- Timeline is for high-level project planning and keeps roadmap planning separate from granular implementation issues. Fulcrum timeline/roadmap views must live at project/initiative level, not as another flat task list. Source: https://linear.app/docs/timeline
- Display options are per-view and include issue ID, priority, status, labels, project, cycle, assignee, estimate, links, time in status, pull requests, and commits. Fulcrum board/list/table/calendar/Gantt/report views must share configurable display properties and always carry project/cycle/task relation fields. Source: https://linear.app/docs/display-options
- Triage is a first-class flow before accepting issues into backlog/cycles. Fulcrum needs inbox/triage for human notes, incoming automation, and agent-generated follow-up tasks. Source: https://linear.app/docs/conceptual-model

Plane positions projects, work items, cycles, modules, pages/docs, views, dashboards, estimates, APIs, webhooks, integrations, and MCP as one workspace. Source: https://docs.plane.so/ and https://plane.so/open-source

Exact Plane UX patterns to match:

- Workspace contains projects, work items, cycles, modules, pages, five layout views, intake, dashboards, estimates, REST API, and webhooks.
- Pages are not a separate app; they are project knowledge beside work items, cycles, and modules.
- Command-K and keyboard-first actions are product-level behavior, not only search.

GitHub Issues and Projects combine issues, sub-issues, milestones, project fields, saved views, insights, pull request links, workflows, and API/webhook surfaces. Source: https://docs.github.com/en/issues

Jira hierarchy patterns to match:

- Default hierarchy: Epic -> Story/Task/Bug -> Sub-task, with workflows per issue type. Fulcrum must support initiative/epic/task/subtask with explicit parent-child relations, not flat tasks only. Source: https://www.visor.us/blog/thinking-tactically-about-jira-issue-hierarchy/
- Boards, list, calendar, timeline, approvals/forms are views over workflow state, not separate entities. Fulcrum board/list/table/calendar/Gantt/report views must share saved filters and project scope.

Implication for Fulcrum:

- `Project` must be the main work container.
- Boards, backlog, list, table, calendar, Gantt, reports, repos, docs, runs, artifacts, memory, context, and automations must be project-scoped by default.
- Global surfaces can exist, but must be portfolio/search/admin views over project-scoped data.
- Task cards must expose linked docs, repo/branch, agent runs, artifacts, memory/context, comments, dependencies, and automation state.
- Navigation should lead with "what am I working on?" and "what changed?" rather than domain silos.

### Documentation Management

Confluence organizes knowledge through spaces, content items, pages, whiteboards, databases, files, search, lifecycle controls, and automation. Atlassian describes Confluence as a single source of truth for team work. Source: https://support.atlassian.com/confluence-cloud/docs/create-and-organize-work-in-confluence-cloud/

GitHub Wikis organize repository documentation around pages with sidebar/footer navigation and edit flows. Source: https://docs.github.com/en/communities/documenting-your-project-with-wikis

Exact documentation UX patterns to match:

- Confluence spaces have page hierarchy and permissions; Jira integration links/issues/filters/boards into docs. Fulcrum docs need project spaces, page hierarchy, backlinks, linked tasks/runs/artifacts, and templates for specs, ADRs, runbooks, decisions, retros, agent prompts, and handoffs. Source: https://klero.ai/resources/confluence
- Confluence software project spaces appear with Jira linkage, which maps to Fulcrum project docs automatically linking task boards, runs, and repo state. Source: https://downloads.atlassian.com/software/confluence/downloads/documentation/Confluence_6-0_CompleteGuide_PDF.pdf

Implication for Fulcrum:

- Docs must be attached to workspace, project, task, run, artifact, repo, or decision scope.
- Docs must backlink to tasks/runs/artifacts/memory and be discoverable from those surfaces.
- Project docs need a tree/space model and templates for specs, ADRs, runbooks, decisions, retros, agent prompts, and handoffs.
- Agent output should be promotable into docs or memory, not remain isolated under run detail pages.

### Agent Runs, Context, Memory, Observability

LangSmith models agent observability as projects containing traces, traces containing runs/spans, and threads linking multi-turn conversations. Source: https://docs.langchain.com/langsmith/observability-concepts

Temporal models durable execution around workflows, activities, workers, task queues, visibility, and operational UI. Source: https://docs.temporal.io/

Exact agent/orchestration UX patterns to match:

- LangSmith projects -> traces -> runs/spans -> threads maps to Fulcrum project -> task -> agent run -> trace/tool timeline -> transcript/artifacts/memory. Source: https://docs.langchain.com/langsmith/observability-concepts
- Temporal workflow/activity/task queue/worker visibility maps to Fulcrum orchestration routes, active run supervision, retries, cancellation, heartbeats, and audit. Source: https://docs.temporal.io/

Implication for Fulcrum:

- An agent run must be tied to a project/task/repo/doc/context bundle, not just a row in `agent_runs`.
- Run detail should show prompt, context bundle, tool timeline, transcript, diff, artifacts, decisions, memory writes, follow-up tasks, retries, approvals, and final status.
- Context assembly must be inspectable before dispatch and reconstructable after dispatch.
- Memory must be promoted from agent traces/docs/tasks and then used in later context bundles with provenance.

- `apps/web/src/routes/projects/[id]/+page.svelte` has quick links to board/backlog/sprints/reports/repos/docs, but project-local workflow is not the dominant product shell.

Observed UX problem:

- The route tree contains many pieces but lacks a single hierarchy and workflow shell that makes relationships obvious.

- Tests often assert route rendering and elements, not complete workflows.

## Integration Model Required for Phase 9.6

Core graph:

```text
Workspace
  -> Project
    -> Local repos / remote integrations
    -> Work items: task / epic / initiative / bug / chore
      -> Board / backlog / sprint / list / table / calendar / Gantt / reports
      -> Docs / decisions / specs / runbooks
      -> Agent runs
        -> Context bundle
        -> Transcript / trace
        -> Artifacts / diff
        -> Memory candidates / decisions
        -> Follow-up tasks
      -> Notifications / audit / automations
```

Surface rule:

```text
Web = richest visual workflow.
CLI = same actions and data, scriptable and JSON-first.
TUI = same actions and data, keyboard-first supervision and daily operation.
Server/API = same application commands/queries, no separate product behavior.
```

## Completion Standard

Phase 9.6 is complete only when:

- Human can complete the full project-to-ship journey in web, verify via CLI, and supervise via TUI.
- Agent can complete the full dispatch-to-artifact-to-memory journey, with context and provenance visible.
- Doctor is green on a fresh local `FULCRUM_HOME`.
- Packaged server, web dev client, CLI, and TUI all start locally without hidden env workarounds.
- E2E tests encode those journeys and fail on disconnected CRUD.
