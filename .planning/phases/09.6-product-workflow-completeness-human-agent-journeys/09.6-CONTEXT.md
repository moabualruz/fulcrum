**Gathered:** 2026-05-08

<domain>
## Phase Boundary

Phase 9.6 rebuilds Fulcrum into one integrated local-first Agent OS product before Phase 10 can begin. Scope is a project-first workflow spine across Web, CLI, TUI, server/API, docs, memory, context, orchestration, artifacts, automations, notifications, reports, startup, doctor, and verification.

Primary product spine:

```text
workspace -> project hierarchy -> repo/local path -> work item -> docs/context
  -> agent run/live session -> artifacts/memory/follow-ups -> audit/notifications/reports
```

Global/domain CRUD is not a product goal. If old routes, commands, screens, schemas, or local state conflict with the product vision, they may be removed, rebuilt, or repurposed. Phase 9.6 must prove full human and agent journeys programmatically before final user UAT.

</domain>

<decisions>
## Implementation Decisions

### Product Scope And Hierarchy
- **D-01:** Fulcrum is strict project-first. Work, docs, runs, artifacts, memory, context, automations, reports, CLI, TUI, and Web flows require explicit project/subproject/root scope.
- **D-02:** `All projects` is an explicit portfolio/root context, not silent global fallback.
- **D-03:** Project hierarchy is first-class: workspace/root -> parent project -> subproject, with arbitrary depth supported. The default mental model and templates use root/project/subproject, but APIs and tests must not assume max depth.
- **D-04:** Represent hierarchy as one `projects` tree using `parent_id`, `kind`, `path`, `depth`, and inheritance configuration. Existing flat projects can migrate to root-level project nodes.
- **D-05:** Parent project views aggregate parent + descendants by default. Parent dashboards can operate on child work directly, but every mutation records the actual child target scope.
- **D-06:** Subprojects use selectable inheritance per module: repo, docs, memory, automations, reports, run policy, and context sources.
- **D-07:** Parent policy can lock inherited settings fine-grained per module/rule; otherwise child overrides win. UI/CLI/TUI/API must show inherited, overridden, and locked state.

### Full Spine First
- **D-08:** The first implementation slice is full spine first, not a thin demo.
- **D-09:** The first spine must cover setup -> repo -> hierarchy/work item -> docs -> context preview -> dispatch/run supervision -> artifact -> memory candidate/promotion -> audit/notification/report signal -> CLI JSON -> TUI workbench using same IDs.
- **D-10:** Build a template engine before hardcoding the first spine. The first canonical template is `Agent OS Software Project`.
- **D-11:** `Agent OS Software Project` seeds parent project, one subproject, repo link step, epic/task, full docs set, context policy, run workflow, automation, and reports. Setup preview can remove modules before creation.
- **D-12:** Local templates support both `FULCRUM_TEMPLATE.md` single-file format and directory format with `fulcrum-template.yaml` plus docs/tasks/scripts folders. Built-in TypeScript templates compile to the same normalized template schema.
- **D-13:** Templates may define full local automation: project tree, tasks, docs, views, automations, policies, context sources, run profiles, routing defaults, Symphony workflow refs, local scripts, hooks, and commands.
- **D-14:** Template trust combines signed/trusted sources with dry-run for executable effects. Trust modes are configurable: Manual, Assisted, Trusted, Full auto. Every executable action records trust mode, source, actor, dry-run/approval, and audit trace.

### Work Items And Task Detail
- **D-15:** Use these UX terms: Workspace, Project, Subproject, Work item, Task, Agent run/run, Trace, Template, Context bundle, Artifact, Memory candidate/memory, Automation, Audit event.
- **D-16:** Work item types are configurable. Built-ins: Initiative, Epic, Story, Task, Subtask, Bug, Chore. Templates/projects can define custom types, hierarchy rules, and allowed parent/child relations.
- **D-17:** Cycles and modules are built-in grouping dimensions. Projects/templates can define other grouping dimensions.
- **D-18:** Task detail is consumed through modes: Planning, Docs, Repo/Workspace, Agent Run, Knowledge, Audit/Activity.
- **D-19:** Mode content is backed by real linked records with stable IDs. Users and agents usually consume task modes, but docs, runs, artifacts, memory, and audit entries remain individually addressable.
- **D-20:** Web, CLI, and TUI share task mode vocabulary. CLI supports `work inspect <task> --mode planning|docs|repo|run|knowledge|audit` plus direct domain commands.

### Web IA And Density
- **D-21:** Topbar project picker owns the full hierarchy tree. Sidebar shows compact current scope, child shortcuts, and contextual sections. Sidebar must not become a giant portfolio tree.
- **D-22:** Cmd-K scopes actions to current project/subproject by default with visible scope override for parent/root/All projects. Mutations record scope in trace/audit.
- **D-23:** Default Web visual mode is minimal/simple plus balanced progressive disclosure. Advanced mode switch exposes dense operational console: compact tables, panes, relationship rails, and full trace/detail density.
- **D-24:** Advanced/minimal mode has both project default and user override, temporary or persistent. Mode affects presentation density, not capability or permissions.
- **D-25:** Run detail uses mode switch: default run review for status, summary, outputs, approvals, artifacts, and memory; advanced trace exposes Overview, Workflow, Context, Workspace, Session, Output, Recovery, Audit.

### Docs, Memory, Artifacts
- **D-26:** Docs use a hybrid model: user-authored docs are first-class records with tree/path/version/backlinks; task mode summaries are generated views that can snapshot/promote to docs when useful.
- **D-27:** First full spine includes doc templates: Spec, ADR, PRD, runbook, meeting note, retro, agent prompt, handoff, incident, release note, decision log.
- **D-28:** Memory scopes: workspace, project, subproject, task, run, doc, artifact, repo.
- **D-29:** Memory promotion is policy-based. Template/project/workflow can auto-promote low-risk scoped memories. Risky/global memories require review unless Full auto explicitly grants direct accepted memory writes.
- **D-30:** Every memory has source ref, scope, confidence, status, last used, supersession/replacement when applicable. Context preview explains why memory was included or excluded.
- **D-31:** Artifact lifecycle states: created, pending review, accepted, rejected, linked, promoted, archived, expired.
- **D-32:** Artifact retention uses template policy and project override. Local-first default keeps important artifacts; scratch/log artifacts can expire by policy. Retention actions are traceable/audited.

### Agent Authority And Run Policy
- **D-33:** Agent dispatch requires context preview by default. Template/project policy can allow auto-dispatch for trusted templates/tasks. Auto-dispatch still records context bundle, routing decision, workspace safety, actor/policy, and audit event.
- **D-34:** Auto-dispatch permission comes from template defaults plus project overrides.
- **D-35:** Approval gates are workflow/profile-defined and project-overridable. Defaults are loose, but tool classes and thresholds must be visible in run setup/run trace.
- **D-36:** Default agent authority is policy-controlled mutations. Full autonomy is a configurable mode.
- **D-37:** Effective agent permissions are computed from agent profile identity capabilities, workflow/template defaults, project policy, and task/run-specific overrides. Most restrictive wins unless explicit user override.
- **D-38:** Agents may perform admin/project actions when explicit policy/trust permits: template import/apply, project settings, doctor/reset proposals, plus work item/doc/artifact/memory/automation actions.
- **D-39:** High-risk actions require trust/policy trace and usually Manual/Assisted approval unless Full auto explicitly allows.
- **D-40:** Always gate destructive actions, executable template/scripts/hooks/shell/network actions, and authority escalation. Authority escalation includes Full auto enablement, project policy loosening, agent admin permissions, and template trust changes.
- **D-41:** Destructive actions are trust-mode aware. Manual/Assisted require approval. Trusted/Full auto can execute configured destructive actions only with policy, trace, and dry-run/snapshot safeguards. Schema reset/rebuild/delete gets extra confirmation unless user explicitly configures otherwise.

### CLI, TUI, API, Search
- **D-42:** CLI/TUI use dual primary model: workflow commands/workbench for journeys and domain commands/screens for direct object control.
- **D-43:** Canonical CLI command names use plurals for domains: `projects`, `tasks`, `docs`, `runs`, `artifacts`, `templates`; also canonical: `work`, `trace`, `memory`, `context`, `automations`, `audit`, `doctor`.
- **D-44:** Every relevant CLI JSON response includes entity data, typed `links`, typed `trace`, and audit/causation IDs. Full graph embedding is not default; explicit inspect/show commands expand.
- **D-45:** TUI starts by resuming last context. Fallback is active project workbench. Workspace portfolio remains available via shortcut/navigation. Status bar shows workspace/project/subproject, repo health, doctor/run state.
- **D-46:** Search defaults to current scope. Global/All projects search must be clearly available in Web, CLI, TUI, and API. Results include trace/provenance.
- **D-47:** Aggregate endpoints support selectable includes, e.g. `include=docs,runs,artifacts,memory,audit`. Default returns adjacent summaries/counts/IDs. UI modes and CLI `work inspect --mode` map to includes.
- **D-48:** Use typed trace spine plus extension links. Required spine fields where applicable: workspace, project, parentProject/subproject, repo, workItem/task, doc, contextBundle, routingDecision, run, liveSession, artifact, memory, audit. Zod schemas required for CLI/API/tRPC outputs.

### Automation, Reports, UAT
- **D-49:** Automation inheritance is configurable: rule applies to self, children, or selected descendants. Child override allowed unless parent locked module/rule. Rule trace shows inherited source and effective target scope.
- **D-50:** Parent dashboards are full drill-down dashboards. Parent aggregate actions use smart default + visible override from current grouping/filter/last-used child. Child overrides win unless parent locked the module.
- **D-51:** Canonical UAT fixture is full Agent OS bootstrap: workspace, parent project, subproject, repo, epic/tasks, docs, context, fake run, artifact, memory, automation, notification, report, CLI/TUI/Web/API verification using same IDs and trace spine.
- **D-52:** UAT uses both deterministic fake runs as required CI gate and optional real local agent run for final proof/UAT when environment supports it.
- **D-53:** Test architecture uses both journey suites and surface suites. H1-H6/A1-A5 journey suites own acceptance; Web/CLI/TUI/API surface suites own local regressions.
- **D-54:** Shared canonical UAT fixture proves cross-surface parity. Per-suite fixtures remain for focused tests. Tests must assert no orphan records.
- **D-55:** Final UAT is both checklist by journey and scenario scripts with expected IDs/screens/CLI/TUI outputs.
- **D-56:** Phase 10 required `09.6-CLOSURE-PROOF.md` citing automated evidence and final user UAT result. Final user UAT was accepted on 2026-05-08, so Phase 10 is unblocked.

### Startup, Local State, Migration
- **D-57:** Product not in use yet; Phase 9.6 can rebuild IA, routes, CLI/TUI flows, schemas, migrations, seeds, and local init for product correctness.
- **D-58:** No legacy compatibility requirement for product UX/API/CLI/TUI if old behavior conflicts with vision.
- **D-59:** Clean rebuild of local dev state is allowed. Existing local state can be reset if needed.
- **D-60:** Doctor/startup must support clean local rebuild path and actionable repair/reset command. No need to preserve current broken local state.

### the agent's Discretion
- Exact implementation ordering is planner discretion, but first full spine and startup/doctor repair must precede broad polish.
- Exact schema/table names are planner discretion if they implement the typed trace spine, hierarchy, inheritance, and no-orphan guarantees.
- Exact Web component composition is planner discretion if it preserves minimal default mode, advanced mode, project-first hierarchy, and shared mode vocabulary.
- Exact CLI subcommand spelling inside canonical command groups is planner discretion, but JSON must include `links`, `trace`, and audit/causation IDs.

</decisions>

## Specific Ideas

- Match Jira/Linear/Plane for project workflow, hierarchy, views, cycles/modules, command palette, triage, and reports.
