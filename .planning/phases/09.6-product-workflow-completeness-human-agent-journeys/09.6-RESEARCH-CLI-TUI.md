Findings:

- CLI help lists many domain commands but not cohesive workflow commands.
- `projects` help currently advertises `list|stats`, not full create/use/link-repo journey.
- Generated command families exist for many domains, which is useful for coverage but insufficient for product UX.
- CLI needs active project and workflow aliases that compose domain commands through the application layer.

## CLI Target Product Model

CLI must be scriptable, JSON-first, and workflow-first.

Global rules:

- Every command accepts `--project <slug|id>` or uses active project.
- Every mutating command supports `--json`.
- Every JSON response includes linked IDs: `projectId`, `taskId`, `docId`, `runId`, `artifactId`, `memoryId`, `repoId` when relevant.
- Commands return structured errors with repair hints.
- Workflow commands compose application services; generated CRUD remains advanced/admin.

## Required CLI Commands

Project and repo:

```text
fulcrum project use <slug>
fulcrum projects create --name <name> --repo-path <path> --template software --json
fulcrum projects show [--project <slug>] --json
fulcrum repos link --project <slug> --path <path> --json
fulcrum repos status --project <slug> --json
```

Work:

```text
fulcrum work init --project <slug> --repo-path <path> --json
fulcrum work triage list --project <slug> --json
fulcrum work triage accept <id> --project <slug> --json
fulcrum work plan --project <slug> --from-doc <docId> --json
fulcrum work inspect <taskId> --json
fulcrum tasks create --project <slug> --type epic|task|bug|subtask --parent <id> --json
fulcrum tasks move <taskId> --status <status> --json
fulcrum tasks relate <from> <rel> <to> --json
```

Docs:

```text
fulcrum docs tree --project <slug> --json
fulcrum docs create --project <slug> --template adr|spec|runbook|handoff --task <id> --json
fulcrum docs link --doc <id> --task <id>|--run <id>|--artifact <id> --json
fulcrum docs backlinks <docId> --json
fulcrum docs promote-memory <docId> --heading <heading> --scope project --json
```

Agent runs:

```text
fulcrum context preview --task <id> --project <slug> --json
fulcrum work run --task <id> --profile <profile> --json
fulcrum runs watch <runId> --json
fulcrum runs context <runId> --json
fulcrum runs artifacts <runId> --json
fulcrum runs memory-candidates <runId> --json
fulcrum runs cancel|retry|continue <runId> --json
```

Search/memory/artifacts:

```text
fulcrum search query <q> --project <slug> --kinds task,doc,run,artifact,memory --json
fulcrum memory candidates --project <slug> --json
fulcrum memory promote <candidateId> --scope project --key <key> --json
fulcrum artifacts list --project <slug> --task <id> --run <id> --json
fulcrum artifacts show <artifactId> --json
```

Automation:

```text
fulcrum automations list --project <slug> --json
fulcrum automations create --project <slug> --on run.completed --then notify --json
fulcrum automations test <ruleId> --event-file event.json --json
fulcrum notify list --project <slug> --json
fulcrum audit query --project <slug> --subject task:<id> --json
```

## TUI Target Product Model

TUI should be a keyboard-first operations console.

First screen:

```text
Current Project: <project selector>
Left pane: Work queue / navigation
Center pane: selected workflow surface
Right pane: relationship detail
Bottom/status: org, project, repo, run health, doctor health, key hints
```

Primary screens:

- Current project dashboard.
- Work queue/triage.
- Board/list/table compact work management.
- Task detail relationship hub.
- Docs tree + reader/editor.
- Run supervision.
- Context preview.
- Artifacts browser.
- Memory candidate review.
- Search.
- Automations/notifications/audit.
- Doctor/startup health.

Required key actions:

- `p`: switch project.
- `g`: go to project dashboard.
- `b`: board.
- `l`: list.
- `d`: docs.
- `r`: runs.
- `c`: context preview.
- `m`: memory.
- `a`: artifacts.
- `/`: search/filter.
- `k` or `Ctrl-K`: command palette.
- `n`: create contextual entity.
- `Enter`: open detail.
- `Space`: select/bulk action.
- `x`: cancel/close/reject depending context.
- `R`: retry run.
- `A`: approve gated action.

## TUI Screen Contracts

Project dashboard:

- Shows project identity, repo path/branch/status, active work, active runs, doc status, artifacts, memory candidates, doctor warnings.

Task detail:

- Header fields.
- Children/dependencies.
- Linked docs.
- Runs and run action.
- Artifacts.
- Memory/context.
- Comments/activity/audit.

Run supervision:

- Active run list grouped by project/status.
- Detail pane with status, heartbeat, current step, transcript summary, tool events, artifacts, memory candidates.
- Actions: cancel/retry/continue/approve/open context/open artifacts.

Docs:

- Project docs tree.
- Read view.
- Lightweight edit/create.
- Link to task/run/artifact.
- Promote section to memory.

Memory/context:

- Candidate queue.
- Promote/demote.
- Context preview for selected task/run.
- Provenance display.

## CLI/TUI Verification Gates

- CLI H1: `projects create --repo-path`, `project use`, `repos status`, JSON IDs.
- CLI H2: create epic/task/subtask, move status, add sprint/cycle, verify reports.
- CLI H3: create doc, link to task/run/artifact, backlinks, promote memory.
- CLI H4/A1-A5: context preview, dispatch run, watch run, list artifacts, promote memory candidate.
- TUI H1-H5: FakeTTY/OpenTUI tests render current project dashboard, task detail relationship panels, run supervision, docs tree, memory/context.
- Cross-surface parity: same entity IDs created via CLI appear in Web and TUI data fixtures.
