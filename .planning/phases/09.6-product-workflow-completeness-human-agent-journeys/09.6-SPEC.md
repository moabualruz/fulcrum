# Phase 9.6: Product Workflow Completeness — Specification

**Created:** 2026-05-08
**Ambiguity score:** 0.09

**Blocks:** Phase 10

## Goal

Turn Fulcrum from a collection of mostly implemented surfaces into one integrated local-first Agent OS product. Completion is measured by full human and agent journeys across Web, CLI, TUI, server/API, docs, memory, context, orchestration, artifacts, repos, notifications, and automation.

## Requirements

1. **Project-first product hierarchy**
   - Current: Web has global and project routes, but the shell still exposes a flat domain list and project context is inconsistent.
   - Target: Workspace -> Project -> Work item -> linked docs/runs/repos/artifacts/memory/context/automation is the default hierarchy.
   - Acceptance: Every work page has visible project context or explicitly states "All projects"; task/board/docs/runs/artifacts/memory views can be reached from project detail.

2. **Project setup includes local repository path**
   - Current: Project repo linking exists under `/projects/[id]/repos`, but first project setup does not make local path a first-class required step.
   - Target: Project creation flow supports local repo path and creates/links repo record.
   - Acceptance: Web, CLI, and TUI can create a project with local path and show repo status on project dashboard.

3. **Project management workflow parity**
   - Current: Boards, backlog, sprints, list/table/calendar/Gantt/reports exist as surfaces, but workflow cohesion and project selection are weak.
   - Target: Jira/Linear/Plane-style work management across project, backlog, board, sprint/cycle, list/table, calendar, Gantt, reports, task detail.
   - Acceptance: E2E creates project -> task hierarchy -> sprint -> board move -> report update and verifies same state via CLI and TUI.

4. **Task detail is the relationship hub**
   - Current: Task surfaces do not consistently expose linked docs, repo/branch, runs, artifacts, memory, dependencies, comments, activity, watchers, and automation.
   - Target: Task detail is the central hub for all work relationships.
   - Acceptance: Task detail shows and links all relationship panels; missing relationships have actionable empty states.

5. **Documentation is project/work scoped**
   - Current: Docs can be global/project but do not behave like Confluence/GitHub Wiki spaces integrated with tasks/runs/artifacts/memory.
   - Target: Project docs tree, templates, backlinks, versions, comments, and links to work entities.
   - Acceptance: Create doc from project task, link to task/run/artifact, edit, view backlinks/history, promote section to memory.

6. **Agent runs start from work**
   - Current: Runs exist globally and project-scoped, but dispatch is not clearly centered on task/context/repo.
   - Target: Primary run path is task -> context preview -> profile/routing -> dispatch -> supervise -> accept outputs.
   - Acceptance: Web/CLI/TUI dispatch from task with context preview and same run ID/data.

7. **Run detail is full agent observability**
   - Current: Run detail shows pieces, but completion must require trace/timeline/context/diff/artifacts/memory/follow-ups/provenance.
   - Target: LangSmith/Temporal-style inspectable run execution.
   - Acceptance: Run detail shows lifecycle, transcript/tool timeline, context bundle, diff, artifacts, memory candidates, follow-up tasks, audit, notifications.

8. **Artifacts are relational outputs**
   - Current: Artifact pages exist, but artifacts must be part of task/project/run/search/doc/memory workflows.
   - Target: Artifact source and downstream usage are visible everywhere.
   - Acceptance: Artifact generated by run appears in run, task, project artifacts, search, CLI, and TUI with source links.

9. **Memory/context loop is explicit**
   - Current: Doctor reports memory schema error; memory/context surfaces are not fully integrated into run/task/doc loops.
   - Target: Memory candidates from docs/runs/tasks can be reviewed and promoted; context bundles cite provenance.
   - Acceptance: Fresh doctor memory checks pass; run -> candidate -> promote -> context preview includes promoted memory with source.

10. **Automation and notifications close the workflow**
    - Current: Notifications/rules exist but are not clearly tied to entity lifecycle.
    - Target: Project-scoped rules react to task/run/artifact/memory events with audit and notifications.
    - Acceptance: E2E creates rule, triggers event, verifies notification and audit with entity links.

11. **CLI workflow commands**
    - Current: CLI exposes many domain commands, but connected workflow commands and active project behavior are insufficient.
    - Target: CLI supports active project, project create with repo path, task/doc/run/context/memory/artifact workflows with JSON.
    - Acceptance: CLI can complete human and agent journeys without web-only steps.

12. **TUI workflow shell**
    - Current: TUI starts as domain list navigation.
    - Target: TUI starts at current project/work queue and supports project dashboard, task detail, run supervision, docs, memory, context, artifacts.
    - Acceptance: TUI tests prove H1-H5 and A1-A3 workflows using the same application data.

13. **Server/API behavior is unified**
    - Current: Startup revealed multiple DB/init concepts and hidden env workaround.
    - Target: Packaged server, Vite web, CLI, and TUI use the same local state and application behavior.
    - Acceptance: Fresh `FULCRUM_HOME` starts server/web/CLI/TUI without `MIKRO_ORM_ALLOW_GLOBAL_CONTEXT` or schema errors.

14. **Doctor/startup blockers fixed**
    - Current: migration drift, memory schema error, product init error, web orgs error.
    - Target: Doctor is a reliable local readiness gate.
    - Acceptance: Fresh and existing local states pass doctor or report actionable migration repair with no false positives.

15. **Navigation and command palette are contextual**
    - Current: Flat nav and command palette risk disconnected CRUD.
    - Target: Nav and palette reflect current project and current entity context.
    - Acceptance: Palette actions create/link/update entities in current project; no dead/global-only actions for project work.

16. **Human journey verification**
    - Current: Tests prove small route/unit behaviors.
    - Target: Tests prove full workflows.
    - Acceptance: Playwright + CLI + TUI tests cover H1-H6 from `09.6-HUMAN-WORKFLOW-UX-SPEC.md`.

17. **Agent journey verification**
    - Current: Run/orchestration tests do not prove full product loop.
    - Target: Tests prove dispatch-to-output-to-memory-to-context loop.
    - Acceptance: E2E covers A1-A5 from `09.6-AGENT-WORKFLOW-UX-SPEC.md`.

18. **Docs and maps reflect reality**
    - Current: Phase completion docs overstate product completeness.
    - Target: Docs distinguish architecture completion from product workflow completion.
    - Acceptance: `.planning/codebase/**`, roadmap, requirements, graphify output, and phase docs updated after implementation.

19. **Deep research drives implementation**
    - Current: Earlier Phase 9.6 research was summary-level and did not deeply explore all product references, all topics, or all targeted Web/TUI/CLI code changes.
    - Target: Implementation consumes topic-specific deep research for platform products, Web UX, CLI/TUI, dependencies, code targets, and verification.
    - Acceptance: Every 9.6 execution plan cites the relevant deep research file and exact target files before edits.

20. **Symphony bidirectional compliance**
    - Current: Existing conformance docs prove architecture-level Symphony coverage, but Phase 9.6 needs full latest SPEC coverage plus Fulcrum-as-context-provider linkage.
    - Target: Fulcrum is compliant as a Symphony implementer and as a project/context provider: strict issue snapshots, workflow runtime snapshots, context bundles, workspace traces, app-server session traces, retry/reconciliation, artifacts, memory, audit, CLI/TUI/Web trace access.
    - Acceptance: `09.6-RESEARCH-SYMPHONY-COMPLIANCE.md` gaps are closed or explicitly scoped; §17 bullet-level conformance trace exists; Web/CLI/TUI expose same Symphony trace graph for a run.

21. **Trace and linkage completeness**
    - Current: Product surfaces can render domain objects without proving the adjacent workflow graph, which creates disconnected CRUD behavior.
    - Target: Every workflow object is relationally reachable through `workspace -> project -> repo/local path -> work item -> docs/context -> route/run/session -> artifacts/memory/follow-ups -> audit/reports`.
    - Acceptance: Entity APIs return adjacent links/counts; mutations emit audit events with causation ids; Web detail pages expose relationship panels and trace drawer; CLI JSON includes `links`/`trace`; TUI exposes active project workbench and trace pane; seeded E2E data contains no orphan tasks/docs/runs/artifacts/memory.

## In Scope

- Web shell/nav/project selector/command palette redesign for workflow cohesion.
- Project dashboard and project setup local path flow.
- Task/project/doc/run/artifact/memory/context relationship panels.
- CLI active project and workflow verbs.
- TUI current-project workflow shell.
- Server/local DB/doctor/product-init fixes.
- E2E journey tests across Web, CLI, TUI.
- Documentation and graph updates.

## Out of Scope

- SaaS multi-tenant hardening: Phase 10.
- Hosted cloud integrations beyond local/GitHub/Git repo paths unless already present.
- New AI model/provider systems.
- Visual marketing redesign.
